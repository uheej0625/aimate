# 로그

현재 구현은 Pino 구조화 로그를 stdout으로 출력한다. `app.environment: "development"`에서는 pino-pretty로 읽기 쉽게 표시한다. 운영 로그의 보관·회전·수집은 PM2 등 실행 환경이 담당한다. 앱 자체 파일 로깅 설정은 없다. CLI가 TTY에서 실행되면 대화 화면을 보호하기 위해 로그를 `silent`로 유지한다. CLI 로그가 필요하면 stdout을 파일이나 파이프로 전달한다.

Discord에서는 `/로그 채널`로 생성 로그를 임베드로 구독할 수 있다. 이 기능은 아래 Pino 레벨과 독립적이다.

## Discord 로그 채널

```text
/로그 채널 상태:활성화
/로그 채널 상태:활성화 대상:#봇-로그
/로그 채널 상태:비활성화 대상:#봇-로그
```

`상태`는 필수이며, `대상`을 생략하면 현재 채널을 사용한다. 서버 관리 권한이 있는 사용자만 설정할 수 있고 DM에서는 사용할 수 없다. 대상은 같은 서버의 텍스트·공지 채널이다. 활성화할 때 봇의 채널 보기·메시지 보내기·링크 임베드 권한을 확인한다. 권한이 사라져도 비활성화할 수 있다.

설정은 **서버·수신 채널별**로 기존 `Channel.logEnabled`에 저장된다. 여러 채널에서 생성 로그를 받을 수 있다. 활성화 시 Channel과 소속 Server가 없으면 등록하며, 기존 scope와 메시지 번호는 유지한다. 비활성화는 선택한 수신 채널의 logEnabled만 false로 바꾸고 이미 보낸 카드와 Channel 행은 남긴다. MessageHandler는 logEnabled가 true인 채널의 생성·수정·삭제 이벤트를 본문 조회·저장·응답 예약 전에 건너뛴다. 비활성화 후에는 일반 등록 채널의 수신 조건을 따른다. 로그는 해당 서버에서 앱이 실제로 저장한 기록을 대상으로 하며, 다른 서버·CLI·DM 기록을 전달하지 않는다. 메시지 본문도 포함되므로 로그 채널의 열람 권한은 운영자가 정한다.

카드는 기존 CHAT·IMAGE Generation의 상태, 진행 표시와 색상, 캐릭터, 프롬프트 이름, 시작·소요 시간, 요청·응답 원문을 보여준다. 대기 표시는 버퍼에서 읽고 생성 시작 후 같은 카드를 갱신한다. 저장된 [메시지와 관찰 사건](../대화/메시지와%20관찰%20사건.md)은 대기 요청을 구성하는 데 사용한다. 별도의 메시지·관찰 사건 로그 카드는 보내지 않는다.

파이프라인은 `대기 5.0s › 생성 3.1s › 전송 1.4s`처럼 단계별 소요 시간을 표시한다. 대기는 입력 묶음의 첫 관찰부터 Generation.createdAt까지로 버퍼 대기를 포함한다. 생성은 createdAt부터 `metadata.timings.generatedAt`까지이며 입력 준비·모델·도구 실행을 포함한다. 전송은 generatedAt부터 `metadata.timings.completedAt`까지로 일반 응답의 타이핑 지연·전송·저장을 포함한다. 모델 호출 중 실행한 reply 도구의 지연은 생성 시간에 들어간다. 진행 중인 단계는 `진행 중`, 경계가 기록되지 않은 단계는 `—`로 표시한다. 총 소요 시간은 첫 관찰부터 완료까지다. 재생성으로 updatedAt이 변경되어도 저장된 완료 시각을 사용한다. `시작`은 첫 관찰 시각을 Discord `<t:...:T>`로 표시한다. 관찰 snapshot이 없으면 Generation.createdAt을 사용한다.

기술 필드에는 Provider, 저장된 API 응답의 모델명, 토큰 usage의 입력·출력·합계, 실제 도구 호출을 표시한다. Provider는 apiRequest.provider와 SDK step.model.provider를 읽어 중복을 제거한다. 여러 API 응답은 합산하며 응답별 totalUsage를 우선해 step usage와 중복 합산하지 않는다. totalUsage·usage가 없으면 step usage를 합산하고, 모델명이 응답에 없으면 저장된 apiRequest.model을 사용한다. 도구 호출은 `generate_photo({"prompt":"..."})`처럼 이름과 입력 인자를 호출 순서대로 한 줄씩 표시하고, 같은 도구를 여러 번 실행해도 각 호출을 남긴다. step toolCalls, 응답의 toolCalls, assistant 메시지의 tool-call, 텍스트에서 복구해 실행한 도구를 지원한다. 필드 제한을 넘는 호출 상세와 도구 결과는 API 응답 전문에서 확인한다. 정보가 없는 기술 필드는 생략한다.

Generation의 프롬프트 이름과 요청·응답 칸은 대기 상태에서도 표시한다. 응답 이후 첫 사용자 메시지가 들어오면 채널별 대기 카드를 만들고, 이후 메시지·수정·삭제를 같은 카드의 요청 칸에 한 줄씩 누적한다. 항목 사이에는 줄바꿈을 한 번만 넣는다. 버퍼 turn이 교체되어도 대기 카드를 취소하거나 새로 만들지 않는다. 생성이 시작되면 같은 카드를 실제 Generation에 연결하고, 입력이 저장되면 `Generation.input.eventSnapshot`의 inputEventIds에 포함된 사건으로 갱신한다. 관찰 시각(observedAt) 순서로 표시하며, 같은 시각이면 Event ID 순서를 따른다. 채널 메시지 번호는 식별자이므로 수정·삭제 행에서도 같은 번호를 반복한다.

```text
#12 [메시지] "안녕[BREAK]반가워"
#13 [메시지] "테스트"
#12 [수정] "안녕[BREAK]반가워" → "안녕"
#13 [삭제] "테스트"
```

요청 본문은 JSON 문자열 표기로 표시해 공백·`[BREAK]`를 유지하고, 본문 내부 줄바꿈은 `\n`으로 나타낸다. 내용이 알려지지 않은 수정 전 본문 등은 `(내용 미상)`으로 표시한다. 모델 입력에 쓰인 설명문이나 저장된 snapshot은 로그 서식 때문에 변경하지 않는다. 응답 수신 전에는 `응답 대기 중`으로 표시한다. 응답은 기존 `Generation.apiResponse`의 SDK `response.messages`에서 마지막 생성 단계의 assistant 텍스트를 읽으며, `[BREAK]`·섹션·공백을 보존한다. 분할된 output을 다시 조립하거나 원문을 다른 필드에 중복 저장하지 않는다. IMAGE 요청은 기존 input, 응답은 output이다. 입력·응답 개수와 응답 미리보기 필드는 사용하지 않는다.

대기 카드는 기존 ConversationBuffer에 예약된 채널의 메시지 묶음을 아직 실행되지 않은 Generation처럼 표시하는 화면 상태다. `ConversationState.handledThroughEventId` 이후 사용자 메시지의 LIVE/READ·EDIT·DELETE를 읽어 대기 요청을 구성한다. 현재 Message 본문 대신 Event의 snapshotContent·previousContent를 사용해 당시 수신 내용과 수정 전후를 보존한다. 삭제된 Message의 수신·수정 기록도 그대로 남는다. 정상 완료된 입력은 다음 묶음에서 제외하고, 취소·실패로 처리되지 않은 입력은 다음 생성의 대기 묶음에 포함한다. 대기 중에는 현재 설정의 사용 예정 프롬프트 이름을 보여주고, 생성이 시작되면 실제 Generation.prompt로 갱신한다. 로그 때문에 PENDING Generation 행을 생성하거나 생성·취소 수명주기를 바꾸지 않는다. 생성으로 이어지지 않고 버퍼가 해제되면 해당 대기 카드를 취소 상태로 마친다.

로그 카드는 상태별 색상·진행 표시·푸터·시각을 사용한다. 사용자 Markdown을 이스케이프하고 멘션 알림은 끈다. 카드의 요청·응답이 임베드 필드 제한을 넘으면 일부를 표시하고, 해당 표시 내용 전체를 `generation-{id}-request.txt`·`generation-{id}-response.txt`로 첨부한다. 요청 파일도 같은 번호·관찰 유형·JSON 문자열 형식을 사용하며, 응답 파일은 assistant 텍스트 원문이다. 상태 변경 시 첨부도 현재 내용으로 교체한다. 전체 API 데이터는 아래 버튼에서 별도로 조회한다.

카드 아래에는 `API 요청 전문`·`API 응답 전문` 버튼 두 개를 둔다. 아직 API 데이터가 저장되지 않은 버튼은 비활성화한다. 요청 전문은 Generation.apiRequest 전체(system·messages·모델·설정 등)와 SDK가 남긴 step별 실제 request를 JSON으로 보낸다. 실제 request.body에 포함된 도구 정의와 도구 실행 후 후속 호출 내용도 그대로 포함한다. 여러 API 응답에 저장된 요청은 호출 번호(call)와 step 번호를 붙여 모두 내보내며, step별 request가 없으면 응답의 request를 사용한다. 응답 전문은 Generation.apiResponse 전체로서 모든 step·도구 호출·입력·도구 결과·usage·SDK 메타데이터를 포함한다. 저장하지 않은 네트워크 데이터는 추가로 수집하지 않는다.

요청·응답 전문은 항상 클릭한 사용자에게만 보이는 ephemeral 메시지로 UTF-8 txt 파일 하나만 첨부한다. 길이 검사와 본문 안내 문구는 사용하지 않는다. 파일 이름은 `generation-{id}-api-request.txt`·`generation-{id}-api-response.txt`다. JSON으로 디코딩하면 저장된 문자열의 공백·줄바꿈·`[BREAK]`도 유지된다. 버튼을 누를 때 DB에서 같은 서버의 Generation인지 확인하므로 재시작 후에도 조회할 수 있다. API 요청 전문에는 사용된 system prompt와 대화 컨텍스트도 포함되므로 로그 채널의 열람 권한은 운영자가 정한다. 전문이 아직 없거나 조회할 수 없는 경우의 안내도 클릭한 사용자에게만 보인다.

DiscordLogService가 1초마다 Channel의 로그 수신 설정과 기존 Generation의 변경을 읽는다. Discord gateway 메시지가 실제로 저장·수정·삭제되면 플랫폼 연결부에서 즉시 로그 갱신을 요청한다. 중복 메시지나 로그 채널 등 건너뛴 메시지는 갱신을 요청하지 않는다. CHAT의 기존 시작·완료·취소·실패 이벤트도 조회를 앞당긴다. Generation은 updatedAt을 기준으로 읽고 표시 내용이 같으면 다시 수정하지 않는다. 빠르게 지나간 중간 상태는 표시되지 않을 수 있다. 단계 시간은 polling 시점 대신 CHAT 상태 저장 때 같은 쓰기로 기록한 metadata.timings의 경계 시각을 사용한다. 조회·전송이 겹치면 같은 작업을 기다려 중복 실행을 막고, 다음 정기 조회에서 최신 상태를 다시 확인한다. Discord 전송 완료를 대화 처리에서 기다리지 않는다. 실패는 `discord.log.failed`에 남긴다. 종료 시 조회 타이머를 중단하고 진행 중인 전송과 마지막 동기화를 마친 뒤 Discord와 DB를 닫는다.

로그 수신 설정은 Channel에 남아 재시작 후에도 유지된다. 조회마다 DB에서 수신 채널을 읽으며, 활성화된 로그 채널이 없으면 Generation·대기 입력 조회는 하지 않는다. 카드 ID·마지막 표시 내용·대기 묶음은 DiscordLogService의 메모리 Map에 둔다. 재시작하면 카드 연결이 초기화되므로 기존 카드를 이어서 수정하지 않는다. 실행 중에는 같은 카드를 수정하며, 카드가 삭제되어 Discord가 Unknown Message(10008)를 반환하면 다시 생성한다. 로그 전용 테이블이나 과거 로그를 재생하는 저장·복구 기능은 없다.

기존 Channel에 기본값 false인 Boolean 필드 logEnabled를 추가한다. DB·Client 반영은 `npm run db:init`, 명령 등록은 `npm run deploy`로 실행하고 봇을 재시작한다. 로그 수신은 한 번 설정하면 유지된다.

구현: `src/platforms/discord/commands/log.js`, `src/platforms/discord/logging/`, `src/platforms/discord/events/interactionCreate.js`, `src/platforms/discord/createDiscordApplication.js`, `src/chat/ChatGenerationLifecycle.js`, `src/repositories/GenerationRepository.js`, `src/core/shutdown.js`, `prisma/schema.prisma`. 응답 데이터 계약 근거: `src/ai/metadata.js`.

검증: `test/platforms/discord/log.test.js`, `test/messages/MessageHandler.test.js`, `test/integration/ChatPipeline.integration.test.js`, `test/core/shutdown.test.js`.

## 설정과 레벨

`config/default.json`의 `logging.level` 기본값은 `info`다. 설정 파일 watcher가 활성화된 실행에서는 JSON reload 뒤 기존 모듈 로거에도 새 레벨이 적용된다. `app.environment`에 따른 pretty 출력 방식은 시작 시 결정하므로 변경 후 재시작한다. 설정 값·인증 값 전체를 출력하지 않는다.

| 레벨 | 기록하는 내용 |
| --- | --- |
| `debug` | 메시지 수신·큐 대기·처리·건너뜀 사유, turn 생성, 버퍼 예약·교체·실행·해제, 생성 단계 시작과 소요 시간, 모델 step 요약, abort 요청, 타이핑 지연, 조각별 전송·저장, 메시지 작업 영수증 재사용 |
| `info` | 앱 시작·종료, 봇 계정·플랫폼 준비, CHAT/IMAGE 생성 시작·완료·취소, 모델 호출 시작·완료, 도구 실행 시작·완료, 명령 핸들러 시작·완료 |
| `warn` | 모델 호출 실패 요약·경고 개수, 오류 결과를 반환한 도구, 전송 후 저장 재시도, 이미지 첨부 누락, 대체 처리로 전환하는 상황 |
| `error` / `fatal` | 생성 실패와 실패 단계, 도구 실행 예외, 전송·저장 실패, 오류 안내 전송 실패, 설정·플랫폼·이벤트 오류. 시작·커맨드 배포 실패는 fatal |

새 입력 때문에 이전 작업이 취소되는 것은 정상 흐름이다. 생성 취소는 `info`, 모델·도구의 abort와 abort 요청은 `debug`로 남긴다. 도구가 예외를 던지지 않아도 `error` 결과, `success: false`, `status: "error"/"failed"`이면 실패로 분류한다. 도구의 입력·결과 원문은 출력하지 않으며 반환된 오류 결과의 상세는 저장된 API 메타데이터와 함께 조사한다.

## 공통 필드와 연결

`event`는 검색에 사용하는 고정 이름이고 `msg`는 사람이 읽는 설명이다. 공통으로 ISO 시각 `time`, `level`, `module`이 있으며 실행 범위에 따라 다음 필드가 붙는다.

| 필드 | 의미 |
| --- | --- |
| `platform`, `platformChannelId` | Discord/CLI와 플랫폼 채널 ID |
| `channelId` | 내부 Channel.id. 등록 채널 조회 뒤 사용할 수 있음 |
| `turnId` | 채널의 응답 소유권을 식별하는 UUID. 버퍼 교체와 재생성을 구분 |
| `generationId`, `generationType` | 해당 CHAT/IMAGE 생성 기록 |
| `parentGenerationId` | 이미지 생성을 요청한 CHAT 생성 ID |
| `rerollGenerationId` | 재생성에 사용한 이전 CHAT 생성 ID |
| `toolName`, `toolCallId` | 도구와 SDK의 호출 ID. 텍스트 도구 호출 복구 등 호출 ID가 없는 실행도 있음 |
| `platformMessageId` | 입력·전송·저장·삭제 대상 메시지 ID. 수신 데이터에 따라 없는 경우도 있음 |
| `interactionId`, `commandName`, `platformUserId` | Discord 명령 실행 정보 |
| `durationMs`, `queueWaitMs`, `delayMs` | 단조 시계로 측정한 소요·대기 시간 또는 설정에 따라 계산한 타이핑 지연 |

AsyncLocalStorage로 비동기 실행 범위에 식별자를 전달한다. 동시 채널의 식별자가 섞이지 않으며, 이미지 생성에서는 자체 generationId를 사용하고 호출한 CHAT ID를 parentGenerationId로 남긴다. 이미지 생성이 끝나면 도구·CHAT 로그는 원래 범위로 돌아온다. 생성 기록이 만들어지기 전 오류에는 generationId가 없을 수 있다.

## 주요 이벤트

| 이벤트 | 확인할 내용 |
| --- | --- |
| `message.skipped`, `message.processed` | 미등록 채널·봇 작성자·변경 없음·관찰 시간 밖인지, 응답 예약 여부 |
| `buffer.scheduled`, `buffer.fired` | 예약 교체 여부, 설정된 timeout과 실제 대기 시간 |
| `generation.requested`, `generation.started` | 요청과 실제 생성 시작. stale turn은 `generation.skipped` |
| `generation.stage.started/completed` | `prepare_input`, `model`, `record_output`, `delivery`, `complete` 단계. 초기 준비 완료는 `start` 단계 |
| `generation.completed` | 총 시간, CHAT 메시지 개수와 실제 전달 여부. IMAGE는 이미지 ID·크기 |
| `generation.cancelled` | 취소 reason과 발생 stage. 일부 전달 후 취소됐다면 delivered가 true일 수 있음 |
| `generation.failed` | 실패 stage와 오류. CHAT은 해당 단계 시간도 기록 |
| `model.started/completed` | provider·model, 소요 시간. CHAT은 finishReason·step 개수·토큰 수·도구 호출 수, IMAGE는 이미지 크기와 제공된 토큰 수 |
| `model.step.completed`, `model.warnings` | step별 요약과 provider 경고 개수. 프롬프트·경고 원문은 출력하지 않음 |
| `tool.started/completed/failed/cancelled` | 도구 실행 결과와 소요 시간 |
| `message.send.started/completed/failed` | 실제 플랫폼 전송. chunkIndex는 0부터 시작 |
| `message.storage.retry/completed/failed` | 플랫폼 전송 확인 뒤 DB 저장. 저장 재시도는 메시지를 다시 보내지 않음 |
| `message.action.confirmed`, `message.action.reused` | reply/react 전달 확인 또는 기존 작업·영수증 재사용 |
| `generation.fallback.sent/skipped/failed` | 생성 실패 뒤 사용자 안내 처리 결과 |

`generation.completed`의 `messageCount: 0, delivered: false`는 정상적인 침묵이다. reply/react만 실행한 경우 메시지 개수가 0이어도 delivered는 true일 수 있다. `command.completed`는 명령 핸들러가 반환됐다는 뜻이며, 핸들러 내부에서 처리한 실패는 개별 오류 이벤트도 함께 확인한다.

모델의 `durationMs`는 SDK 호출 전체 시간으로 내부 재시도와 도구 실행이 포함될 수 있다. 세부 네트워크 요청별 재시도 횟수를 기록하는 것은 아니다. 토큰 필드는 provider가 반환한 경우에만 존재한다. `Generation` DB의 상태·입력·출력·API 기록과 로그는 별도 자료이며 로그 저장 실패를 DB 트랜잭션과 묶지 않는다.

## 장애 조사

먼저 `platformChannelId`로 채널을 찾고 `turnId`와 `generationId`로 요청을 좁힌다. `generation.failed.stage`나 마지막 `generation.stage.started`를 확인하면 입력 준비·모델·전송·저장 중 어디에서 멈췄는지 조사할 수 있다. 이미지 문제는 parentGenerationId를 통해 IMAGE 기록까지 따라간다.

`message.send.completed` 뒤 `message.storage.failed`가 있으면 사용자는 이미 메시지를 받았지만 저장은 실패한 상태다. `generation.cancelled`는 reason과 새 turn의 시작을 함께 확인한다. 수신 이후 생성이 시작되지 않았다면 `debug`로 올려 `message.skipped`, `message.processed`, `buffer.scheduled/fired`, `generation.skipped`를 확인한다.

```powershell
pm2 logs aimate --lines 200
```

일반 로그는 메시지·프롬프트·도구 입력 및 결과·응답 본문을 통째로 출력하지 않는다. 오류는 type·message·stack·code·statusCode·isRetryable과 제한된 cause를 직렬화한다. SDK 재시도 실패는 reason·실패 시도 개수와 마지막 오류도 보존한다. SDK 오류의 request·response·headers 같은 부가 객체는 제외한다. `secrets` 및 최상위/한 단계 아래의 알려진 인증 필드·headers는 마스킹한다. 임의 문자열, 오류 message·stack 안에 포함된 비밀까지 자동 제거하는 기능은 아니므로 오류 메시지에 사용자 본문이나 인증 값을 직접 넣지 않는다. 상세 API 기록 공유 시에는 [실행과 장애 대응](실행과%20장애%20대응.md)의 주의사항도 따른다.
