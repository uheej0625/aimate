# 메시지와 관찰 사건

`Message`는 플랫폼 메시지의 최신 상태이고 `Event`는 캐릭터가 읽거나 변화를 목격한 경험이다. 수정된 현재 본문을 과거에 읽은 것처럼 전달하지 않기 위해 분리한다.

## 수신과 저장

MessageHandler는 플랫폼·채널별 큐에서 이벤트를 처리한다. 등록된 Channel이 없으면 종료하고, CREATE·UPDATE에서 봇 메시지는 무시한다. 봇 출력은 전송 경로에서 따로 저장한다.

| 입력 | 상태 갱신 | 사건과 응답 |
| --- | --- | --- |
| 새 CREATE | 관련 계정·채널을 준비하고 Message 저장 | READ 생성, 이전 작업 취소와 새 응답 예약 |
| 중복 CREATE | 기존 메시지 유지 | 새 사건·응답 없음. 늦은 재수신으로 편집을 되돌리지 않음 |
| UPDATE | 최신 본문·수정 시각 갱신. 오래된 버전·삭제된 메시지는 무시 | 주시 중 본문 변화면 EDIT와 응답 예약. 비주시 변경은 상태만 갱신 |
| DELETE | `deletedAt`으로 soft delete | 주시 중 DELETE 기록. 삭제 대상에 사용자 메시지가 있으면 응답 예약 |

Message 저장·변경과 관련 Event 생성은 같은 트랜잭션으로 묶는다. 계정·서버 준비 전체가 하나의 트랜잭션인 것은 아니다. 일괄 삭제에는 `batchId`를 사용하고 중복 ID를 제거한다. 알 수 없는 삭제 ID는 tombstone Message로 남겨 늦은 CREATE가 되살리지 못하게 한다.

EDIT의 이전 내용은 최신 DB 본문이 아니라 마지막으로 관찰한 snapshot이다. DELETE도 마지막 관찰 내용을 사용하고 모르면 미상으로 표시한다. 삭제 실행자나 이유를 추정하지 않는다.

## 과거 내역을 읽는 시점

EventRepository의 `snapshot`은 DB에 저장된 활성 Message를 확인한다. 현재 내용과 마지막 관찰 snapshot이 다르면 `source: HISTORY`인 READ를 추가한다. Discord 서버에서 과거 메시지를 새로 가져오는 작업은 아니다.

HistoryService는 Event ID 순으로 경험을 렌더링한다. HISTORY는 ‘현재 과거 내역에서 읽음’으로, EDIT·DELETE는 목격한 변화로 구분한다. `source: LIVE`인 사용자 READ·EDIT·DELETE가 처리 대상 입력이다.

`discardedAt`이 있는 Generation의 사건은 일반 컨텍스트에서 제외한다. 일반 soft delete는 이미 관찰한 경험을 지우지 않는다.

## 담당 클래스와 호출 관계

| 클래스·메서드 | 입력과 결과 | 담당하는 결정 |
| --- | --- | --- |
| MessageHandler.handle | MessageEvent → changed·deletedCount·refreshed | 채널 등록, 수신 순서, 주시 여부, 응답 예약 |
| MessageService.saveMessage | 정규화 메시지 → 저장 Message와 관련 계정·채널 | 계정 준비와 최초 READ 또는 SENT 기록 |
| MessageService.updateMessage | 정규화 메시지와 observed → 실제 본문 변화 여부 | 오래된 편집 차단, 관찰한 이전 내용 유지 |
| MessageService.deleteMessages | 플랫폼 ID 목록과 observed → 삭제 결과 | soft delete, batchId, tombstone |
| EventRepository.snapshot | 내부 채널 ID → 경험 목록과 처리 범위 | HISTORY 보충, 철회 출력 제외, 재생성 snapshot 조회 |
| HistoryService.render | Event → 모델용 관찰 메시지 | EDIT·DELETE·HISTORY를 서로 다른 경험으로 표현 |

MessageHandler가 반환하는 changed는 DB 상태가 바뀌었음을, refreshed는 응답 예약을 갱신했음을 뜻한다. 비주시 UPDATE는 changed가 true여도 refreshed가 false일 수 있다. 두 값을 같은 의미로 사용하면 화면이나 명령 결과에서 잘못된 처리를 만들 수 있다.

## 예시: 읽은 내용과 현재 본문이 다른 경우

사용자 메시지의 최초 본문이 ‘금요일에 만나자’라고 가정한다. 봇이 이를 읽으면 Message와 READ snapshot 모두 그 본문을 가진다.

주시가 끝난 뒤 사용자가 ‘토요일에 만나자’로 수정하면 Message만 바뀐다. 나중에 봇이 과거 내역을 읽으면 토요일 본문을 HISTORY로 읽었다고 기록한다. 금요일을 읽었던 경험은 그대로 남는다. 따라서 ‘그때 편집되는 걸 봤다’고 표현하지 않는다.

비주시 중 토요일로 수정된 뒤, 과거 내역을 읽기 전에 주시 중 삭제가 발생하면 DELETE에는 마지막으로 관찰한 금요일 본문이 남을 수 있다. 삭제 순간의 DB 본문이 토요일이라는 이유로 봇이 그 중간 수정까지 알고 있었다고 만들지 않는다.

## 경계 조건과 수정 시 주의점

- UPDATE의 본문이 같고 editedAt만 달라지면 수정 버전은 저장할 수 있지만 본문 변화에 따른 응답은 예약하지 않는다.
- 처음 보는 완전한 UPDATE도 상태를 저장할 수 있다. observed=false라면 최초 발견을 EDIT 목격으로 꾸미지 않는다.
- CREATE 경로는 공통 처리기에서 빈 본문을 자동 차단하지 않는다. CLI는 UI 입력 정책을 별도로 적용할 수 있다.
- DELETE batch에는 사용자·봇 메시지가 섞일 수 있다. 사건은 각각 기록하되 응답 예약은 한 번만 한다.
- 플랫폼 이벤트와 명령이 동일한 삭제를 전달할 수 있다. 중복 방지는 공통 저장 경로에 유지한다.

구체적인 재현 근거는 통합 테스트의 idle edit, intermediate edit, mixed bulk deletion, older edit version 사례다.
