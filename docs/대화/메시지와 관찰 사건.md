# 메시지와 관찰 사건

`Message`는 마지막으로 확인한 플랫폼 메시지 상태이고 `Event`는 캐릭터가 읽거나 변화를 목격한 경험이다. 수정된 현재 본문을 과거에 읽은 것처럼 전달하지 않기 위해 분리한다.

## 수신과 저장

MessageHandler는 플랫폼·채널별 큐에서 이벤트를 처리한다. 대화 정책이 없는 실행에서 등록된 Channel이 없거나 어느 캐릭터든 로그 구독 중인 채널이면 본문 조회·저장·응답 예약 전에 종료한다. 자기 계정의 CREATE·UPDATE는 무시하고 자기 출력은 전송 확인 경로에서 SENT로 저장한다. 다른 캐릭터 소유 계정의 발언은 isBot 표식과 관계없이 READ로 관찰하고 자동 응답할 수 있다. 외부 봇의 발언은 관찰하지만 자동 응답하지 않는다. User.characterId로 캐릭터 소유권을 확인하며 자신의 발언에는 응답하지 않는다.

| 입력 | 상태 갱신 | 사건과 응답 |
| --- | --- | --- |
| 새 CREATE | 관련 계정·채널을 준비하고 Message 저장 | 캐릭터별 READ 생성. 응답 대상이면 이전 작업 취소와 새 응답 예약 |
| 이미 저장된 CREATE | 기존 메시지와 고정 번호 유지 | 해당 캐릭터의 첫 수신이면 READ 생성. 같은 캐릭터의 재수신은 사건·응답 없음 |
| UPDATE | 더 오래되지 않은 본문·첨부·수정 시각 갱신. 삭제 상태는 유지 | 주시 중 처음 받은 수정 버전이면 입력 snapshot으로 EDIT 기록. 다른 캐릭터가 먼저 상태를 갱신했어도 생략하지 않음 |
| DELETE | 활성 원본에 `deletedAt` 반영 | 각 캐릭터가 처음 목격한 DELETE 기록. 이미 공통 삭제된 메시지여도 관찰은 별도 |

Message 저장·변경과 관련 Event 생성은 같은 트랜잭션으로 묶는다. 계정·서버 준비 전체가 하나의 트랜잭션인 것은 아니다. 일괄 삭제에는 `batchId`를 사용하고 중복 ID를 제거한다. 알 수 없는 삭제 ID는 tombstone Message로 남겨 늦은 CREATE가 되살리지 못하게 한다. 주시 중이면 알 수 없는 삭제도 본문 미상의 DELETE로 기록하며 작성자를 모르므로 그 삭제만으로 응답하지 않는다.

LIVE 사건의 중복 키는 `(characterId, platform, platformMessageId, observationKey)`다. CREATE는 CREATE, 전송 확인은 SENT, 삭제는 DELETE를 사용한다. EDIT는 `observationId` 또는 플랫폼 editedAt으로 버전을 구분한다. 본문이 이전 값으로 되돌아와도 새로운 버전이면 새 경험이다. 관찰할 UPDATE에는 둘 중 하나가 필요하며 없으면 트랜잭션을 실패시킨다. editedAt이 없는 어댑터는 안정적인 observationId와 입력 순서를 보장해야 한다. 본문만으로 수정 중복을 추측하지 않는다.

공통 Message보다 오래된 수정이 늦게 도착해도 공통 최신 상태는 되돌리지 않는다. 해당 캐릭터가 처음 받은 버전이면 Event에는 수신 본문·첨부·editedAt을 그대로 남긴다. 같은 버전의 재수신은 새 경험이 아니다. 관찰 ID 순서와 플랫폼 수정 시각을 같은 것으로 취급하지 않는다.

플랫폼의 원래 전송 시각은 Message.sentAt에 별도로 저장한다. READ·SENT·EDIT·DELETE·HISTORY의 모델용 헤더는 대상 메시지의 이 시각을 사용하며, 사건의 observedAt은 관찰 시각으로 계속 보존한다. 수정·삭제가 전송 시각을 갱신하지 않으며 시각을 모르면 표시하지 않는다. 날짜·작성자·7분 간격에 따른 헤더 규칙은 [전송 시각과 화자 표시](../AI/컨텍스트와%20프롬프트.md#전송-시각과-화자-표시)를 참고한다.

EDIT의 이전 내용은 최신 DB 본문이 아니라 마지막으로 관찰한 snapshot이다. DELETE도 마지막 관찰 내용을 사용하고 모르면 미상으로 표시한다. 삭제 실행자나 이유를 추정하지 않는다.

## 과거 내역을 읽는 시점

EventRepository.snapshot은 해당 캐릭터의 기존 Event와 처리 cursor만 조회한다. 반복 호출해도 새로운 관찰이나 지식을 만들지 않는다. 최신 Message.content를 Event 본문으로 보충하지 않는다.

새 대화 세션의 LIVE 입력을 저장한 뒤, 응답 예약 전에 MessageService.readRecentHistory가 해당 계정의 ChannelPort.readHistory를 호출한다. 시작 입력 이전의 최근 최대 50건을 오래된 순서로 받아 HISTORY READ로 기록한다. 시작 입력은 LIVE로 보존하며 HISTORY에 중복 포함하지 않는다. 주시가 유지되는 동안에는 재조회하지 않는다. 현재 주시는 진행 중인 turn과 종료 후 10분이다. HISTORY는 문맥으로만 사용하고 응답을 예약하지 않는다. 50건은 새로 읽는 범위이며 이미 관찰한 전체 Event의 상한이 아니다.

Discord는 해당 client의 메시지 API를 cache=false로 호출한다. CLI는 로컬 플랫폼의 원본 저장소인 SQLite를 선택한 UI 채널에서 명시적으로 읽는다. Discord 조회 실패를 공통 DB로 대체하지 않는다. 조회 권한은 호출 전과 기록 전에 확인하며 다른 채널의 snapshot은 거부한다. 플랫폼 조회 실패 시 경고를 남기고 현재 LIVE 입력 처리는 계속한다. 읽기 기능이 없는 테스트 연결은 HISTORY를 추가하지 않는다.

HistoryService는 Event ID 순으로 경험을 렌더링한다. HISTORY는 ‘현재 과거 내역에서 읽음’으로, EDIT·DELETE는 목격한 변화로 구분한다. `source: LIVE`인 사용자 READ·EDIT·DELETE가 처리 대상 입력이다.

메시지는 최초 저장 시 채널별 고정 번호를 받는다. READ·SENT·EDIT·DELETE의 모델용 표시는 같은 대상의 번호를 유지하며, 번호순으로 경험을 재정렬하지 않는다. [메시지 번호와 답장·리액션](메시지%20번호와%20답장·리액션.md)에 발급·도구 실행 계약을 기록한다.

자신의 `discardedAt`이 있는 Generation에 연결된 사건은 자신의 컨텍스트에서 제외한다. A의 출력 철회가 B의 과거 READ를 숨기지는 않는다. 일반 soft delete도 이미 관찰한 경험을 지우지 않으며 실제 삭제를 목격하면 별도 DELETE가 남는다.

## 담당 클래스와 호출 관계

| 클래스·메서드 | 입력과 결과 | 담당하는 결정 |
| --- | --- | --- |
| MessageHandler.handle | MessageEvent → changed·observedChanged·deletedCount·refreshed | 채널 등록, 수신 순서, 주시 여부, 새 관찰에 따른 응답 예약 |
| MessageService.saveMessage | 정규화 메시지 → 저장 Message와 관련 계정·채널 | 계정 준비와 최초 READ 또는 SENT 기록 |
| MessageService.updateMessage | 정규화 메시지와 observed → changed·observedChanged | 공통 상태와 관찰 중복을 별도 판정, 관찰한 이전 내용 유지 |
| MessageService.readRecentHistory | 계정 ChannelPort와 권한 확인 → HISTORY READ | 명시적 최대 50건 읽기. 공통 상태로 경험을 추정하지 않음 |
| MessageService.deleteMessages | 플랫폼 ID 목록과 observed → 삭제 결과 | soft delete, batchId, tombstone |
| EventRepository.snapshot | 내부 채널 ID → 경험 목록과 처리 범위 | 읽기 전용 조회, 자기 철회 출력 제외, 재생성 snapshot 조회 |
| HistoryService.render | Event → 모델용 관찰 메시지 | EDIT·DELETE·HISTORY를 서로 다른 경험으로 표현 |

changed는 공통 Message 상태 변경, observedChanged는 해당 캐릭터의 새 Event 기록, refreshed는 응답 예약 갱신을 뜻한다. B가 A와 같은 수정을 목격하면 changed=false여도 observedChanged=true이고 응답할 수 있다. 비주시 UPDATE는 changed=true여도 관찰·응답은 없을 수 있다. 삭제 결과의 deletedMessages는 이번에 공통 삭제한 원본이고 observedMessages는 이번 캐릭터가 새로 목격한 대상이다.

## 예시: 읽은 내용과 현재 본문이 다른 경우

사용자 메시지의 최초 본문이 ‘금요일에 만나자’라고 가정한다. 봇이 이를 읽으면 Message와 READ snapshot 모두 그 본문을 가진다.

주시가 끝난 뒤 사용자가 ‘토요일에 만나자’로 수정하면 Message만 바뀐다. 나중에 봇이 과거 내역을 읽으면 토요일 본문을 HISTORY로 읽었다고 기록한다. 금요일을 읽었던 경험은 그대로 남는다. 따라서 ‘그때 편집되는 걸 봤다’고 표현하지 않는다.

비주시 중 토요일로 수정된 뒤, 과거 내역을 읽기 전에 주시 중 삭제가 발생하면 DELETE에는 마지막으로 관찰한 금요일 본문이 남을 수 있다. 삭제 순간의 DB 본문이 토요일이라는 이유로 봇이 그 중간 수정까지 알고 있었다고 만들지 않는다.

## 경계 조건과 수정 시 주의점

- UPDATE의 본문이 같아도 새로운 수정 버전이나 첨부 변경은 별도 관찰이다. 주시 중인 응답 대상의 새 관찰이면 응답을 예약할 수 있다.
- 버전 식별자가 없고 본문·첨부·수정 시각이 공통 상태와 모두 같은 UPDATE는 새 수정 관찰 없이 건너뛴다. 실제 내용이 달라진 관찰에는 버전 식별자를 요구한다.
- 처음 보는 완전한 UPDATE도 상태를 저장할 수 있다. observed=false라면 최초 발견을 EDIT 목격으로 꾸미지 않는다.
- CREATE 경로는 공통 처리기에서 빈 본문을 자동 차단하지 않는다. CLI는 UI 입력 정책을 별도로 적용할 수 있다.
- DELETE batch에는 사용자·봇 메시지가 섞일 수 있다. 사건은 각각 기록하되 응답 예약은 한 번만 한다.
- 플랫폼 이벤트와 명령이 동일한 삭제를 전달할 수 있다. 중복 방지는 공통 저장 경로에 유지한다.

구체적인 재현 근거는 통합 테스트의 idle edit, intermediate edit, mixed bulk deletion, older edit version 사례다.
