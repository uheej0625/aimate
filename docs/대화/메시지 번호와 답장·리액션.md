# 메시지 번호와 답장·리액션

`Message.channelMessageNo`는 채널 안에서 메시지를 가리키는 불변 참조 번호다. 모델 컨텍스트에서 `#11 본문`처럼 표시하며, 수정·삭제 경험에도 대상 메시지의 같은 번호를 붙인다. 사용자에게 전송하는 본문에는 시스템이 번호를 붙이지 않는다.

## 번호 발급

채널마다 1부터 시작한다. 최초 Message 저장 시 `Channel.lastMessageNo`를 원자적으로 증가시키고, 반환된 번호를 Message에 저장한다. 번호 발급·Message 쓰기·관련 관찰 Event 쓰기는 같은 트랜잭션이다. `(channelId, channelMessageNo)` 고유 제약도 둔다.

동일 플랫폼 메시지 재수신, 수정, 삭제, 재시작에는 기존 번호를 유지한다. 새 플랫폼 메시지로 교체하는 재생성이나 분할 전송은 새 번호를 받는다. 처음 보는 삭제 ID를 tombstone Message로 저장할 때도 번호를 발급하며, 이후 확인된 봇 출력을 채워 넣어도 번호와 삭제 상태를 유지한다. 조회 배열의 인덱스나 시간순 순위를 번호로 계산하지 않는다.

번호는 실제 발송 순서·채팅방의 메시지 총수·봇의 읽은 횟수를 보장하지 않는다. 번호 사이의 간격으로 관찰 공백을 추정하지 않는다.

| 저장 상황 | 처리 |
| --- | --- |
| 챗1~10 저장 후 챗11~100을 수신하지 못하고 챗101을 저장 | 챗101에 다음 번호 `#11` 부여 |
| 챗11~100을 저장했지만 봇은 관찰하지 않음 | 저장한 메시지들에도 번호가 있어 챗101은 `#101` |
| 챗101을 `#11`로 저장한 뒤 과거 메시지를 발견 | 발견한 메시지에 `#12`부터 발급. 챗101의 번호 유지 |

저장과 관찰은 별개다. 번호 발급 자체는 READ를 생성하거나 본문을 모델에 노출하지 않는다. 현재 snapshot은 저장된 활성 메시지를 HISTORY로 보충하는 정책을 유지한다. 앞으로 저장한 메시지를 정책상 읽지 않는 기능을 만들 때는 snapshot 대상 선정도 함께 바꿔야 한다.

## 모델 컨텍스트와 고정 입력

EventRepository가 Message의 번호를 사건 snapshot에 복사하고 HistoryService가 이를 전달한다. SequenceBuilder는 기존 사건 순서·role·관찰 시각을 유지하면서 번호를 본문 앞에 붙인다. history slice로 일부 사건을 제외해도 번호를 다시 매기지 않는다.

```text
#11 안녕
#11 [수정 목격]
이전에 읽은 내용: "안녕"
현재 내용: "반가워"
#11 [삭제 목격]
...
```

Generation.input의 `{id, content}`에서 id는 기존 전역 Message.id다. 번호는 eventSnapshot.events의 `channelMessageNo`에 보존한다. 따라서 사건·기억 참조와 번호를 혼용하지 않는다. 채널 밖에 참조를 저장할 때는 Message.id 또는 채널 ID와 번호의 조합을 사용한다.

## reply와 react

두 도구는 Discord에서 노출한다. CLI는 번호 표시를 공유하지만 답장·리액션 UI를 제공하지 않아 도구를 노출하지 않는다.

```javascript
reply({ targetMessageNo: 11, text: "여기에 답장할게." });
react({ targetMessageNo: 11, emoji: "👍" });
```

모델은 채널을 지정하지 않는다. 실행 컨텍스트의 채널에서 번호를 조회해 플랫폼 메시지 ID로 변환한다. 현재 생성의 관찰 snapshot에 있거나 해당 생성이 직접 보낸 봇 메시지만 대상으로 삼는다. 번호를 추측해 저장만 된 미관찰 메시지에 작업할 수 없다.

reply는 공백이 아닌 1~2000자 텍스트를 바로 전송한다. Discord 답장 참조에 `failIfNotExists: true`를 사용하고 대상 작성자의 자동 멘션은 끈다. 실제 전송 확인 후 Message와 SENT 사건을 현재 CHAT Generation에 연결해 저장한다. 같은 본문을 최종 messages에 또 넣지 않도록 도구 설명에서 안내한다.

react는 유니코드 또는 Discord 커스텀 이모지를 받는다. 플랫폼에서 대상을 다시 조회하고, 조회 중 취소되면 리액션을 추가하지 않는다. 리액션은 새 Message나 메시지 번호를 만들지 않는다. 별도 리액션 Event 종류는 없다.

대상 없음·삭제·채널 불일치·미관찰 대상·취소된 생성·플랫폼 오류는 모델에 error로 반환한다. 다른 메시지나 채널의 같은 번호로 대체하지 않는다. 플랫폼에서 실행 직전에 삭제된 답장 대상도 일반 발언으로 전환하지 않는다.

답장 또는 리액션만 성공하고 최종 messages가 비어 있어도 CHAT을 완료하고 처리 cursor를 전진시킨다. 주시 유예는 실제 플랫폼 작업의 성공 확인 시각을 기준으로 한다. 텍스트 형태의 도구 호출 회수 경로에서도 성공한 reply/react 뒤에 확인 문구를 추가 전송하지 않는다.

## 중복 실행과 재생성

MessageAction은 `(generationId, key)` 고유 키로 외부 작업 시작과 결과를 저장한다. key는 도구 종류·대상 번호·본문 또는 이모지의 해시다. 같은 생성 안에서 같은 작업을 동시에 호출하거나 다른 toolCallId로 반복해도 플랫폼 작업은 한 번만 시작한다.

확인된 답장 원본과 관찰 시각을 먼저 실행 결과에 저장한다. Message 저장만 실패하면 전송 없이 같은 확인 결과의 저장을 재시도할 수 있다. 실행 기록만 있고 결과가 없으면 성공 여부를 알 수 없으므로 재전송하지 않고 unknown 오류를 반환한다. 외부 API와 DB가 하나의 트랜잭션인 것은 아니므로 중단 시 자동 복구 worker나 무조건적인 exactly-once 보장을 제공하지 않는다.

재생성은 새로운 CHAT Generation이다. 기존 답장도 다른 봇 출력과 함께 기존 삭제·철회 경로에 포함되고, 교체 답장은 새 번호를 받는다. 이미 플랫폼에 추가한 리액션은 재생성이나 생성 취소로 제거하지 않는다. 이후 같은 봇의 같은 이모지를 추가하는 것은 플랫폼의 리액션 동작을 따른다.

## 스키마 적용과 검증

프로젝트의 개발 원칙에 따라 기존 데이터의 번호 backfill이나 migration을 구현하지 않는다. 필수 `Message.channelMessageNo`가 없는 기존 DB는 새 스키마로 재생성해야 한다. 코드 변경 과정에서는 사용자 개발 DB를 초기화하지 않는다. Prisma Client는 `npm run db:generate`로 생성한다.
