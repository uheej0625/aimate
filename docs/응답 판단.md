# 응답 판단

`conversation.responseMode`로 응답 방식을 선택한다. 기본값인 `buffer`는 기존처럼 마지막 입력 후 5초를 기다렸다가 생성한다. `decision`은 Parallel Decisions Fast로 참여 여부와 진행 중인 답변의 처리 방식을 판단한다. Discord와 CLI에 같은 규칙이 적용된다.

## 켜고 끄기

환경 변수에 `AI_GATEWAY_API_KEY` 또는 `VERCEL_OIDC_TOKEN`을 준비하고 YAML을 바꾼 뒤 재시작한다. 판단은 AI Gateway를 사용하며, 본문 생성 모델인 `ai.chat`은 기존 설정을 사용한다. 예를 들어 본문은 Vertex Gemini로 생성하면서 판단만 Parallel로 호출할 수 있다.

```yaml
conversation:
  responseMode: decision
```

Decision API를 사용할 수 없으면 `responseMode: buffer`로 설정한다. 이 모드에서는 Decision 모델이나 인증을 검증하거나 호출하지 않는다. 채팅·이미지 모델 자체의 인증은 여전히 필요하다. 캐릭터별 선택은 `characters[].settings.conversation.responseMode`로 덮어쓴다.

관련 기본 설정은 다음과 같다. 인증 값은 YAML에 넣지 않는다.

```yaml
ai:
  decision:
    provider: gateway
    model: parallel/parallel-decisions-fast
    prompt: default
    timeoutMs: 10000
    providerOptions: {}
conversation:
  responseMode: buffer
  bufferTimeout: 5000
  decision:
    debounceMs: 1000
    maxWaitMs: 5000
    recheckMs: 5000
    recheckMultiplier: 2
    maxRecheckMs: 30000
    maxContextMessages: 20
    maxContextTokens: 4000
    character: ""
    rules: ""
```

`ai.decision.provider`는 현재 `gateway`만 지원한다. 이 값은 [models.js](../src/ai/models.js)의 Decision 모델 생성에 사용하며 다른 provider를 지정하면 시작 시 거부한다. `ai.decision.prompt`는 chat·image와 같은 프롬프트 팩 이름이다.

`content/prompts/<팩>/decision/prompt.json`에 공통 지시문인 `instructions`, 대기 중 판단 기준인 `idle`, 생성·전송 중 판단 기준인 `active`를 둔다. 기본 경로는 `content/prompts/default/decision/prompt.json`이다. Decision API의 선택지별 기준을 그대로 표현하기 위해 JSON을 사용한다. 필수 키는 `idle`의 `respond`, `wait`, `ignore`와 `active`의 `keep`, `restart`, `stop`, `wait`다. 각 기준과 지시문은 비어 있지 않은 문자열이어야 하며 시작 시 검증한다.

`character`에는 참여 판단에 필요한 짧은 설명을 직접 지정한다. 본문 생성용 identity나 프롬프트 전체를 자동으로 읽어 넣지 않는다. 기본 참여 규칙은 Decision 프롬프트에 두고, YAML의 `rules`에는 캐릭터별 추가 규칙을 지정한다. `character`와 `rules`는 각각 최대 2000자다. 모드·Decision 설정·프롬프트 변경은 재시작 후 적용된다. 로컬 콘텐츠는 기존 정책대로 Git에서 제외하며, 공개 최소 예시는 [Decision 프롬프트 테스트 자료](../test/fixtures/prompts/minimal/decision/prompt.json)에 있다.

## 언제 판단하는가

정책상 관찰 가능한 새 메시지를 먼저 저장한다. 수정·삭제는 기존의 관찰 세션 규칙을 따른다. 외부 봇 제외, 비활성 채널 제외 등의 기존 정책도 유지한다.

Decision 모드에서는 마지막 입력 후 `conversation.decision.debounceMs`만큼 추가 입력을 모은다. 단위는 ms이며, `debounceMs: 0`은 이 예약 대기를 없앤다. 같은 채널의 판단 호출은 하나씩 실행하므로 호출 중 들어온 입력은 다음 판단 묶음에 포함한다. 0을 설정해도 메시지마다 별도 API 호출을 쌓거나 병렬로 실행하지 않는다. 입력이 이어질 때 예약 대기는 첫 입력부터 `conversation.decision.maxWaitMs`를 상한으로 한다. 이 상한은 API 응답 시간이나 본문 생성 시간을 포함하지 않으며, 같은 채널의 판단 호출이 진행 중이면 해당 호출이 끝난 뒤 다음 판단을 예약한다. 다른 채널은 독립적으로 진행한다.

호출 중 새 입력이 오면 그 호출의 결과를 버리고 최신 묶음을 다시 판단한다. 이전 호출을 입력마다 취소하거나 병렬로 늘리지는 않는다. 판단 중 기존 답변이 전송되거나 완료되어 상태가 바뀐 경우에도 결과를 버리고 다시 판단한다. 느린 API 호출은 메시지 수신 큐를 점유하지 않는다.

| 현재 상태 | 판단 | 처리 |
| --- | --- | --- |
| 대기 중 | `respond` | 최신 대화로 답변 생성 시작. |
| 대기 중 | `ignore` | 이번 묶음에 답하지 않고 판단 완료. |
| 생성·전송 중 | `keep` | 진행 중인 답변 유지, 이번 입력에 별도 생성 없음. |
| 생성·전송 중 | `restart` | 기존 작업을 취소하고 최신 대화로 다시 생성. |
| 생성·전송 중 | `stop` | 작업을 중단하고 이번 묶음의 판단 완료. |
| 어느 상태든 | `wait` | 진행 중인 작업이 있으면 중단하고 후속 입력 대기. |

`wait` 뒤 새 입력이 없으면 재평가를 반복한다. 다음 간격은 `min(maxRecheckMs, ceil(recheckMs × recheckMultiplier ^ 재평가횟수))`이며 첫 대기에서 횟수는 0이다. 기본 간격은 5 → 10 → 20 → 30 → 30초 순이다. 직전 판단과 결과 저장이 끝난 뒤 간격을 계산해 예약하며, 새 입력은 재평가 예약을 대체하고 횟수를 0으로 초기화한다. 이후에도 `wait`가 유지되면 상한 간격으로 계속 재평가한다. 다른 행동이 적용되거나 채널이 비활성화·종료되면 대기 재평가가 끝난다. API 실패 때는 기존과 같이 새 입력을 기다린다.

`debounceMs`는 0 이상의 정수, 재평가 간격은 양의 정수다. `recheckMultiplier`는 1보다 큰 유한수이며 소수도 허용한다. `maxRecheckMs`는 첫 간격 이상, Node 타이머 한도인 2,147,483,647ms 이하여야 한다.

시스템은 추정 대기와 명시적 대기를 분류하는 별도 상태를 두지 않는다. 다음 Decision 모델에 대화 문맥·마지막 입력 이후 경과 시간(`silenceMs`)·재평가 횟수(`recheckCount`)를 전달하고 계속 기다릴지 모델이 판단한다. 시간이나 횟수만으로 응답을 강제하지 않는다. chat 모델은 `respond`·`restart` 뒤에 호출되며, 대기 해제 자체는 Decision 모델이 결정한다.

Decision을 기다리는 동안 기존 답변은 계속 진행할 수 있다. 중단은 판단을 적용하는 시점부터 유효하며 이미 전송한 메시지를 회수하지 않는다. API 오류·10초 타임아웃 때는 기존 생성을 유지하고, 새로운 입력이 올 때 다시 판단한다. 자동 재시도나 buffer 모드로의 자동 전환은 없다.

## 어떤 문맥을 넣는가

- 해당 캐릭터가 해당 채널에서 관찰한 최근 20개 이벤트. 수정·삭제도 각각 이벤트로 센다.
- 최근 봇 발언과 새 입력의 답장 대상. 최근 20개 범위 밖이라도 별도로 조회한다.
- 작성자·시각·본문·멘션·답장 관계·수정 전 본문·첨부 유무. 첨부 파일 내용은 해석하지 않는다.
- 아직 판단을 마치지 않은 새 입력 표시, 현재 생성에 포함된 관찰 범위, 생성 상태, 마지막 발언과 입력 후 경과 시간, 재평가 횟수.
- 짧은 캐릭터 설명과 참여 규칙.

답장 대상이 관찰 기록에 없으면 해당 연결의 `ChannelPort.readMessage`로 읽는다. Discord가 이를 제공하며, 읽을 수 없으면 알 수 없는 대상으로 표시한다. 답장 관계 메타데이터는 최근 입력의 메모리에만 유지하며 DB 스키마는 추가하지 않는다.

입력은 JSON의 UTF-8 바이트 수를 3으로 나눈 **추정 토큰 예산**에 맞춘다. 실제 모델 토크나이저나 제공자가 추가하는 검색 문맥까지 제한하는 값은 아니다. 최신 새 입력, 최근 봇 발언·답장 대상, 나머지 새 입력, 과거 문맥 순으로 우선한다. 긴 본문은 잘라서 표시하고, 넣지 못한 항목 수를 함께 전달한다. 하나의 긴 메시지가 예산을 독점하지 않도록 항목별 크기도 제한한다.

이 제한은 Decision 전용이다. 본문 생성의 Event 문맥 제한과는 별개다. Parallel Decisions는 웹 근거를 활용하는 모델이며 현재 연결에는 검색을 끄는 전용 옵션이 없다. 판단 지시문은 주어진 채팅만으로 판단하도록 요청한다. 제공자 동작은 [Parallel 문서](https://docs.parallel.ai/decisions/decisions-quickstart)를 참고한다.

## 관찰과 처리 위치

`ignore`나 `keep`여도 메시지는 관찰 기록에 남아 다음 판단과 생성의 문맥으로 사용할 수 있다. Decision의 처리 위치는 메모리의 채널별 커서로 관리한다. 채팅 생성이 정상 완료될 때 갱신하는 DB의 `handledThroughEventId`와 구분한다. 판단만으로 채팅 생성 기록을 만들거나 채팅 입력을 처리 완료로 바꾸지 않는다.

판단 호출은 각각 `Generation.type: DECISION`으로 저장한다. `wait` 재평가도 별도 기록이다. 호출 전 `PROCESSING` 기록과 API 요청을 저장하고, 요청 저장에 실패하면 모델을 호출하지 않는다. `input`에는 실제 판단 state와 `throughEventId`, `apiRequest`에는 provider·model·프롬프트 팩·지시문·선택 기준·호출 설정을 남긴다. SDK client와 인증 객체는 저장하지 않는다.

`output`은 `action`과 `probabilities`의 JSON이며, `apiResponse`에는 SDK의 판단 답변·사용량·제공자 메타데이터·응답 정보를 저장한다. `metadata`에는 provider·model·사용량·소요 시간과 `application`을 남긴다. `application.applied`는 판단을 적용했는지 나타낸다. 응답을 시작했으면 `application.turnId`도 기록한다.

| 호출 결과 | Generation 상태 | 적용 정보 |
| --- | --- | --- |
| 성공하고 행동 적용 | `COMPLETED` | `applied: true`, `reason: null`. |
| 성공했지만 새 입력·응답 상태 변화로 폐기 | `COMPLETED` | `applied: false`, `new_input` 또는 `assistant_changed`. |
| 성공했지만 취소·정책 확인으로 미적용 | `COMPLETED` | `applied: false`, `cancelled` 또는 `channel_disabled`. |
| 성공했지만 행동 적용 중 실패 | `COMPLETED` | `applied: false`, `apply_failed`와 오류 종류. |
| API 실패·시간 초과 | `FAILED` | `applied: false`, `failed` 또는 `timeout`. |
| 취소 신호로 호출 중단 | `CANCELLED` | `applied: false`, 취소 이유. |

호출 결과와 행동 적용을 구분하므로, 이미 성공한 결과를 폐기했어도 호출 상태는 `COMPLETED`다. 오류는 종류와 상태 코드만 기록한다. 이 기록은 채팅 완료 처리와 독립적이며 `Event`를 추가하거나 기존 `Event.generationId`를 변경하지 않는다. `Generation.sentAt`도 비어 있다.

프로세스를 재시작하면 판단 커서는 초기화된다. 과거 메시지만으로 자동 판단을 시작하지는 않으며 새 입력이 계기가 된다. 채널 비활성화·종료 시 예약과 진행 중인 판단을 취소하고, 런타임 종료는 판단 작업이 끝나기를 기다린다.

일반 판단 로그에는 모델·행동·확률·시간·사용량을 남기며 대화 본문은 남기지 않는다. DB의 판단 입력·API 요청에는 문맥이 포함된다. Discord의 대기 카드는 판단을 마치고 채팅을 생성하지 않은 경우 취소 상태로 끝나고, DECISION 카드는 호출 상태와 판단 적용 여부를 별도로 표시한다.
