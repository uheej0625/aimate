# 테스트와 프롬프트 비교

자동 검증은 Node 내장 test runner를 사용한다. `npm test`는 cross-env로 NODE_ENV=test를 지정하고 `test/**/*.test.js`를 실행한다. 테스트 모드에서는 일반 설정 watcher와 development pretty 로깅을 억제한다.

## 검증 범위

| 대상 | 검증 위치와 핵심 시나리오 |
| --- | --- |
| 수신·저장 | `test/messages/`: 중복·편집·삭제, 관찰 정책과 snapshot |
| 세션·생성 | `test/chat/`: debounce, 순서·취소, 조건부 상태 전이 |
| 프롬프트 | `test/chat/context/`: sequence, 시간 표지·배치, 필수 파일 |
| AI·도구 | `test/ai/`, `test/tools/`: 모델 선택, native 도구, 이미지·abort |
| 플랫폼 | `test/platforms/`: 어댑터, Discord 삭제·기동, CLI TUI |
| 공통 흐름 | `test/integration/ChatPipeline.integration.test.js`: 파이프라인의 경합과 완료 |
| 비교 스크립트 | `test/scripts/compareCharacterPrompts.test.js`: 입력 일관성·원문 계약·도구 모의 실행 |

```powershell
npm test
$env:NODE_ENV = 'test'
node --test test/chat/ConversationSession.test.js test/messages/MessageHandler.test.js
```

테스트 근거는 구현 의도를 확인하는 자료이며 실서비스의 네트워크 성공을 보장하지 않는다. 수정한 행동에 필요한 검증부터 실행한다. 문서만 변경할 때는 링크·경로·다이어그램과 설명의 정확성을 확인한다.

## 프롬프트 비교 스크립트

`scripts/compareCharacterPrompts.js`는 snapshot과 compare 두 모드를 제공한다. `characterPromptCases.js`의 사례와 고정 시각으로 before/after 입력을 구성하고 생성 결과를 다음 사례에 넘기지 않는다.

```powershell
node scripts/compareCharacterPrompts.js snapshot --out .local/prompt-baseline --prompt-dir content/prompts/<pack>/chat --character-dir content/characters/<id>
node scripts/compareCharacterPrompts.js compare --baseline .local/prompt-baseline --out .local/prompt-dry-run --prompt-dir content/prompts/<pack>/chat --dry-run
```

`<pack>`과 `<id>`는 실제 이름으로 바꾼다. output 디렉터리는 새 위치여야 한다. snapshot은 팩·캐릭터 파일을 복사하고 snapshot.json을 만든다. compare는 baseline 캐릭터를 양쪽에 사용하므로 캐릭터 자체를 before/after 비교하는 도구가 아니다.

`--dry-run`은 모델 호출 없이 입력 파일과 보고서를 작성한다. 옵션을 빼면 실제 AI 호출을 수행한다. `--case <ID>`로 사례를 선택할 수 있으며 nativeTools는 비활성화해야 한다. 사례의 도구는 모의 실행으로, 이미지 실패와 status 결과를 재현한다.

results.json·report.md에 원문, 메시지 수, token usage, 도구 실행, 계약 위반을 남긴다. 검사 계약은 `# response`, `## messages`, 한 줄 본문과 정확한 `[BREAK]` 구분자다. 운영 파서보다 엄격하며 text-tool 회수도 위반으로 기록한다. 캐릭터 품질·캐시 개선은 사람의 검토가 필요하다.

복사한 팩·캐릭터와 모델 입력·응답은 비공개 자료를 포함할 수 있다. 예시 `.local/`은 Git 제외 설정에 추가했으며 결과를 위키에 복사하지 않는다. 현재 비교 스크립트와 테스트는 기존 로컬 작업을 그대로 참조하며 이 위키 작업에서 구현을 수정하지 않는다.

## 테스트 파일을 고르는 기준

메서드 반환과 객체 간 호출 계약을 바꾸면 해당 단위 테스트를 먼저 확인한다. 저장과 취소 순서, cursor, 플랫폼 전송 결과가 함께 바뀌면 ChatPipeline 통합 테스트가 필요하다. 이 통합 테스트는 별도 임시 SQLite DB와 모델 대체 함수를 사용해 동작을 재현한다.

현재 핵심 통합 시나리오는 중복 봇 echo, 비주시 편집, 주시 중 삭제, 전송 도중 새 변화, 철회한 출력의 재등장 방지, 저장 재시도 시 중복 전송 방지다. 코드 줄마다 구현을 따라 쓰는 테스트보다 이 사용자 행동이 유지되는지 확인한다.

## 비교 결과를 해석하는 순서

먼저 같은 case의 before/after input을 비교해 기대한 프롬프트 변경만 반영됐는지 확인한다. 다음 원문 계약 위반과 native tool call을 보고, 마지막으로 짧은 메시지의 자연스러움·캐릭터·상황 대응을 검토한다.

최종 messages가 정상처럼 보여도 운영 파서나 text-tool 회수가 원문 위반을 보정했을 수 있다. rawText와 violations를 함께 봐야 한다. 캐시 읽기 값이 미제공이면 미측정이며 0이나 개선 없음으로 단정하지 않는다.

snapshot은 비교에 쓸 캐릭터와 팩을 고정한다. compare는 현재 설정의 복사본을 사용하므로 모델·provider 설정까지 baseline 시점 그대로 복원하는 도구는 아니다. 보고서 settings를 확인해 실행 조건 차이를 구분한다.
