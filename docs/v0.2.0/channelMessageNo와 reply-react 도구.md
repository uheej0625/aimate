# channelMessageNo와 reply/react 도구 설계

이 문서는 `channelMessageNo`와 이를 사용하는 답장·리액션 도구의 설계 초안이다. 컨텍스트 구성 개편의 구현 범위에서는 제외하며, `reply`/`react` 도구를 만들 때 별도 검토·확정한다.

아래 내용은 분리 전 문서의 제안을 보존한 것이며, 구현 완료나 스키마 확정을 의미하지 않는다. 컨텍스트 축소·요약 사례는 번호의 불변성을 설명할 뿐이며, 현재 확정된 무제한 히스토리를 변경하지 않는다.

## 목적

AI가 특정 메시지를 정확히 가리킬 수 있도록 컨텍스트에 고정 번호를 표시한다. 같은 문구가 여러 번 등장해도 수정·삭제의 대상, 답장 대상, 리액션 대상을 구분할 수 있어야 한다.

```text
#1 사용자: 안녕?
#2 AI: 반가워!
#3 사용자: 사랑해
[#3의 내용이 삭제되었습니다.]
```

번호를 표시하지 않고 본문이나 상대적 위치로 대상을 선택하는 방법도 가능하지만, 동일 문구의 반복이나 새 메시지 유입으로 대상이 모호해질 수 있다. 앞으로 답장과 리액션 도구에서도 같은 참조 방식을 사용한다.

## 채널별 고정 번호

기존 전역 `Message.id`는 유지하고, AI에게 표시할 채널별 메시지 번호를 별도로 저장한다. 각 채널은 1부터 시작하며, 한 번 부여한 번호는 바꾸거나 재사용하지 않는다.

전역 ID를 그대로 표시해도 메시지 식별 기능에는 문제가 없다. 다만 다른 채널의 메시지 저장에 따라 번호가 크게 뛰고 숫자가 커진다. 채널 안에서 사용할 참조 번호는 채널별로 관리한다. 번호가 연속적이라는 이유만으로 모델의 이해도나 도구 선택 정확도가 향상된다고 가정하지는 않는다.

| 식별자 | 역할 |
| --- | --- |
| `Message.id` | DB 전체에서 메시지를 식별한다. 기존 사건·기억 등의 참조에 사용한다. |
| `Message.channelId` | 메시지가 속한 채널을 식별한다. |
| `Message.channelMessageNo` | 추가할 채널별 고정 번호다. 컨텍스트에서 `#3`처럼 표시한다. |
| `Message.platform` + `Message.platformId` | 실제 플랫폼 메시지를 식별하고 답장·리액션을 실행하는 데 사용한다. |
| `Event.id` | 메시지를 읽거나 수정·삭제를 목격한 개별 사건을 식별한다. 메시지 번호와 구분한다. |

`channelId`와 `channelMessageNo`의 조합은 유일해야 한다. 서로 다른 채널에 같은 번호가 존재하는 것은 정상이다.

| 기존 DB ID | 채널 | 채널별 번호 | 내용 | 상태 |
| --- | --- | --- | --- | --- |
| 100 | A | 1 | 안녕 | 유지 |
| 101 | B | 1 | 안녕하세요 | 유지 |
| 105 | A | 2 | 반가워 | 삭제됨 |
| 182 | A | 3 | 뭐 해? | 유지 |

```text
A 채널의 #3 → DB 메시지 182 → 해당 플랫폼 메시지
B 채널의 #1 → DB 메시지 101 → 해당 플랫폼 메시지
```

## 번호 부여와 저장

번호는 메시지를 처음 저장할 때 한 번 부여하고 `Message`에 영속 저장한다. 채널별 마지막 발급 번호도 영속 저장한다. 마지막 발급 번호의 구체적인 저장 위치는 구현 시 정한다.

1. 플랫폼 식별자로 이미 저장된 메시지인지 확인한다. 같은 메시지의 재수신이면 기존 번호를 사용한다.
2. 새 메시지라면 해당 채널의 마지막 발급 번호 다음 값을 할당한다.
3. 메시지 저장과 채널의 마지막 발급 번호 갱신을 같은 트랜잭션에서 처리한다.
4. 동시 저장에서도 번호가 중복되지 않도록 발급을 직렬화하거나 원자적으로 갱신하고, DB의 조합 고유 제약으로 중복을 막는다.

```text
A 채널의 마지막 발급 번호: 3
→ 새 메시지에 4 부여
→ Message.channelMessageNo = 4로 저장
→ A 채널의 마지막 발급 번호를 4로 갱신
```

조회 시에는 저장된 번호를 읽는다. 채널별 메시지를 매번 시간순으로 나열해 순번을 다시 계산하지 않는다. 현재 조회 결과의 개수나 배열 인덱스도 번호로 사용하지 않는다.

번호의 유일성과 불변성이 중요하다. 삭제, 컨텍스트 제한 등의 이유로 표시되는 번호 사이에 빈틈이 있어도 괜찮다. AI가 보지 않은 메시지에 번호가 있다는 이유로 그 내용을 컨텍스트에 노출하지 않는다.

## 번호가 유지되는 경우

| 상황 | 처리 |
| --- | --- |
| 메시지 수정 | 같은 메시지 번호를 유지한다. |
| 메시지 삭제 | 삭제된 메시지의 번호를 유지하고 재사용하지 않는다. |
| 같은 플랫폼 메시지 재수신 | 기존 번호를 사용한다. |
| 봇 재시작·날짜 변경 | 마지막 발급 번호 이후부터 계속한다. |
| 오래된 컨텍스트 제외·요약 | 남은 메시지의 번호를 바꾸지 않는다. |
| 기존 메시지를 과거 내역에서 다시 읽음 | 기존 번호를 사용한다. 새 관찰 사건과 구분한다. |
| 처음 발견한 과거 메시지 저장 | 다음 번호를 새로 부여한다. 기존 번호는 변경하지 않는다. |
| 새 플랫폼 메시지로 AI 답변 재생성 | 새 메시지 번호를 부여한다. 교체된 출력의 번호는 재사용하지 않는다. |

사용자와 AI 메시지는 같은 채널 번호 체계를 공유한다. AI 응답이 실제 플랫폼 메시지 여러 개로 나뉘어 전송되면 각각 별도 번호를 부여한다. 답장·리액션의 대상이 되는 단위가 개별 플랫폼 메시지이기 때문이다.

번호는 시스템이 저장된 메시지에 부여한다. 모델이 생성 중인 자신의 메시지 번호를 임의로 정하거나 다음 번호를 예측하게 하지 않는다.

## 시간순 정렬과 번호의 관계

번호는 해당 메시지의 고정 참조값이며, 채널의 실제 역사에서 몇 번째로 발송된 메시지인지까지 뜻하지 않는다. 메시지 번호 부여와 컨텍스트의 사건 정렬은 별도로 처리한다. 기존 관찰 사건의 순서를 번호순으로 재정렬하지 않는다.

Soft delete는 삭제에 따른 순번 변경을 막는 데 도움이 되지만, 매번 시간순 순위를 계산해도 번호가 유지된다는 보장은 하지 않는다. 나중에 가져온 과거 메시지를 발송 시각 기준으로 중간에 넣으면 순위가 바뀔 수 있다.

```text
매번 순번을 계산하는 경우:
기존       #1 안녕 → #2 반가워
과거 추가  #1 안녕 → #2 누락됐던 발언 → #3 반가워
```

이 경우 기존 참조 `#2`의 의미가 바뀐다. 고정 번호 방식에서는 `반가워`의 번호를 유지하고, 새로 발견한 메시지에 다음 번호를 부여한다.

컨텍스트를 최근 일부로 제한하더라도 다시 1부터 매기지 않는다.

```text
전체 기록:  #1, #2, #3, #4
일부 제외:          #3, #4
```

## 수정·삭제 사건의 표시

번호는 메시지에 붙이고, 수정·삭제 사건은 대상 메시지 번호를 참조한다. 수정·삭제 알림 자체가 새 메시지 번호를 소비하지 않는다.

```text
#1 사용자: 안녕?
#2 AI: 반가워!
#3 사용자: 사랑해

[#3 수정: "사랑해" → "좋아해"]
[#3 삭제됨]

#4 사용자: 못 본 걸로 해줘.
```

내부적으로는 각 수정·삭제 사건에 별도 `Event.id`가 존재한다. 개별 사건을 도구 대상으로 지정할 필요가 없다면 사건 ID까지 컨텍스트에 표시할 필요는 없다.

위 예시는 참조 형식을 설명하기 위한 것이다. 실제로 AI가 목격한 수정·삭제만 기존 관찰 정책에 따라 전달한다. 번호 도입으로 원문 보존 정책을 변경하거나, 삭제 실행자와 이유를 추정하지 않는다.

`[#3 삭제됨]`이라는 참조만으로 AI가 원문을 알 수 있는 것은 아니다. 원문이 컨텍스트에서 제외된 경우, 내용을 알아야 하는 작업에는 관찰한 원문이나 필요한 발췌를 함께 제공하거나 별도로 조회할 수 있어야 한다. 보지 못한 원문을 복원한 것처럼 제시하지 않는다.

## 답장·리액션 도구와 연결

모델은 현재 채널에서 대상 메시지 번호를 선택한다. 채널은 모델이 임의로 지정하는 값이 아니라 현재 요청의 실행 컨텍스트에서 가져온다.

```text
현재 요청의 채널 + 대상 메시지 번호
→ 저장된 Message 조회
→ 플랫폼 메시지 식별자와 현재 상태 확인
→ 플랫폼에 답장 또는 리액션 실행
→ 모델에 성공·실패 결과 반환
```

다음은 도구 호출 형식의 예시다.

```js
reply({
  targetMessageNo: 3,
  text: "여기 너가 이렇게 말했잖아.",
});

react({
  targetMessageNo: 11,
  emoji: "😴",
});
```

같은 번호가 다른 채널에 있어도 현재 채널과 함께 조회하므로 충돌하지 않는다. 대상이 없거나 실행 전에 삭제되어 작업할 수 없다면 실패를 반환한다. 다른 메시지로 대체하거나 다른 채널에서 같은 번호를 찾아 실행하지 않는다. 재시도·재생성 과정에서는 같은 답장이 중복 전송되지 않도록 실행 결과를 관리해야 한다.

컨텍스트의 번호 표시와 실제 사용자에게 보이는 채팅 표시는 별도다. AI는 `#3`을 선택하되, 사용자에게는 플랫폼의 답장 UI와 답변 본문만 보여줄 수 있다.

채널 밖으로 참조를 옮기는 요약·기억에는 번호만 단독으로 보관하지 않는다. DB 메시지 ID 또는 채널과 번호의 조합으로 원래 대상을 식별할 수 있어야 한다.

## 기존 데이터 적용

기존 메시지는 채널별로 정렬해 최초 한 번 번호를 부여하고 저장한다. Soft delete된 메시지도 포함해 수정·삭제 사건의 참조 대상을 유지한다. 초기 정렬 기준과 동일 시각의 순서 기준은 구현 시 확정한다.

초기 번호 부여 후 채널별 마지막 발급 번호를 설정하고, 이후 새 메시지에는 다음 번호만 발급한다. 과거 메시지 추가, 조회 조건 변경, 재시작을 이유로 기존 번호를 다시 계산하지 않는다.

기존 `Message.id`와 이를 참조하는 사건·기억의 관계는 유지한다. 현재 수정·삭제 표기에 쓰는 전역 메시지 ID와 새 채널별 번호가 같은 `#숫자` 형식으로 혼용되지 않도록 컨텍스트 렌더링과 도구의 번호 해석을 함께 맞춘다. 기존 생성 입력·재생 기록의 참조 방식도 적용 시 확인한다.

## 구현 시 확인할 사례

- A 채널과 B 채널이 각각 `#1`부터 시작하고, 도구가 현재 채널의 메시지만 선택한다.
- 사용자와 AI 메시지가 같은 번호 체계를 사용하며, 분할 전송된 AI 메시지는 각각 식별된다.
- 동시 수신과 동일 플랫폼 메시지 재수신에서도 번호가 중복 발급되지 않는다.
- 수정·삭제, 봇 재시작, 컨텍스트 축소 이후에도 기존 번호가 유지된다.
- 과거 메시지를 뒤늦게 추가해도 기존 답장·삭제 참조가 다른 메시지를 가리키지 않는다.
- 도구 실행 전에 대상이 삭제되면 실패가 반환되고, 재시도로 답장이 중복 전송되지 않는다.
- 기존 데이터의 초기 번호 부여 후에도 사건·기억과 생성 입력의 참조가 올바른 메시지로 연결된다.

관련 기존 설계: [메시지 사건과 대화 주시](message-observation-design.md). 현재 데이터 구조: [Prisma 스키마](../prisma/schema.prisma).
