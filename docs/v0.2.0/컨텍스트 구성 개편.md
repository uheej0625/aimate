# 컨텍스트 구성 개편

이 문서는 모델에 전달할 컨텍스트의 배치 순서, 시간 정보의 위치, 메시지 식별 번호를 제안한다. 자연어 프롬프트의 문구 재작성은 별도 작업으로 둔다. 아래 조립 코드, 컬럼명과 도구 호출 형식은 설계 예시이며, 구현 완료를 의미하지 않는다.

## 범위와 전제

- 현재 캐릭터·채널에서 컨텍스트에 포함할 수 있는 메시지와 관찰 사건은 개수 제한 없이 전부 포함한다. 최근 N개 선택, 날짜 기준 절단, 요약으로 원문을 대체하는 방식은 이번 안에 넣지 않는다.
- 전체 포함은 기존 관찰·가시성 정책 안에서의 전체를 뜻한다. 다른 채널의 기록, 목격하지 않은 수정 원문, 재생성으로 폐기된 출력까지 노출한다는 뜻은 아니다. 플랫폼에서 과거 메시지를 새로 수집하는 범위도 별도다.
- `fact`와 `episode`는 아직 존재하지 않는 기능이다. 위치와 주입 외형만 예약하고, 주입 코드는 주석 처리한다. 조회·추출·저장·검색 기능이나 가짜 데이터는 추가하지 않는다.
- 현재의 `MemoryService`와 `userMemories`를 새 `fact`·`episode` 기능으로 간주하지 않는다. 제안하는 조립 경로에서는 기존의 맨 앞 기억 주입을 사용하지 않으며, 기존 기억 데이터의 이전은 별도 작업이다.
- 이 문서는 설계만 갱신한다. 실제 소스, 사용자 소유 프롬프트, DB와 스키마는 변경하지 않는다. 모델 입력 한도를 넘는 경우의 처리는 별도 설계 대상으로 남긴다.

## 제안하는 최종 순서

핵심은 고정 내용과 누적 기록을 먼저 두고, 요청마다 달라지는 내용을 맨 뒤에 두는 것이다. 최신 사용자 입력도 전체 기록 안에서 제자리를 유지한다.

| 순서 | 내용 | 전달 형태 | 변경 기준 |
| --- | --- | --- | --- |
| 1 | 시스템 지시 | API의 `system` | 프롬프트·플랫폼·언어 설정 변경 시 |
| 2 | 페르소나, 캐릭터 정체성, 행동·말투 규칙, 출력 형식, 체크 규칙 | 고정 `user` 메시지들. 현재 역할을 유지한다. | 해당 설정이나 파일 변경 시 |
| 3 | 전체 메시지·관찰 사건. 이번에 받은 입력도 포함한다. | 원래 발언의 `user` / `assistant` 역할과 사건 순서 유지 | 새 사건을 끝에 추가 |
| 4 | `fact` 자리 | 향후 별도 컨텍스트 데이터. 지금은 주석만 존재 | 미구현 |
| 5 | `episode` 자리 | 향후 별도 컨텍스트 데이터. 지금은 주석만 존재 | 미구현 |
| 6 | 현재 요청 정보: 현재 시각, 시간대, 응답 대상 메시지 번호 | 마지막 `user` 메시지에 구조화한 데이터 | 요청마다 교체 |

도구 정의는 위 메시지 사이에 문자열로 끼워 넣지 않고 API의 `tools`로 전달한다. 같은 설정에서는 도구 목록·순서·스키마를 유지한다. 도구 설명 축소나 중복 도구 통합은 별도 작업이다. 실제 모델 입력에서 도구가 배치되는 위치는 공급자 구현에 따르므로, 이 표가 도구까지 포함한 내부 직렬화 순서를 보장하지는 않는다.

### 최신 입력과 현재 시각의 위치

| 배치안 | 장점 | 비용 |
| --- | --- | --- |
| 과거 기록 → 현재 시각·기억 → 최신 사용자 입력 | 실제 사용자 입력이 마지막에 온다. | 다음 요청에서 최신 입력을 과거 기록 쪽으로 옮기게 된다. 기존 요청에서 현재 시각 뒤에 있던 입력까지 동일한 앞부분으로 이어 붙이기 어렵다. |
| 전체 기록에 최신 입력까지 포함 → 기억 자리 → 현재 요청 정보 | 한 번 포함한 발언의 위치와 형태를 유지한다. 현재 시각이 기존 기록을 가로막지 않는다. | 마지막 `user` 메시지가 실제 발언이 아닌 요청 메타데이터이므로 두 종류를 명확히 구분해야 한다. |

두 번째 안을 채택한다. 마지막 메시지는 `type: "request_context"`로 구분하고, 실제 사용자 발언을 다시 복사하지 않는다. 자연어로 이 데이터를 해석하게 하는 안내 문구는 프롬프트 재작성 작업에서 다룬다.

## 고정 구간의 구성

현재 파일을 기준으로 아래 순서를 제안한다. 파일의 지시 문구를 새로 작성하거나 역할 우선순위를 바꾸는 것은 이번 안에 포함하지 않는다.

1. `system.md` → `systemInstruction`.
2. `persona-frame.md` → 페르소나.
3. `state.md`의 캐릭터 정체성 부분 → 현재 시각을 분리한 정체성.
4. `behavior-core.md` → 행동 규칙.
5. `messenger-style.md` → 말투 규칙.
6. `response-contract.md` → 출력 형식. 대화 뒤에서 이 위치로 이동한다.
7. `final-check.md` → 체크 규칙. 대화 뒤에서 이 위치로 이동한다.

마지막 두 파일도 현재 내용으로는 고정 지시이므로 고정 구간에 둔다. 위치 변경이 응답 형식 준수에 미치는 영향은 구현 후 모델 응답으로 확인한다. 별도 자연어 개편 시 중복 제거와 이름 변경을 검토하되, 여기서는 새 체크 문구를 만들지 않는다.

`memory.md`는 현재 기억 계층 설명과 `<Foundation>`, `<Deep_Memory>`, `<Recent>` 같은 데이터 경계를 함께 담고 있다. 이 파일 전체를 그대로 끼워 넣으면 새 배치와 충돌한다. 제안 구조에서는 이 묶음을 그대로 주입하지 않으며, 필요한 설명의 재배치는 별도 자연어 작업으로 남긴다. 빈 기억 블록이나 존재하지 않는 기능의 안내를 모델 입력에 보내지 않는다.

캐릭터 컨텍스트와 렌더링 기준 시각은 요청당 한 번 구성해 공유한다. 태그 하나나 고정 텍스트를 렌더링할 때마다 캐릭터 파일을 다시 읽고 시각을 새로 만들지 않는다. 날짜로 계산되는 나이·학년 같은 값은 정체성에서 실제 값이 바뀔 때만 고정 구간이 달라지는 것으로 취급한다.

## 전체 기록은 하나의 누적 구간으로 유지

`Recent`, `This_Moment`, `User_Action`처럼 매 요청 경계가 이동하는 구간으로 나누지 않는다. 조회 단계의 개수 제한과 시퀀스의 `slice`를 모두 없애는 것을 전제로 한다. 시퀀스만 바꾸고 저장소에서 이미 잘린 기록을 받는 것은 전체 포함이 아니다.

현재 `historyMessages`와 `pendingMessages`를 내부 처리용으로 유지할 수는 있다. 다만 모델에 전달할 때는 사건 ID로 중복을 제거하고 관찰 순서대로 합친 한 구간으로 만든다. 같은 본문이나 같은 메시지 번호라는 이유로 사건을 합치지 않는다. 하나의 메시지에 대한 발언·수정·삭제는 서로 다른 사건이다.

- 일반 발언은 본래의 `user` / `assistant` 역할을 유지한다.
- 수정·삭제와 과거 내역을 읽은 표시는 관찰 데이터로 전달한다. 봇이 직접 말한 새 발언이나 시스템 명령으로 만들지 않는다.
- 원래 발언을 최신 내용으로 덮어쓰지 않고, 목격한 수정·삭제를 뒤에 추가한다.
- 뒤늦게 읽은 과거 메시지는 그 관찰 위치에 추가한다. 발송 시각이나 메시지 번호로 기존 기록 중간에 재삽입하지 않는다.
- 이번 응답의 대상은 기존 `inputEventIds`로 내부에서 식별한다. 모델에는 마지막 요청 정보의 `inputMessageNos`로 해당 메시지를 가리킨다. 이 목록은 사건 커서의 대체물이 아니며, 같은 메시지에 발생한 여러 변화는 전체 사건 기록에서 확인한다.
- 이전 요청의 현재 시각·요청 정보 블록은 다음 요청의 대화 기록에 넣지 않는다. 실제 발언과 관찰 사건만 누적한다.

```text
요청 A
고정 구간 → 사건 1 → 사건 2 → 사건 3 → 현재 요청 정보 A

요청 B
고정 구간 → 사건 1 → 사건 2 → 사건 3 → 실제 전송된 AI 응답 → 사건 4 → 현재 요청 정보 B
           └──────── 그대로 유지되는 앞부분 ────────┘
```

캐시 대상으로 유지하려는 부분은 고정 구간과 이미 포함한 사건들이다. 이전 요청 전체나 모델이 생성한 출력까지 그대로 재사용된다고 가정하지 않는다. 생성 원문이 여러 플랫폼 메시지로 나뉘어 저장되는 경우에도, 한 번 기록된 출력 사건은 이후 동일한 형식으로 렌더링한다.

## 시간 정보의 위치와 형식

현재 시각과 과거 사건의 시각은 분리한다.

| 정보 | 위치 | 형식과 갱신 |
| --- | --- | --- |
| 이번 생성의 기준 시각 | 마지막 `request_context.currentTime` | 준비 시작 시 한 번 잡은 절대 시각. 초 단위 ISO 8601과 실제 시간대 오프셋 사용 |
| 기준 시간대 | 마지막 `request_context.timezone` | `app.timezone`, 예: `Asia/Seoul` |
| 메시지·사건을 관찰한 시각 | 해당 기록의 메타데이터 | 저장된 `observedAt`을 절대 시각으로 표시. 다음 요청에서도 동일한 값 |
| 원래 메시지 발송 시각 | 해당 기록의 메타데이터, 필요한 경우 | 확인된 값이 있을 때만 별도로 표시. 관찰 시각과 혼동하지 않음 |
| 날짜에 따라 달라지는 캐릭터 상태 | 정체성 값 또는 향후 요청 정보 | 나이·학년처럼 실제 값이 바뀌는 경우만 갱신. 현재 시각 문자열을 정체성에 섞지 않음 |

예를 들어 현재 시각은 `2026-09-24T22:40:00+09:00`처럼 표현한다. 밀리초는 제외한다. 오프셋을 무조건 `+09:00`으로 덧붙이지 않고 설정된 시간대로 변환한다. 초를 줄이는 것보다 위치를 맨 뒤로 옮기는 것이 우선이다.

과거 기록에는 `3분 전`, `어제`처럼 요청 때마다 달라지는 상대 시각을 넣지 않는다. 고정된 절대 시각을 사용하고, 현재 시각과의 차이는 모델이 해석하게 한다. 발송 시각이나 작성자를 알 수 없는 사건은 값을 추정해 채우지 않는다. 작성자 표시를 넣을 때도 같은 사건이 매번 다른 이름으로 렌더링되지 않도록 한다. 다인 채팅의 상세 표기 정책은 별도다.

`currentTime`은 해당 생성 요청의 기준 시각이다. 생성 도중 실제 현재 시각이 추가로 필요하면 시간 도구의 반환값을 사용한다. 도구 호출 단계마다 기존 컨텍스트 앞부분의 시각을 다시 렌더링하지 않는다.

## fact·episode 주입 자리

두 자리는 전체 기록 뒤, 현재 요청 정보 앞에 둔다. 향후 검색 결과나 기억 내용이 달라져도 고정 지시와 전체 기록의 앞부분을 바꾸지 않기 위해서다. `fact` → `episode` 순서는 배치 순서이며, 원문보다 우선하는 지시 계층을 의미하지 않는다.

아래는 제안 구조를 설명하는 독립적인 조립 예시다. 현재 `sequence.js`에 그대로 붙여 넣는 설정이 아니며, `staticMessages`, `eventMessages` 등은 위 규칙대로 준비됐다고 가정한다. 미구현 주입부는 JavaScript 주석이므로 모델에 전송되지 않는다.

```js
function composeContext({
  systemInstruction,
  staticMessages,
  eventMessages,
  currentTime,
  timezone,
  inputMessageNos,
}) {
  return {
    systemInstruction,
    context: [
      ...staticMessages,
      ...eventMessages,

      // TODO: fact 기능 구현 후 연결. 현재는 조회·주입하지 않는다.
      // {
      //   role: "user",
      //   content: JSON.stringify({ type: "facts", items: facts }),
      // },

      // TODO: episode 기능 구현 후 연결. 현재는 조회·주입하지 않는다.
      // {
      //   role: "user",
      //   content: JSON.stringify({ type: "episodes", items: episodes }),
      // },

      {
        role: "user",
        content: JSON.stringify({
          type: "request_context",
          currentTime,
          timezone,
          inputMessageNos,
        }),
      },
    ],
  };
}
```

`items` 내부 스키마와 조회 조건은 해당 기능을 설계할 때 정한다. 지금은 빈 배열이나 빈 태그조차 주입하지 않는다. 프롬프트 문자열 안에 HTML 주석으로 숨기는 방식도 사용하지 않는다. 문자열에 포함된 주석은 모델 입력 토큰이 되므로, 실행 코드에서 주입 자체를 비활성화한다.

## 캐시 관점의 확인 사항

현재 `cache-point`는 `SequenceBuilder`에서 아무 동작도 하지 않는다. 제안 순서에서는 이 마커를 캐시 보장의 근거로 사용하지 않는다. Grok의 자동 캐싱은 앞에서부터 동일한 입력을 재사용하는 방식이며, 실제 재사용은 응답의 `usage.inputTokenDetails.cacheReadTokens`로 확인한다. [xAI Prompt Caching](https://docs.x.ai/developers/advanced-api-usage/prompt-caching)

고정 구간과 사건의 문자열·역할·메시지 경계를 일정하게 유지한다. 앞선 여러 메시지를 매번 하나의 문자열로 다시 묶거나, 응답 완료에 따라 기존 메시지에 다른 구간 태그를 붙이지 않는다. 현재 시각·응답 대상 번호·향후 기억 검색 결과는 모두 마지막 가변 구간에만 둔다.

재생성으로 기존 출력이 제외되거나 설정·정체성이 실제로 바뀌는 경우에는 앞부분이 달라질 수 있다. 이때는 올바른 컨텍스트를 우선하며, 캐시를 위해 폐기된 출력을 남기거나 변경된 설정을 숨기지 않는다.

## 컨텍스트 조립 검증 기준

- 20개를 넘는 기록에서도 첫 사건부터 마지막 사건까지 누락 없이 포함된다. 조회 개수와 시퀀스 양쪽에 제한이 없어야 한다.
- 같은 사건 목록에서 현재 시각만 바꾸면 마지막 요청 정보만 달라진다.
- 새 입력이 오면 기존 사건의 본문·역할·순서·절대 시각은 유지되고 새 사건만 뒤에 추가된다.
- Pending이 처리 완료되어도 같은 사건의 렌더링이나 위치가 달라지지 않는다.
- 최신 사용자 발언은 전체 기록 안에 한 번만 존재하고, 마지막 요청 정보에는 번호만 들어간다.
- 수정·삭제는 해당 메시지 번호를 참조하며, 같은 메시지의 여러 사건을 중복으로 오인해 제거하지 않는다.
- `fact`·`episode`의 조회 호출, 실제 주입 메시지, 빈 블록은 모두 없다. 예시의 주석을 활성화하지 않는다.
- 현재 시각은 한 요청에서 한 번만 잡고, 과거 사건 시각은 상대 표현으로 재계산하지 않는다.
- 배치 변경 후 출력 형식 준수와 실제 캐시 재사용량을 각각 확인한다. 문자열이 안정됐다는 이유만으로 캐시 적중을 보장하지 않는다.

## 기존 메시지 번호 설계와의 관계

아래 번호 설계는 유지한다. 컨텍스트 제외·요약 사례는 향후 그런 처리가 생겨도 번호가 불변이어야 한다는 성질을 설명한다. 이번 배치안에 메시지 개수 제한이나 요약 기능을 도입하는 것은 아니다.

## 목적

AI가 특정 메시지를 정확히 가리킬 수 있도록 컨텍스트에 고정 번호를 표시한다. 같은 문구가 여러 번 등장해도 수정·삭제의 대상, 답장 대상, 리액션 대상을 구분할 수 있어야 한다.

```text
#1 사용자: 안녕?
#2 AI: 반가워!
#3 사용자: 사랑해
[#3의 내용이 삭제되었습니다.]
```

번호를 표시하지 않고 본문이나 상대적 위치로 대상을 선택하는 방법도 가능하지만, 동일 문구의 반복이나 새 메시지 유입으로 대상이 모호해질 수 있다. 앞으로 답장과 리액션 도구에서도 같은 참조 방식을 사용한다.

## 채널별 고정 번호

기존 전역 `Message.id`는 유지하고, AI에게 표시할 채널별 메시지 번호를 별도로 저장한다. 각 채널은 1부터 시작하며, 한 번 부여한 번호는 바꾸거나 재사용하지 않는다.

전역 ID를 그대로 표시해도 메시지 식별 기능에는 문제가 없다. 다만 다른 채널의 메시지 저장에 따라 번호가 크게 뛰고 숫자가 커진다. 채널 안에서 사용할 참조 번호는 채널별로 관리한다. 번호가 연속적이라는 이유만으로 모델의 이해도나 도구 선택 정확도가 향상된다고 가정하지는 않는다.

| 식별자 | 역할 |
| --- | --- |
| `Message.id` | DB 전체에서 메시지를 식별한다. 기존 사건·기억 등의 참조에 사용한다. |
| `Message.channelId` | 메시지가 속한 채널을 식별한다. |
| `Message.channelMessageNo` | 추가할 채널별 고정 번호다. 컨텍스트에서 `#3`처럼 표시한다. |
| `Message.platform` + `Message.platformId` | 실제 플랫폼 메시지를 식별하고 답장·리액션을 실행하는 데 사용한다. |
| `Event.id` | 메시지를 읽거나 수정·삭제를 목격한 개별 사건을 식별한다. 메시지 번호와 구분한다. |

`channelId`와 `channelMessageNo`의 조합은 유일해야 한다. 서로 다른 채널에 같은 번호가 존재하는 것은 정상이다.

| 기존 DB ID | 채널 | 채널별 번호 | 내용 | 상태 |
| --- | --- | --- | --- | --- |
| 100 | A | 1 | 안녕 | 유지 |
| 101 | B | 1 | 안녕하세요 | 유지 |
| 105 | A | 2 | 반가워 | 삭제됨 |
| 182 | A | 3 | 뭐 해? | 유지 |

```text
A 채널의 #3 → DB 메시지 182 → 해당 플랫폼 메시지
B 채널의 #1 → DB 메시지 101 → 해당 플랫폼 메시지
```

## 번호 부여와 저장

번호는 메시지를 처음 저장할 때 한 번 부여하고 `Message`에 영속 저장한다. 채널별 마지막 발급 번호도 영속 저장한다. 마지막 발급 번호의 구체적인 저장 위치는 구현 시 정한다.

1. 플랫폼 식별자로 이미 저장된 메시지인지 확인한다. 같은 메시지의 재수신이면 기존 번호를 사용한다.
2. 새 메시지라면 해당 채널의 마지막 발급 번호 다음 값을 할당한다.
3. 메시지 저장과 채널의 마지막 발급 번호 갱신을 같은 트랜잭션에서 처리한다.
4. 동시 저장에서도 번호가 중복되지 않도록 발급을 직렬화하거나 원자적으로 갱신하고, DB의 조합 고유 제약으로 중복을 막는다.

```text
A 채널의 마지막 발급 번호: 3
→ 새 메시지에 4 부여
→ Message.channelMessageNo = 4로 저장
→ A 채널의 마지막 발급 번호를 4로 갱신
```

조회 시에는 저장된 번호를 읽는다. 채널별 메시지를 매번 시간순으로 나열해 순번을 다시 계산하지 않는다. 현재 조회 결과의 개수나 배열 인덱스도 번호로 사용하지 않는다.

번호의 유일성과 불변성이 중요하다. 삭제, 컨텍스트 제한 등의 이유로 표시되는 번호 사이에 빈틈이 있어도 괜찮다. AI가 보지 않은 메시지에 번호가 있다는 이유로 그 내용을 컨텍스트에 노출하지 않는다.

## 번호가 유지되는 경우

| 상황 | 처리 |
| --- | --- |
| 메시지 수정 | 같은 메시지 번호를 유지한다. |
| 메시지 삭제 | 삭제된 메시지의 번호를 유지하고 재사용하지 않는다. |
| 같은 플랫폼 메시지 재수신 | 기존 번호를 사용한다. |
| 봇 재시작·날짜 변경 | 마지막 발급 번호 이후부터 계속한다. |
| 오래된 컨텍스트 제외·요약 | 남은 메시지의 번호를 바꾸지 않는다. |
| 기존 메시지를 과거 내역에서 다시 읽음 | 기존 번호를 사용한다. 새 관찰 사건과 구분한다. |
| 처음 발견한 과거 메시지 저장 | 다음 번호를 새로 부여한다. 기존 번호는 변경하지 않는다. |
| 새 플랫폼 메시지로 AI 답변 재생성 | 새 메시지 번호를 부여한다. 교체된 출력의 번호는 재사용하지 않는다. |

사용자와 AI 메시지는 같은 채널 번호 체계를 공유한다. AI 응답이 실제 플랫폼 메시지 여러 개로 나뉘어 전송되면 각각 별도 번호를 부여한다. 답장·리액션의 대상이 되는 단위가 개별 플랫폼 메시지이기 때문이다.

번호는 시스템이 저장된 메시지에 부여한다. 모델이 생성 중인 자신의 메시지 번호를 임의로 정하거나 다음 번호를 예측하게 하지 않는다.

## 시간순 정렬과 번호의 관계

번호는 해당 메시지의 고정 참조값이며, 채널의 실제 역사에서 몇 번째로 발송된 메시지인지까지 뜻하지 않는다. 메시지 번호 부여와 컨텍스트의 사건 정렬은 별도로 처리한다. 기존 관찰 사건의 순서를 번호순으로 재정렬하지 않는다.

Soft delete는 삭제에 따른 순번 변경을 막는 데 도움이 되지만, 매번 시간순 순위를 계산해도 번호가 유지된다는 보장은 하지 않는다. 나중에 가져온 과거 메시지를 발송 시각 기준으로 중간에 넣으면 순위가 바뀔 수 있다.

```text
매번 순번을 계산하는 경우:
기존       #1 안녕 → #2 반가워
과거 추가  #1 안녕 → #2 누락됐던 발언 → #3 반가워
```

이 경우 기존 참조 `#2`의 의미가 바뀐다. 고정 번호 방식에서는 `반가워`의 번호를 유지하고, 새로 발견한 메시지에 다음 번호를 부여한다.

컨텍스트를 최근 일부로 제한하더라도 다시 1부터 매기지 않는다.

```text
전체 기록:  #1, #2, #3, #4
일부 제외:          #3, #4
```

## 수정·삭제 사건의 표시

번호는 메시지에 붙이고, 수정·삭제 사건은 대상 메시지 번호를 참조한다. 수정·삭제 알림 자체가 새 메시지 번호를 소비하지 않는다.

```text
#1 사용자: 안녕?
#2 AI: 반가워!
#3 사용자: 사랑해

[#3 수정: "사랑해" → "좋아해"]
[#3 삭제됨]

#4 사용자: 못 본 걸로 해줘.
```

내부적으로는 각 수정·삭제 사건에 별도 `Event.id`가 존재한다. 개별 사건을 도구 대상으로 지정할 필요가 없다면 사건 ID까지 컨텍스트에 표시할 필요는 없다.

위 예시는 참조 형식을 설명하기 위한 것이다. 실제로 AI가 목격한 수정·삭제만 기존 관찰 정책에 따라 전달한다. 번호 도입으로 원문 보존 정책을 변경하거나, 삭제 실행자와 이유를 추정하지 않는다.

`[#3 삭제됨]`이라는 참조만으로 AI가 원문을 알 수 있는 것은 아니다. 원문이 컨텍스트에서 제외된 경우, 내용을 알아야 하는 작업에는 관찰한 원문이나 필요한 발췌를 함께 제공하거나 별도로 조회할 수 있어야 한다. 보지 못한 원문을 복원한 것처럼 제시하지 않는다.

## 답장·리액션 도구와 연결

모델은 현재 채널에서 대상 메시지 번호를 선택한다. 채널은 모델이 임의로 지정하는 값이 아니라 현재 요청의 실행 컨텍스트에서 가져온다.

```text
현재 요청의 채널 + 대상 메시지 번호
→ 저장된 Message 조회
→ 플랫폼 메시지 식별자와 현재 상태 확인
→ 플랫폼에 답장 또는 리액션 실행
→ 모델에 성공·실패 결과 반환
```

다음은 도구 호출 형식의 예시다.

```js
reply({
  targetMessageNo: 3,
  text: "여기 너가 이렇게 말했잖아.",
});

react({
  targetMessageNo: 11,
  emoji: "😴",
});
```

같은 번호가 다른 채널에 있어도 현재 채널과 함께 조회하므로 충돌하지 않는다. 대상이 없거나 실행 전에 삭제되어 작업할 수 없다면 실패를 반환한다. 다른 메시지로 대체하거나 다른 채널에서 같은 번호를 찾아 실행하지 않는다. 재시도·재생성 과정에서는 같은 답장이 중복 전송되지 않도록 실행 결과를 관리해야 한다.

컨텍스트의 번호 표시와 실제 사용자에게 보이는 채팅 표시는 별도다. AI는 `#3`을 선택하되, 사용자에게는 플랫폼의 답장 UI와 답변 본문만 보여줄 수 있다.

채널 밖으로 참조를 옮기는 요약·기억에는 번호만 단독으로 보관하지 않는다. DB 메시지 ID 또는 채널과 번호의 조합으로 원래 대상을 식별할 수 있어야 한다.

## 기존 데이터 적용

기존 메시지는 채널별로 정렬해 최초 한 번 번호를 부여하고 저장한다. Soft delete된 메시지도 포함해 수정·삭제 사건의 참조 대상을 유지한다. 초기 정렬 기준과 동일 시각의 순서 기준은 구현 시 확정한다.

초기 번호 부여 후 채널별 마지막 발급 번호를 설정하고, 이후 새 메시지에는 다음 번호만 발급한다. 과거 메시지 추가, 조회 조건 변경, 재시작을 이유로 기존 번호를 다시 계산하지 않는다.

기존 `Message.id`와 이를 참조하는 사건·기억의 관계는 유지한다. 현재 수정·삭제 표기에 쓰는 전역 메시지 ID와 새 채널별 번호가 같은 `#숫자` 형식으로 혼용되지 않도록 컨텍스트 렌더링과 도구의 번호 해석을 함께 맞춘다. 기존 생성 입력·재생 기록의 참조 방식도 적용 시 확인한다.

## 구현 시 확인할 사례

- A 채널과 B 채널이 각각 `#1`부터 시작하고, 도구가 현재 채널의 메시지만 선택한다.
- 사용자와 AI 메시지가 같은 번호 체계를 사용하며, 분할 전송된 AI 메시지는 각각 식별된다.
- 동시 수신과 동일 플랫폼 메시지 재수신에서도 번호가 중복 발급되지 않는다.
- 수정·삭제, 봇 재시작, 컨텍스트 축소 이후에도 기존 번호가 유지된다.
- 과거 메시지를 뒤늦게 추가해도 기존 답장·삭제 참조가 다른 메시지를 가리키지 않는다.
- 도구 실행 전에 대상이 삭제되면 실패가 반환되고, 재시도로 답장이 중복 전송되지 않는다.
- 기존 데이터의 초기 번호 부여 후에도 사건·기억과 생성 입력의 참조가 올바른 메시지로 연결된다.

관련 기존 설계: [메시지 사건과 대화 주시](message-observation-design.md). 현재 데이터 구조: [Prisma 스키마](../prisma/schema.prisma).
