# 컨텍스트 구성 개편

이 문서는 모델에 전달할 컨텍스트의 최종 배치 순서와 시간 정보의 위치를 정한다. 자연어 프롬프트의 문구 재작성은 별도 작업으로 둔다. 아래 조립 코드는 설계 예시이며, 구현 완료를 의미하지 않는다.

## 범위와 전제

- 현재 캐릭터·채널에서 컨텍스트에 포함할 수 있는 메시지와 관찰 사건은 개수 제한 없이 전부 포함한다. 최근 N개 선택, 날짜 기준 절단, 요약으로 원문을 대체하는 방식은 이번 안에 넣지 않는다.
- 전체 포함은 기존 관찰·가시성 정책 안에서의 전체를 뜻한다. 다른 채널의 기록, 목격하지 않은 수정 원문, 재생성으로 폐기된 출력까지 노출한다는 뜻은 아니다. 플랫폼에서 과거 메시지를 새로 수집하는 범위도 별도다.
- `summary`, `fact`, `episode`는 아직 존재하지 않는 기능이다. 세 자리의 위치만 예약하고, 주입 코드는 주석 처리한다. 실제 요약·기억의 조회·추출·저장·검색이나 가짜 데이터 주입은 추가하지 않는다.
- 현재의 `MemoryService`와 `userMemories`를 새 `fact`·`episode` 기능으로 간주하지 않는다. 제안하는 조립 경로에서는 기존의 맨 앞 기억 주입을 사용하지 않으며, 기존 기억 데이터의 이전은 별도 작업이다.
- 이 문서를 기준으로 기본 `ultimate` 채팅 프롬프트와 컨텍스트 조립 경로를 구현한다. 프롬프트의 배치와 시간 분리만 변경하며 자연어 지시 재작성, DB와 스키마 변경은 포함하지 않는다. 모델 입력 한도를 넘는 경우의 처리는 별도 설계 대상으로 남긴다.
- 무제한 히스토리는 이 개편의 확정 요구사항이다. 구현 완료 후에는 실사용 규모에 대응해야 하지만, `main`에 정식 병합할지와 그 시점은 별도로 판단한다.

## 최종 순서

핵심은 고정 내용과 이전까지의 누적 기록을 먼저 두고, 이번 요청의 응답 지시와 마지막 봇 발언 이후의 관찰을 맨 뒤에 두는 것이다.

| 순서 | 내용 | 전달 형태 | 변경 기준 |
| --- | --- | --- | --- |
| 1 | 시스템 지시 | API의 `system` | 프롬프트·플랫폼·언어 설정 변경 시 |
| 2 | 페르소나·정체성·행동 규칙 등 고정 지시 | 고정 `user` 메시지들. 현재 역할을 유지한다. | 해당 설정이나 파일 변경 시 |
| 3 | `summary` 자리 | 향후 요약 데이터. 지금은 주석만 존재하며 아무것도 주입하지 않음 | 미구현 |
| 4 | 마지막 봇 전송 사건까지의 전체 메시지·관찰 사건 | 원래 발언의 `user` / `assistant` 역할과 사건 순서 유지 | 새 사건을 끝에 추가 |
| 5 | `fact` 자리 | 향후 별도 컨텍스트 데이터. 지금은 주석만 존재 | 미구현 |
| 6 | `episode` 자리 | 향후 별도 컨텍스트 데이터. 지금은 주석만 존재 | 미구현 |
| 7 | 메시지 포맷 규칙, 초 단위 현재 시각, 응답 지시 | 요청별 `user` 메시지 | 요청마다 교체 |
| 8 | 마지막 봇 발언 이후 관찰 | 이후의 모든 관찰 사건. 사건별 역할과 메시지 경계 유지 | 관찰 사건 누적·봇 전송 시 경계 갱신 |

도구 정의는 위 메시지 사이에 문자열로 끼워 넣지 않고 API의 `tools`로 전달한다. 같은 설정에서는 도구 목록·순서·스키마를 유지한다. 도구 설명 축소나 중복 도구 통합은 별도 작업이다. 실제 모델 입력에서 도구가 배치되는 위치는 공급자 구현에 따르므로, 이 표가 도구까지 포함한 내부 직렬화 순서를 보장하지는 않는다.

### 마지막 봇 발언 이후 관찰과 현재 시각의 위치

8번은 현재 캐릭터가 현재 채널에 마지막으로 전송한 메시지 이후의 모든 관찰 사건이다. 사용자 발언 여러 개, 수정·삭제, 뒤늦게 읽은 과거 내역을 모두 포함한다. 7번의 응답 지시 직후 이 사건들을 배치하며, 사건 본문을 요청 메타데이터 안에 복사하지 않는다.

경계는 기존 가시성 정책을 적용한 사건 중 마지막 봇 전송 사건(`SENT`)의 ID로 정한다. 발송 시각이나 처리 완료 커서로 경계를 정하지 않는다. 4번은 그 사건까지, 8번은 그 이후이며, 각 사건은 두 구간 중 한 곳에만 존재한다.

- 봇이 아직 전송한 적 없으면 전체 관찰 기록을 8번에 둔다.
- 마지막 봇 전송 이후 관찰이 없으면 8번을 생략한다.
- 여러 조각으로 전송한 응답은 실제 전송된 마지막 조각의 사건을 경계로 삼는다. 생성 완료를 기다리지 않는다.
- 재생성에서는 폐기된 출력을 제외한 뒤 경계를 계산한다.
- 과거 봇 메시지를 뒤늦게 읽은 `READ/HISTORY` 사건은 새 봇 전송이 아니므로 경계를 옮기지 않는다.
- 입력 처리·완료 커서는 기존 의미를 유지한다. 8번의 사건 목록과 처리해야 할 입력 목록이 같다고 가정하지 않는다.

다음 봇 전송 후에는 이전 8번의 관찰과 실제 전송된 AI 응답이 사건 순서대로 4번에 들어간다. 이동해도 사건의 본문·역할·메시지 경계·절대 시각은 동일하게 유지한다. 7번의 요청별 정보는 누적 기록에 넣지 않는다.

## 고정 구간의 구성

현재 파일을 기준으로 아래 구성을 제안한다. 파일의 지시 문구를 새로 작성하거나 역할 우선순위를 바꾸는 것은 이번 안에 포함하지 않는다.

1. `system.md` → `systemInstruction`.
2. `persona-frame.md` → 페르소나.
3. `state.md`의 캐릭터 정체성 부분 → 현재 시각을 분리한 정체성.
4. `behavior-core.md` → 행동 규칙.
5. `messenger-style.md` → 말투 규칙.
6. `response-contract.md` → 7번의 메시지 포맷 규칙과 응답 지시.
7. `final-check.md` → 필요하면 7번의 응답 지시에 포함할 체크 규칙.

앞의 네 캐릭터 파일은 2번 고정 지시에 둔다. `response-contract.md`와 `final-check.md`의 관련 내용은 현재 시각과 함께 7번에 배치한다. 별도 자연어 개편 시 중복 제거와 이름 변경을 검토하되, 여기서는 새 체크 문구를 만들지 않는다.

`memory.md`는 현재 기억 계층 설명과 `<Foundation>`, `<Deep_Memory>`, `<Recent>` 같은 데이터 경계를 함께 담고 있다. 이 파일 전체를 그대로 끼워 넣으면 새 배치와 충돌한다. 제안 구조에서는 이 묶음을 그대로 주입하지 않으며, 필요한 설명의 재배치는 별도 자연어 작업으로 남긴다. 빈 기억 블록이나 존재하지 않는 기능의 안내를 모델 입력에 보내지 않는다.

캐릭터 컨텍스트와 렌더링 기준 시각은 요청당 한 번 구성해 공유한다. 태그 하나나 고정 텍스트를 렌더링할 때마다 캐릭터 파일을 다시 읽고 시각을 새로 만들지 않는다. 날짜로 계산되는 나이·학년 같은 값은 정체성에서 실제 값이 바뀔 때만 고정 구간이 달라지는 것으로 취급한다.

## 전체 기록의 순서와 렌더링 유지

`Recent`, `This_Moment`, `User_Action` 태그를 사건에 붙이지 않는다. 전체 기록을 마지막 봇 전송 기준으로 4번과 8번에 배치하되, 두 구간은 동일한 렌더링을 사용한다. 기본 조립 경로의 조회 개수 제한과 시퀀스의 `slice`를 모두 없애는 것을 전제로 한다. 시퀀스만 바꾸고 저장소에서 이미 잘린 기록을 받는 것은 전체 포함이 아니다.

현재 `historyMessages`와 `pendingMessages`를 내부 처리용으로 유지할 수는 있다. 다만 모델에 전달할 때는 사건 ID로 중복을 제거하고 관찰 순서대로 합친 뒤 마지막 봇 전송 경계로 나눈다. 같은 본문이라는 이유로 사건을 합치지 않는다. 하나의 메시지에 대한 발언·수정·삭제는 서로 다른 사건이다.

- 일반 발언은 본래의 `user` / `assistant` 역할을 유지한다.
- 수정·삭제와 과거 내역을 읽은 표시는 관찰 데이터로 전달한다. 봇이 직접 말한 새 발언이나 시스템 명령으로 만들지 않는다.
- `channelMessageNo` 도입 전에는 수정·삭제·과거 내역 안내에 DB ID나 플랫폼 ID를 `#번호`로 표시하지 않는다. `[수정 목격]`, `[삭제 목격]`과 관찰한 원문을 전달하며, 내부 메시지 참조는 유지한다.
- 원래 발언을 최신 내용으로 덮어쓰지 않고, 목격한 수정·삭제를 뒤에 추가한다.
- 뒤늦게 읽은 과거 메시지는 그 관찰 위치에 추가한다. 발송 시각으로 기존 기록 중간에 재삽입하지 않는다.
- 마지막 봇 전송 이후의 모든 관찰 사건은 4번에서 제외하고 8번에 둔다.
- 이전 요청의 포맷 규칙·현재 시각·응답 지시는 다음 요청의 대화 기록에 넣지 않는다. 실제 발언과 관찰 사건만 누적한다.

```text
요청 A
시스템·고정 지시 → summary 자리 → 사건 1 → 사건 2 → fact 자리 → episode 자리
→ 포맷·시각·응답 지시 A → 이후 관찰 A (발언·수정·삭제·과거 읽기)

요청 B
시스템·고정 지시 → summary 자리 → 사건 1 → 사건 2 → 이후 관찰 A → 실제 전송된 AI 응답
→ fact 자리 → episode 자리 → 포맷·시각·응답 지시 B → 이후 관찰 B
                        └──── 새로 누적된 4번 기록 ────┘
```

캐시 대상으로 유지하려는 부분은 1~4번이다. 이전 요청의 5~8번까지 그대로 재사용된다고 가정하지 않는다. 생성 원문이 여러 플랫폼 메시지로 나뉘어 저장되는 경우에도, 한 번 4번 기록에 들어간 출력 사건은 이후 동일한 형식으로 렌더링한다.

## 시간 정보의 위치와 형식

현재 시각과 과거 사건의 시각은 분리한다.

| 정보 | 위치 | 형식과 갱신 |
| --- | --- | --- |
| 이번 생성의 기준 시각 | 7번 응답 지시 | 준비 시작 시 한 번 잡은 절대 시각. 초 단위 ISO 8601과 실제 시간대 오프셋 사용 |
| 기준 시간대 | 7번 응답 지시의 현재 시각 | `app.timezone`으로 변환한 오프셋에 반영 |
| 메시지·사건을 관찰한 시각 | 대화 시작과 5분 이상 공백 뒤 해당 기록 앞 | 저장된 `observedAt`을 `app.timezone`과 `app.language`에 맞춰 `[2026년 9월 29일 화요일 오전 9:00]`처럼 표시. 같은 설정에서는 다음 요청에서도 동일한 값 |
| 원래 메시지 발송 시각 | 해당 기록의 메타데이터, 필요한 경우 | 확인된 값이 있을 때만 별도로 표시. 관찰 시각과 혼동하지 않음 |
| 날짜에 따라 달라지는 캐릭터 상태 | 정체성 값 또는 7번 응답 지시 | 나이·학년처럼 실제 값이 바뀌는 경우만 갱신. 현재 시각 문자열을 정체성에 섞지 않음 |

예를 들어 현재 시각은 `2026-09-24T22:40:00+09:00`처럼 표현한다. 밀리초는 제외한다. 오프셋을 무조건 `+09:00`으로 덧붙이지 않고 설정된 시간대로 변환한다. 초를 줄이는 것보다 위치를 맨 뒤로 옮기는 것이 우선이다.

과거 기록에는 `3분 전`, `어제`처럼 요청 때마다 달라지는 상대 시각을 넣지 않는다. 고정된 절대 시각을 사용하고, 현재 시각과의 차이는 모델이 해석하게 한다. 발송 시각이나 작성자를 알 수 없는 사건은 값을 추정해 채우지 않는다. 작성자 표시를 넣을 때도 같은 사건이 매번 다른 이름으로 렌더링되지 않도록 한다. 다인 채팅의 상세 표기 정책은 별도다.

모든 사건의 `observedAt`은 저장하되, 모델 입력에는 첫 사건과 직전 사건으로부터 5분 이상 지난 사건에만 시각을 붙인다. 직전 사건의 시각을 모르면 현재 사건의 알려진 시각을 표시한다. 일반 발언·수정·삭제·과거 읽기에 같은 규칙을 적용하며, 마지막 표시 시각이 아닌 직전 사건과 비교한다. `history`와 `pending`을 이어서 판단하므로 응답 지시나 전송 경계 이동 때문에 기존 표시가 바뀌지 않는다. 연속된 사건 사이의 정확한 초 단위 간격은 모델 입력에서 생략된다.

관찰 시각 표시는 설정된 시간대의 날짜·요일·오전/오후와 분까지만 포함한다. `app.language`가 없으면 `ko-KR`로 표시한다. 시간 간격은 초·밀리초를 포함한 원래 시각으로 계산하므로 분 단위 표시나 서머타임 전환 때문에 간격이 달라지지 않는다. 예를 들어 `2026-09-29T00:00:00Z`는 `Asia/Seoul`에서 `2026년 9월 29일 화요일 오전 9:00`, `America/New_York`에서 `2026년 9월 28일 월요일 오후 8:00`으로 표시된다.

`currentTime`은 해당 생성 요청의 기준 시각이다. 생성 도중 실제 현재 시각이 추가로 필요하면 시간 도구의 반환값을 사용한다. 도구 호출 단계마다 기존 컨텍스트 앞부분의 시각을 다시 렌더링하지 않는다.

## summary·fact·episode 주입 자리

`summary`는 고정 지시 뒤와 전체 기록 앞에, `fact`와 `episode`는 전체 기록 뒤와 7번 응답 지시 앞에 둔다. 세 기능 모두 현재는 미구현 스텁이며 실제 데이터를 주입하지 않는다. `summary` → `fact` → `episode`는 배치 순서이며, 원문보다 우선하는 지시 계층을 의미하지 않는다.

`summary`가 나중에 실제 구현되어 자주 갱신되면 그 뒤의 4번 전체 기록까지 캐시가 깨진다. 현재는 주석으로만 자리를 예약하므로 이 문제가 발생하지 않는다. 구현 시에는 요약 갱신 주기와 캐시 손실을 함께 검토한다.

아래는 확정된 구조를 설명하는 독립적인 조립 예시다. 현재 `sequence.js`에 그대로 붙여 넣는 설정이 아니며, `fixedMessages`, `historyMessages`, `observationsSinceLastBotMessage` 등은 위 규칙대로 준비됐다고 가정한다. 미구현 주입부는 JavaScript 주석이므로 모델에 전송되지 않는다.

```js
function composeContext({
  systemInstruction,
  fixedMessages,
  historyMessages,
  messageFormatRules,
  currentTime,
  responseInstruction,
  observationsSinceLastBotMessage,
}) {
  return {
    systemInstruction,
    context: [
      ...fixedMessages,

      // TODO: summary 기능 구현 후 연결. 현재는 요약하거나 주입하지 않는다.
      // {
      //   role: "user",
      //   content: JSON.stringify({ type: "summary", content: summary }),
      // },

      ...historyMessages,

      // TODO: fact 기능 구현 후 연결. 현재는 조회·주입하지 않는다.
      // {
      //   role: "user",
      //   content: JSON.stringify({ type: "facts", items: facts }),
      // },

      // TODO: episode 기능 구현 후 연결. 현재는 조회·주입하지 않는다.
      // {
      //   role: "user",
      //   content: JSON.stringify({ type: "episodes", items: episodes }),
      // },

      {
        role: "user",
        content: renderResponseInstruction({
          messageFormatRules,
          currentTime,
          responseInstruction,
        }),
      },
      ...observationsSinceLastBotMessage,
    ],
  };
}
```

각 스텁의 내부 스키마와 조회 조건은 해당 기능을 설계할 때 정한다. 지금은 빈 배열이나 빈 태그조차 주입하지 않는다. 프롬프트 문자열 안에 HTML 주석으로 숨기는 방식도 사용하지 않는다. 문자열에 포함된 주석은 모델 입력 토큰이 되므로, 실행 코드에서 주입 자체를 비활성화한다.

## 캐시 관점의 확인 사항

현재 `cache-point`는 `SequenceBuilder`에서 아무 동작도 하지 않는다. 제안 순서에서는 이 마커를 캐시 보장의 근거로 사용하지 않는다. Grok의 자동 캐싱은 앞에서부터 동일한 입력을 재사용하는 방식이며, 실제 재사용은 응답의 `usage.inputTokenDetails.cacheReadTokens`로 확인한다. [xAI Prompt Caching](https://docs.x.ai/developers/advanced-api-usage/prompt-caching)

1~4번의 문자열·역할·메시지 경계를 일정하게 유지한다. 앞선 여러 메시지를 매번 하나의 문자열로 다시 묶거나, 응답 완료에 따라 기존 메시지에 다른 구간 태그를 붙이지 않는다. 5~8번은 요청마다 바뀌는 것이 정상이며, 이 가변 구간 때문에 앞의 캐시 가능 구간까지 다시 렌더링하지 않는다.

따라서 현재 캐시 재사용 가능 구간은 1~4번이다. `summary`가 미구현인 동안 3번은 실제 메시지를 만들지 않는다. 향후 `summary`를 주입하면 그 내용이 바뀔 때마다 뒤의 4번 캐시도 무효화될 수 있음을 감수하거나 별도 배치를 다시 검토해야 한다.

재생성으로 기존 출력이 제외되거나 설정·정체성이 실제로 바뀌는 경우에는 앞부분이 달라질 수 있다. 이때는 올바른 컨텍스트를 우선하며, 캐시를 위해 폐기된 출력을 남기거나 변경된 설정을 숨기지 않는다.

## 컨텍스트 조립 검증 기준

- 20개를 넘는 기록에서도 첫 사건부터 마지막 사건까지 누락 없이 포함된다. 조회 개수와 시퀀스 양쪽에 제한이 없어야 한다.
- 같은 전체 기록에서 현재 시각만 바꾸면 7번만 달라진다.
- 새 관찰은 8번 끝에 추가된다. 봇 전송 후에는 이전 관찰과 실제 AI 전송이 4번에 누적되며, 기존 사건의 본문·역할·순서·메시지 경계·절대 시각은 유지된다.
- 처리 완료 커서만 바뀌어도 같은 사건의 렌더링이나 위치가 달라지지 않는다. 4번·8번 경계는 마지막 봇 전송 사건으로만 결정한다.
- 마지막 봇 전송 이후의 모든 사건은 4번에 없고 8번에 한 번씩만 존재한다. 수정·삭제만 있는 요청, 봇 전송이 없는 첫 요청, 이후 관찰이 없는 요청도 검증한다.
- 부분 전송, 뒤늦은 과거 봇 메시지 읽기, 재생성으로 폐기된 출력 제외에서도 전송 사건 기준 경계를 유지한다.
- 같은 메시지의 여러 수정·삭제 사건을 중복으로 오인해 제거하지 않는다.
- `summary`·`fact`·`episode`의 조회 호출, 실제 주입 메시지, 빈 블록은 모두 없다. 예시의 주석을 활성화하지 않는다.
- 현재 시각은 한 요청에서 한 번만 잡고, 과거 사건 시각은 상대 표현으로 재계산하지 않는다.
- 관찰 시각은 첫 사건과 직전 사건 대비 5분 이상 공백 뒤에만 표시한다. 5분 미만의 연속 사건에서는 생략하며, 응답 경계 이동과 현재 시각 변경에도 표시 여부가 유지된다.
- 관찰 시각의 날짜·요일·오전/오후는 `app.timezone`과 `app.language`를 반영한다. 날짜 경계, 서머타임, 분 단위 오프셋에서도 올바르게 표시한다.
- 수정·삭제 안내는 번호 없이 관찰한 원문을 유지하며, 원문 자체의 `#번호` 문자열은 변경하지 않는다.
- 캐시 입력 비교에서 1~4번은 재사용 가능하고 5~8번의 변경은 정상으로 확인된다.
- 배치 변경 후 출력 형식 준수와 실제 캐시 재사용량을 각각 확인한다. 문자열이 안정됐다는 이유만으로 캐시 적중을 보장하지 않는다.
