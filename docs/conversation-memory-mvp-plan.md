# 대화·장기 기억 MVP 개발 계획

작성일: 2026-09-17. 수정일: 2026-09-18. 상태: 구현 전 설계안.

이 문서는 [기존 개발 계획](conversation-episode-development-report.md)과 [기존 TODO](conversation-episode-development-todo.md)를 대체하기 위한 새 설계다. 구현 시 이 문서의 범위와 순서를 사용한다. 이전 문서는 설계 이력으로 보존하며, 이전 문서에만 있는 기능을 완료 조건으로 가져오지 않는다.

목표는 최근 대화를 원문으로 이해하고 오래된 사실과 경험을 필요한 순간에 떠올리는 것이다. 경험의 철회·복원과 정밀한 출처 추적은 구현하지 않는다. 테이블 수만 줄이기보다 상태 전이, 모델 호출, 운영해야 할 기능을 줄인다.

## 1. 설계의 중심

원문 대화가 일정 토큰량에 도달하면 Review로 정리한다. Review는 대화의 주제와 흐름을 읽고 앞부분에서 Episode와 Fact를 만들며, 다음 응답에 원문이 필요한 끝부분은 Pending으로 남기는 손실 압축이다. 주제의 완전한 종료를 기다리거나 모든 발언을 기억으로 저장하지 않는다.

30분은 reroll의 허용 시간에만 사용한다. 봇의 직전 응답은 전송이 끝난 뒤 30분 동안만 재생성할 수 있고, 이 응답과 그 사용자 입력은 Review에서 보호한다. 나머지 대화는 30분이 지나지 않았어도 정리할 수 있다. 재생성 가능한 내용을 먼저 기억으로 만든 다음 취소하는 경로는 없다.

확정된 경험은 누적하고 현재 이해는 갱신한다. “그 일은 잊어줘”는 삭제 명령이 아니라 그 일을 꺼내지 말아 달라는 새 요청이다. “실제로는 서울에 살아”는 현재 사실의 정정이다. 관리자에 의한 직접 데이터 삭제는 대화 밖의 유지보수로 취급한다.

이번 대화에서 정한 정책과 이 문서에서 제안하는 축소 범위는 다음과 같다.

| 구분 | 내용 |
| --- | --- |
| 합의한 방향 | 토큰 임계치에서 Review, 연속된 앞 구간의 Episode·Fact 추출, 끝부분 하나를 Pending으로 보존, Evidence와 자동 철회 제거 |
| reroll 정책 | 전송 종료 후 30분 미만인 직전 응답만 허용, 응답과 해당 사용자 입력은 애플리케이션에서 보호 |
| 구현을 위한 기본값 | Review 임계치 N은 초기 4,000토큰 제안, 1분 간격 대상 확인. 모델 전체 입력 한도와는 별개 |
| 이번 설계의 축소 제안 | 핵심 기억·단어 검색부터 구현, 벡터 검색은 후속, 전송 전 별도 모델 검사와 자동 설정 재검사 제외 |
| 수용하는 한계 | 다른 채널에는 Review 완료 후 기억 공유, 짧은 대화는 장기간 원문으로만 남을 수 있음. 채널 간 즉시 일치와 의미 검색 품질은 보장하지 않음 |

## 2. 유지할 것과 걷어낼 것

| 유지 | 제거하거나 후속으로 미룰 것 |
| --- | --- |
| Message의 현재 상태와 Event의 관찰 이력 | FactEvidence, EpisodeEvidence, 근거 역할·누적·역조회 |
| 사용자와 봇이 함께 사용하는 Fact·Episode | Event 철회, 파생 기억 연쇄 무효화, 자동 복원·재추출 |
| 명시적 정정과 변화, 대화 방식에 관한 요청 | 기억 충돌 그래프, 신뢰도 점수, 과거 기억 버전 체계 |
| 같은 캐릭터의 장기 기억 공유 | 기억 저장용 scope/scopeKey 중복 필드와 스코프 승격 |
| 고정 입력, 원자적 저장, 중복 적용 방지 | 분산 worker, claim, 범용 작업·재처리 프레임워크 |
| 토큰 기준 Review와 제한된 재시도 | 시간 경과에 따른 강제 추출, idle/age/token 복합 조건 |
| 연속된 앞 구간과 Pending 끝부분 | Topic·Pending 테이블, 주제별 처리 상태, 별도의 주제 분할 호출 |
| 현재 설정을 우선하는 프롬프트 | 캐릭터별 CHAT 직렬화, 매 답변 별도 충돌 검사 호출 |
| 핵심 기억 조회와 단어 검색 | 임베딩·벡터DB·reranker·질의 확장 파이프라인 |
| 관리자 직접 유지보수 | 기억 삭제 콘솔, 연관 데이터 자동 삭제, 자동 재구축 |

실행은 현재처럼 단일 Node.js 프로세스와 SQLite를 전제로 한다. Repository가 DB를 접근하고 서비스가 흐름을 조정하는 기존 구조를 따른다. Fact와 Episode는 별도 테이블이지만 추출·검색을 위해 사용자용·봇용 시스템을 따로 만들지 않는다.

## 3. 원문, 사실, 경험의 역할

| 저장소 | 책임 |
| --- | --- |
| Message | 플랫폼 메시지의 현재 상태. 수정하면 갱신하고 일반 삭제 시 행을 제거한다. |
| Event | 수신한 발언과 수정·삭제 관찰. Message 삭제와 독립적으로 보존한다. |
| Fact | 현재 알고 있는 사실·취향·자기 설정·대화 선호. 정정되면 현재 값을 갱신한다. |
| Episode | 함께 겪은 일·결정·약속의 요약과 시점. 대화 전체를 하나의 요약으로 덮어쓰지 않는다. |
| Generation | CHAT과 MEMORY_REVIEW의 실행 기록. 기억의 근거 그래프 역할은 맡지 않는다. |

Event를 유지하는 이유는 “메시지를 삭제해도 이미 경험한 일은 사라지지 않는다”는 정책 때문이다. Message만 사용하면 삭제 전 발언과 수정 전 경험을 보존할 수 없다. Event를 통해 임의 시점의 DB 전체를 복원하는 이벤트 소싱 시스템까지 만들지는 않는다.

### 메시지 수정과 일반 삭제

- 현재 대화 대상으로 수신한 사용자 발언은 즉시 Event로 기록한다. 답변 전 수정·삭제도 경험에 포함한다.
- 수정은 새 Event다. 확인한 변경 내용과 이전 Event 참조를 남기며, 과거 Event 본문을 덮어쓰지 않는다.
- 삭제도 새 Event다. 일반 삭제는 기억 삭제나 약속 취소를 뜻하지 않는다.
- 이전 내용을 모르면 모르는 상태로 기록한다. 작성자·본문·삭제 의도를 추측하지 않는다.
- Message 변경과 Event 추가는 같은 트랜잭션으로 저장한다. 같은 플랫폼 메시지의 변경은 순서대로 적용한다.
- 중복 수신과 무변경 업데이트는 추가 기록하지 않는다. A→B→A 수정은 서로 다른 변화이며, 늦은 갱신으로 삭제한 Message를 되살리지 않는다.

봇 Event에는 실제 전송이 확인된 내용만 저장한다. Generation.output의 초안 전체를 경험으로 사용하지 않는다. 전송 후 저장 실패는 확인된 플랫폼 메시지 ID로 저장을 재시도하고, 확인 불가능한 부분은 오류로 남긴다. 플랫폼 전체 재동기화나 자동 전송 복구 시스템은 이번 범위가 아니다.

## 4. reroll: 아직 기억으로 만들지 않은 응답만 교체

### 가능 조건

아래 조건을 모두 만족해야 한다.

1. 요청한 메시지가 해당 캐릭터가 해당 채널에 실제 전달한 CHAT 응답의 일부다. 사용자 메시지나 IMAGE Generation 자체는 대상이 아니다.
2. 그 응답이 해당 캐릭터·채널의 가장 최근 전달 응답이다. 여러 조각으로 보냈다면 Generation 하나를 응답 하나로 취급한다.
3. 전송이 정상 완료됐고, 전송 종료 시각부터 30분 미만이다. 정확히 30분부터는 불가능하다.
4. 같은 채널에서 다른 CHAT 생성·전송 또는 reroll이 진행 중이지 않고, 대상은 이미 교체된 응답이 아니다.

새 응답이 전달되면 이전 응답은 30분이 남아 있어도 reroll 대상이 아니다. 최신 응답을 지웠거나 교체에 실패했다고 이전 응답을 다시 대상으로 삼지 않는다. 사용자가 후속 발언을 보냈다는 사실만으로는 대상이 바뀌지 않지만, 새 CHAT이 실행 중이면 reroll을 거부한다.

전송 종료 시각은 최초 Generation 생성 시각이나 갱신될 수 있는 updatedAt으로 대신하지 않는다. 정상 응답은 마지막 조각의 전송 확인 뒤 기록한다. 중단·실패한 전송의 확인된 조각은 일반 경험으로 남기되 MVP의 reroll 대상에서는 제외한다.

### 실행 순서

1. 애플리케이션에서 시간·최신 응답·실행 중 작업 여부를 다시 확인하고 대상 Generation에 `discardedAt`을 저장한다. 이 판정과 저장은 같은 채널의 CHAT 시작·출력 확정과 순서가 보장돼야 한다.
2. 해당 Generation이 실제 출력한 봇 Event와 그 메시지의 수정·삭제 관찰을 이후 컨텍스트·추출에서 제외한다. 기록 자체는 보존한다.
3. 플랫폼의 기존 출력 메시지를 정리하고 새 CHAT을 실행한다. 사용자 발언은 유지하며 교체 대상 응답에 사용한 사용자 입력도 다시 원문으로 제공한다.

`discardedAt`은 추출 전 출력 교체 여부만 나타낸다. Event별 RETRACTED 상태나 장기 기억의 무효화 처리는 만들지 않는다. 기존 Message.generationId에는 사용자 입력도 연결되므로 generationId 일치만으로 삭제·제외 대상을 정하지 않는다. 출력 작성자와 실제 전송 메시지 ID를 함께 확인한다.

준비 화면에서 허용됐어도 실행 시 30분이 지났으면 거부한다. DB에 교체 표시를 남기기 전에 플랫폼 메시지를 삭제하지 않는다. 플랫폼 삭제나 새 생성이 실패해도 예전 출력을 자동으로 복구하지 않고 실패를 알린다. 뒤따르는 삭제 이벤트는 일반 삭제처럼 새 답변을 예약하지 않는다.

원본 봇 출력을 제외해도 사용자가 별도로 작성한 반응이나 인용까지 지우지는 않는다. 인용을 독립적인 자기 진술로 확정하지 않는 추출 규칙은 유지하지만, 관련된 모든 흔적이 사라지는 완전한 시간 되감기는 제공하지 않는다.

## 5. 토큰 경계와 원문 컨텍스트

### Review를 시작하는 기준

현재 CHAT에 넣을 사용자·봇 원문 대화가 `N`토큰 이상이면 Review 대상이다. 작성 후 경과 시간으로 실행하지 않는다. 초기 N은 4,000토큰으로 제안하되 사용하는 모델의 입력 한도와 실제 대화량을 보고 정한다. N은 Review를 시작하는 임계치이며, 호출당 앞의 N토큰만 잘라 읽는 배치 크기가 아니다.

토큰은 해당 캐릭터·채널의 아직 정리하지 않은 원문 Event를 CHAT 표현으로 렌더링한 뒤 센다. 발언과 수정·삭제 관찰, 실제로 읽는 첨부 텍스트는 포함하고 identity·운영 지시·기존 Fact·Episode·도구 내부 로그는 제외한다. reroll로 교체한 출력은 세지 않는다. 토큰 계산은 CHAT 예산 계산과 같은 방식을 사용한다.

Review는 그 시점의 원문 전체를 고정된 스냅샷으로 읽는다. 이미 정리한 과거 원문이나 다른 채널의 원문까지 다시 불러오지 않는다. 기존 기억은 정정·중복 확인에 필요한 제한된 참고 자료로만 제공한다.

### 애플리케이션이 보호하는 끝부분

모델 호출 전에 아래 항목 중 가장 앞선 Event를 보호 시작점으로 정하고, 그 위치부터 끝까지 원문으로 남긴다.

- §4에 따라 아직 reroll 가능한 직전 봇 응답과 그 응답에 새로 들어온 사용자 입력.
- 생성·전송 중인 CHAT의 신규 사용자 입력과 이미 전송된 출력 조각.
- 아직 정상 응답을 받지 못한 사용자 입력.

진행 중인 CHAT 때문에 reroll 명령이 잠시 거부되더라도, 새 출력이 전달되기 전의 직전 응답 보호를 조기에 해제하지 않는다. 실패하면 다시 reroll 대상이 될 수 있기 때문이다. 전송된 출력은 응답 하나의 중간에서 경계를 자르지 않는다.

사용자 입력은 교체되지 않은 정상 완료 CHAT이 처리했을 때 답변된 것으로 본다. 실패·중단·reroll로 교체된 응답의 입력은 다시 미응답으로 남는다. 전체 CHAT 히스토리와 그 응답에 새로 들어온 사용자 입력 목록을 구분한다. 단순히 마지막 봇 Event가 있다는 이유로 입력을 처리 완료로 간주하지 않는다.

보호 위치는 애플리케이션이 정한다. 모델은 그 앞에서 어디까지 정리할지 선택할 수 있지만 보호 범위를 줄일 수 없다. 새 응답 전달이나 30분 만료는 보호 범위를 바꿀 뿐, 토큰이 N 미만인 대화의 Review를 강제로 실행하지 않는다.

### 모델이 남기는 Pending

Review 결과는 앞에서부터 연속된 정리 구간과 그 뒤의 Pending 하나로 나뉜다. Pending은 별도 테이블이나 모델이 다시 작성한 요약이 아니라 남아 있는 원문 Event다. 중간에 처리하지 않은 구멍을 남기고 뒤쪽만 정리하지 않는다.

Pending은 “끝나지 않은 모든 주제”가 아니라 “다음 답변을 위해 원문으로 더 유지할 흐름”이다. 모델은 앱이 보호한 범위보다 앞에서 Pending을 시작할 수 있다. 긴 여행 계획 전체를 남길 필요는 없으며, 앞부분은 “여행지를 논의했고 숙소는 아직 미정”으로 요약하고 최근 대화만 남길 수 있다. 봇이 질문으로 끝냈다는 이유만으로 모든 과거 대화를 미완료로 묶지 않는다.

| 상태 | CHAT 입력 | Review에서 기억으로 저장 |
| --- | --- | --- |
| 임계치 미만의 원문 | 원문 유지 | 아직 하지 않음 |
| 보호 범위 앞의 원문 | Review 성공 전까지 유지 | 모델이 선택한 연속된 앞 구간만 |
| 앱 보호 범위 또는 모델이 남긴 Pending | 원문 유지 | 불가. Fact도 미리 추출하지 않음 |
| Review에 성공한 앞 구간 | Fact·Episode로 회상 | 이후 다시 처리하지 않음 |
| reroll로 교체한 봇 출력 | 제외 | 제외 |

### 예산과 조회의 일관성

원문은 해당 캐릭터·채널의 관찰 순서로 제공한다. Review 저장과 CHAT 입력 조회 사이에 원문과 기억이 모두 빠지지 않도록 처리 위치·원문·기억을 짧은 일관된 DB 읽기로 고정한다. Review 중 수신한 새 Event는 이번 처리 위치에 포함하지 않고 원문으로 남긴다.

N은 모델의 하드 입력 한도보다 충분히 작게 잡는다. Review에도 전체 원문·기존 기억·지시문·출력 공간이 들어갈 여유가 필요하다. 전체 입력이 넘으면 선택적인 관련 기억부터 줄인다. CHAT이 실제 한도를 넘는 경우에만 같은 담당 작업에 Review를 요청하거나 진행 중 작업을 제한 시간 동안 기다린 뒤 입력을 다시 조립한다.

보호할 원문만으로 한도를 넘거나 Review가 진행할 수 없으면 명시적인 입력 초과로 처리한다. Pending을 몰래 자르거나 보호를 해제하지 않는다. Review 자체가 한도를 넘는 긴 단일 입력의 자동 분할·재귀 요약 체계는 후속으로 둔다. 토큰 임계치만으로 모든 입력 크기를 해결한다고 보장하지 않는다.

## 6. 최소 데이터 모델

아래는 필요한 저장 정보이며 최종 Prisma 필드 선언은 아니다. 조회에 쓰는 값은 컬럼으로, 실행 스냅샷 같은 묶음은 기존 JSON 기록으로 저장한다.

| 모델 | 최소 정보 |
| --- | --- |
| Event | 순서 ID, characterId, channelId, User 작성자와 플랫폼 계정, 플랫폼 메시지 식별자, CREATE/UPDATE/DELETE, 관찰 시각, 확인한 내용, 이전 버전 참조, 중복·순서 판별 정보, 봇 출력의 generationId |
| Fact | ID, characterId, subjectId, factKey, content, 용도(coreReason), 확인 시각 |
| Episode | ID, characterId, 참여자 ID 목록, content, 사건 시점, 갱신 시각 |
| MemoryProcessingState | characterId/channelId 고유 키, 마지막 정리 Event ID, 실패 횟수, 다음 시도 시각 |
| Generation 확장 | MEMORY_REVIEW 타입, CHAT의 전송 종료 시각과 discardedAt, 입력 Event 목록·내용, CHAT의 신규 사용자 입력 목록, Review의 시작 위치·스냅샷 끝·보호 시작점·결과 |
| User 확장 | 봇 계정 공유용 선택적 고유 characterId |

Fact·Episode와 Event 사이에 관계 테이블이나 sourceEventIds JSON을 만들지 않는다. Event에 추출 Generation을 역으로 연결하지도 않는다. 추출 실행 로그의 입력·출력은 진단용이며, 이를 분석해 연쇄 삭제하거나 재구축하는 기능은 없다.

Review와 Pending도 테이블로 만들지 않는다. Review는 Generation에 기록하는 실행이고, Pending은 마지막 정리 위치 뒤에 남은 원문이다. 주제 분할 결과나 Topic ID를 따로 저장하지 않는다.

기억은 같은 characterId의 채널·서버·provider에서 공유한다. 이 정책은 기존의 GLOBAL에 해당하므로 상수인 scope와 characterId를 반복하는 scopeKey를 저장하지 않는다. 모든 기억 조회·변경은 characterId를 필수 조건으로 적용한다. 기존 채널 활성화 scope 설정은 기억 범위를 바꾸지 않는다.

같은 캐릭터의 봇 계정은 공통 User에 연결한다. 사람의 서로 다른 계정은 명시적으로 연결된 경우만 같은 User로 취급한다. 기존 계정 연결도 확인된 캐릭터 매핑으로 수행한다.

Fact는 현재 값을 보관한다. 명시적인 정정이면 같은 행을 갱신하고 별도 SUPERSEDED/INVALIDATED 상태·supersedesId·revision 이력을 두지 않는다. 과거에 무엇을 말했는지는 Event에 남는다. factKey는 좁은 속성을 식별하는 보조 수단이며 문자열이 같다는 이유만으로 서로 다른 사실을 덮어쓰지 않는다. 알레르기·취향처럼 여러 값을 가질 수 있는 속성은 대상별로 구분한다.

Fact의 확인 시각은 추출 실행 시각이 아니라 해당 진술의 관찰 시각이다. 다른 채널의 오래된 구간이 늦게 처리돼도 더 최근 진술로 갱신된 값을 덮어쓰지 않는다. 같은 사실의 재확인도 확인 시각을 과거로 되돌리지 않는다. 이 비교는 출처 그래프 없이 현재 행과 입력 시각으로 처리한다.

Episode는 경험 단위로 추가하고 명백히 같은 사건의 후속 진행이면 갱신한다. 여행 일정을 정정할 수는 있지만 예전 여행과 새 여행을 하나로 합치지 않는다. 과거 사실을 별도로 회상할 가치가 있으면 Episode 내용에 당시 시점을 남긴다.

## 7. Review: 경계 결정과 기억 추출

### 실행 조건과 담당 작업

프로세스에 Review 담당 작업 하나를 둔다. 시작 시 한 번, 이후 1분마다 원문이 N토큰 이상인 채널을 확인한다. 이 주기는 대상을 확인하는 간격이며 시간 경과에 따른 추출 조건이 아니다. N 미만이면 며칠이 지나도 원문으로 유지한다.

한 번에 한 채널의 Review를 실행하고 같은 작업을 중복 실행하지 않는다. 전체 원문이 보호 범위라 정리할 앞부분이 없으면 모델을 호출하지 않는다. 같은 원문 끝 Event와 같은 보호 범위에서는 성공한 Review를 반복하지 않는다. 처리 위치 전진만으로 남은 Pending을 즉시 다시 Review하지 않고, 새 Event나 보호 범위 변화가 있을 때 N을 다시 검사한다. 마지막 성공 실행의 입력 정보로 판단하며 별도 예약 상태 체계는 만들지 않는다.

한 채널의 실패가 다른 채널의 처리를 막지 않도록 제한된 재시도 사이에는 다음 채널을 처리한다. 보통의 CHAT은 Review와 독립적으로 진행한다. §5의 실제 입력 한도 초과 때문에 요청한 Review도 같은 담당 작업을 사용하며 별도 추출 경로를 만들지 않는다.

### 한 번의 Review

1. 마지막 정리 위치 다음의 원문 전체와 스냅샷 끝을 읽고 각 항목에 1부터 시작하는 순번을 붙인다. 애플리케이션이 보호 시작점 `protectedFrom`을 정한다. 보호할 항목이 없으면 원문 개수+1이다.
2. 참여자 별칭, 현재 설정, 제한된 관련 기억과 함께 MEMORY_REVIEW Generation에 입력을 고정한다. DB ID와 모델에 보여 주는 순번·별칭의 매핑은 애플리케이션이 관리한다.
3. 한 번의 모델 호출로 `reviewedThrough`, Episode 후보, Fact 후보를 받는다. 주제 파악·경계 선택·기억 추출을 같은 호출에서 수행한다.
4. 경계·대상·입력 참조·제안한 갱신을 검증한다. 검증에 실패한 결과를 임의로 잘라 적용하지 않는다.
5. 짧은 트랜잭션에서 Fact·Episode 갱신, 마지막 정리 위치, Generation 완료를 함께 저장한다. 처리 위치는 스냅샷 끝이 아니라 `reviewedThrough`가 가리키는 원래 Event ID까지만 전진한다.

저장 시 시작 처리 위치·실행 상태와 선택 구간의 보호 여부를 재확인한다. 도중에 보호가 풀려도 이번 스냅샷의 경계를 더 넓히지 않는다. 교체된 출력은 입력에서 제외하며, 해당 출력의 이력은 실제로 정리한 경계 안에서만 처리 위치가 통과할 수 있다. 새로 도착한 Event와 선택한 경계 뒤의 원문은 그대로 남는다.

### 반환 계약

- `reviewedThrough`는 정리할 마지막 입력 순번이다. `0 <= reviewedThrough < protectedFrom`을 만족해야 하며, `0`은 이번에는 정리할 구간이 없다는 뜻이다.
- Episode는 경험의 내용·참여자·시점과 입력 구간을 반환한다. 정리 구간에서 여러 개를 만들거나 하나도 만들지 않을 수 있다. 주제마다 반드시 하나씩 만들거나 모든 발언을 Episode로 덮을 필요는 없다.
- Fact는 대상 별칭·속성·내용·용도와 `sourceIndexes`를 반환한다. 출처 순번은 자기 진술과 범위를 확인하기 위한 이번 호출의 검증 자료다.
- 모든 후보의 출처는 `reviewedThrough` 이하에 있어야 한다. Pending의 진술로 Fact를 먼저 만들거나 기존 기억을 갱신하지 않는다. Episode에 Pending의 새로운 정보도 섞지 않는다.
- Pending 원문은 반환하지 않는다. 애플리케이션이 경계 뒤의 원문을 그대로 유지한다. `topics`, 별도 구간 처리 상태, 요약을 다시 요약하는 중간 산출물은 없다.
- 기존 기억 갱신은 입력에 제공한 같은 캐릭터·대상의 기억 별칭만 참조한다. 모델이 임의 DB ID·scope·삭제 명령을 만들지 못하게 한다.

원문 전체를 읽는 것은 대화의 흐름과 경계를 파악하기 위해서다. 보호 범위와 모델이 남긴 Pending은 기억을 저장하는 근거로 사용할 수 없다. 후보의 출처 순번 검증만으로 내용의 정확성까지 보장되지는 않으므로, Pending의 정보를 앞 구간의 사실인 것처럼 섞는 사례를 모델 평가에 포함한다. 검증용 출처와 Episode 구간은 실행 기록에만 남기고 Fact·Episode의 영구 관계로 저장하지 않는다.

초기 후보 상한은 Fact·Episode 합계 30개, 각 본문은 1,000자로 둔다. 초과 결과를 잘라 성공 처리하지 않는다. 경계가 전진하고 후보가 없는 경우는 기억할 만한 내용이 없었다는 정상 성공이다. `reviewedThrough = 0`이면 후보도 비어 있어야 하며 원문을 그대로 남긴다. 잘못된 JSON이나 모델 실패는 이 두 경우와 구분한다.

### 예시: 자기소개와 점심 메뉴

1~4번에서 처음 인사하고 이름을 말했으며, 5~10번에서 돈까스를 추천하고 봇의 기호를 이야기했다고 하자. 11번은 사용자의 “비린내 때문에 해산물을 잘 못 먹는다”, 12번은 봇의 “조개도 못 먹어?”다. 12번 응답과 그 입력인 11번이 reroll 보호 대상이면 `protectedFrom = 11`이다.

기존 설정과 충돌하지 않는다고 가정한 신규 기억 출력 예시는 다음과 같다. `user`와 `bot`은 입력에 제공한 참여자 별칭이다. 날짜·갱신 제안 등 선택 필드는 생략했다.

```json
{
  "reviewedThrough": 10,
  "episodes": [
    { "from": 1, "to": 4, "participants": ["user", "bot"], "content": "사용자와 봇이 처음 인사하고 서로 이름을 소개했다." },
    { "from": 5, "to": 10, "participants": ["user", "bot"], "content": "봇이 점심으로 돈까스를 추천했고 사용자는 좋다고 했다. 봇은 자신은 비린내 때문에 돈까스를 싫어한다고 말했다." }
  ],
  "facts": [
    { "subject": "user", "factKey": "name", "content": "사용자의 이름은 아무개다.", "coreReason": "NONE", "sourceIndexes": [3] },
    { "subject": "bot", "factKey": "name", "content": "봇의 이름은 엄준식이다.", "coreReason": "SELF_SETTING", "sourceIndexes": [4] },
    { "subject": "bot", "factKey": "preference:돈까스", "content": "봇은 비린내 때문에 돈까스를 싫어한다.", "coreReason": "NONE", "sourceIndexes": [8, 10] }
  ]
}
```

애플리케이션은 11~12번을 원문으로 남긴다. 해산물에 관한 Fact는 이번에 만들지 않는다. 이후 해당 구간을 정리하더라도 “잘 못 먹는다”를 “싫어한다”나 “알레르기가 있다”로 바꾸지 않는다. 첫 인사를 별도 경험으로 남길 가치가 없다고 판단했다면 첫 Episode를 생략해도 된다. 이 예시는 필수 주제 분할 정답이 아니라 경계와 출처 범위를 설명한다.

### 내용 규칙

- 사용자와 봇의 자기 진술을 같은 기준으로 처리한다. Fact 대상은 진술한 참여자와 일치해야 한다.
- 타인 보고·추측·인용·가정에서 인물의 사실을 만들지 않는다. 제3자 이야기를 Episode로 우회 저장하지 않는다.
- 압축하더라도 대상·이유·조건·시점·부정·불확실성을 임의로 바꾸지 않는다. 아직 결정하지 않은 계획은 미정인 상태로 요약할 수 있다.
- 같은 사실의 재확인은 확인 시각만 갱신한다. 새로운 근거 목록이나 확인 횟수 점수는 쌓지 않는다.
- 명시적인 정정·변화만 기존 사실을 갱신한다. 자동 모순 해결은 만들지 않고, 해석이 불명확한 갱신 후보는 적용하지 않는다.
- identity에 없는 봇 자기 설정은 실제 발언에서 추출할 수 있다. 추출 모델이 새로운 설정이나 사건을 창작하지 않는다.
- 일반 삭제 관찰만으로 취소·거짓·망각을 추론하지 않는다.

### 실패와 재시작

모델 호출은 초기 60초 제한을 두고, 실패하면 처리 위치를 유지한 채 1분·5분·15분 뒤 최대 세 번 재시도한다. 계속 실패하면 해당 채널의 자동 시도를 멈추고 로그로 알린다. 재시도 재개는 유지보수로 실패 상태를 초기화하는 수준으로 두며 전용 운영 도구는 만들지 않는다.

재시작하면 DB의 처리 위치와 마지막 실행 기록에서 이어 간다. 미완료 실행은 중단 처리하고 현재 원문·보호 범위로 입력을 다시 구성한다. 실패 재시도도 지금 유효한 입력인지 확인한다. 검증 출력만 별도 저장해서 모델 호출을 생략하는 복구 단계는 만들지 않는다. DB 커밋이 이미 끝났다면 처리 위치와 완료 상태로 중복 적용을 막는다. 종료·시간 초과 뒤 늦게 반환된 결과는 현재 실행 상태를 검사해 버린다.

AI 호출은 DB 트랜잭션 밖에서 수행한다. 종료 시 새 Review를 중단하고 진행 호출을 취소한 뒤 기존 종료 절차의 제한된 대기 안에서 정리한다. 실패 시 원문은 그대로 남긴다. 실제 CHAT 입력 한도도 넘었다면 무제한 재시도하거나 원문을 조용히 자르지 않고 입력 초과를 보고한다.

## 8. 검색과 답변

CHAT 입력은 현재 identity·운영 지시, 필요한 Fact·Episode, 현재 채널의 원문 Event로 구성한다. 기억을 방금 작성된 사용자 메시지나 운영 명령으로 위장하지 않는다. 기억 속 문장을 시스템 지시로 실행하지 않도록 구분한다.

기억 검색은 다음 두 경로로 시작한다.

- 핵심 Fact: 현재 참여자의 건강 제약·대화 선호와 캐릭터의 기본 자기 설정을 직접 조회한다. 초기 용도는 NONE, HEALTH_CONSTRAINT, SELF_SETTING, DIALOGUE_PREFERENCE로 제한한다.
- 관련 기억: 현재 질문의 단어·이름·장소를 바탕으로 Fact·Episode 본문을 검색한다. 최근 N개만 후보로 삼지 않아 오래된 기억도 찾을 수 있게 한다. 조회 결과와 입력 예산은 제한한다.

검색 결과를 모델에 전달하기 전에 캐릭터와 대상 범위를 DB 조회에 적용한다. MVP는 1:1 대화를 기준으로 현재 사용자와 캐릭터에 관련된 기억을 공급한다. 다른 사용자에게 귀속된 건강 제약이나 언급 회피 요청을 현재 사용자의 것으로 제공하지 않는다.

관련 기억의 초기 예산은 3,000토큰이다. 핵심 Fact는 검색 점수 때문에 빠뜨리지 않는다. 핵심 Fact와 필수 원문이 모델 한도를 넘으면 입력 초과로 처리한다. 별도 모델 압축 호출을 추가하지 않는다.

현재 사용자의 명시적 정정과 최신 대화 요청을 오래된 기억보다 우선한다. 봇 자기 설정은 현재 identity를 우선하고, 설정 변경만으로 가상의 이사 같은 사건을 만들지 않는다. 설정 파일 변경에 따른 기억 재검사·자동 무효화 작업과 매 답변 전 별도 모델 검사는 제외한다. 이 우선순위는 모델 평가로 확인하며 절대적인 일관성을 보장한다고 표현하지 않는다.

### “그 일은 잊어줘”

요청은 원문에 있을 때부터 답변에 반영한다. 이후 Review가 해당 발언을 정리하는 시점에 “사용자는 특정 이야기를 먼저 꺼내지 않기를 원한다”는 대화 선호 Fact로 저장하고 핵심 조회에 포함한다. Pending에 남아 있는 동안은 원문으로 반영한다. 관련 사건의 Episode는 유지한다. 요청의 대상과 조건을 내용에 남기며, 영구히 아무 상황에서도 답하지 않는 규칙으로 확대하지 않는다.

사용자가 나중에 먼저 그 이야기를 꺼내면 현재 요청의 맥락에서 응답한다. 회피 요청을 명시적으로 철회하면 해당 선호를 갱신한다. 별도 금지 주제 테이블, Episode별 억제 플래그, 정책 엔진은 만들지 않는다.

### 수용하는 검색·공유 한계

다른 채널의 원문은 제공하지 않는다. 같은 캐릭터라도 새 자기 설정과 대화 선호는 해당 구간의 Review 완료 전까지 다른 채널에서 알지 못할 수 있다. N 미만으로 끝난 짧은 대화나 Pending은 장기간 공유되지 않을 수 있다. 이 지연을 수용하며, 유휴 시간에 따른 강제 Review나 즉시 공유가 필요해지면 별도 요구사항으로 다룬다.

단어 검색만으로 표현이 크게 다른 질문까지 잘 찾는다고 가정하지 않는다. 첫 구현에서는 오래된 기억의 저장·조회·답변 반영을 검증하고, 표현 변화에 따른 검색 실패 사례를 모은다. 벡터 검색은 이 사례를 개선하는 후속 작업으로 추가한다.

과거 원문을 명시적으로 조회하는 기능은 현재 Message만 사용한다. 삭제된 메시지를 Event나 Generation 로그로 우회해서 찾아 주지 않는다. 일반 회상은 Fact·Episode를 사용한다.

## 9. 관리자 유지보수의 경계

관리자는 필요할 때 특정 Fact·Episode를 직접 수정·삭제할 수 있다. 이 작업을 캐릭터에게 일어난 사건으로 자동 기록하지 않는다. 범용 콘솔이나 명령을 이번 MVP에서 개발하지 않는다.

자동 연쇄 처리는 없다. Event를 삭제해도 이미 만든 Fact·Episode는 남고, Fact를 삭제해도 관련 Episode까지 사라지지 않는다. 이미 처리한 구간은 자동 재추출하지 않으므로 삭제한 기억을 복원하는 작업도 없다. 다만 이후의 새 대화에서 같은 사실을 다시 배울 수는 있다.

직접 유지보수는 프로세스를 멈추고 수행한다. 실행 중 추출과 관리자 수정을 조정하는 잠금·버전 체계를 만들지 않는다. 아직 처리하지 않은 원문을 남겨 두면 이후 추출로 기억이 생성될 수 있으므로 필요한 삭제 범위는 관리자가 결정한다. 이 기능은 “관련 흔적 전체의 완전 삭제”를 보장하지 않는다.

## 10. 구현 순서와 확인할 결과

각 단계에서 관련 단일 테스트를 먼저 실행하고, 동작 변경을 마무리할 때 전체 `npm test`를 실행한다. DB 변경은 실사용 DB가 아닌 격리된 임시 SQLite와 별도 생성 경로에서 검증한다. 실제 Discord 배포, 실사용 `.env`·DB·사용자 content 변경은 이 계획의 구현 검증에 포함하지 않는다.

### 1단계: Event 저장과 제한된 reroll

- [ ] Message와 Event 저장, 플랫폼 수정·삭제 연결, 봇 전송 종료 시각과 실제 출력 식별을 구현한다.
- [ ] reroll의 최신 응답·30분 조건과 discardedAt 적용을 공통 유스케이스에 둔다. Discord 명령은 판정 결과에 따라 정리·응답한다.
- [ ] 일반 수신·수정·삭제의 답변 예약은 기존 Buffer 흐름을 사용한다. 중복·무변경·봇 자신의 출력·reroll 정리 삭제는 중복 예약하지 않는다.
- [ ] 신규 기억 경로로 전환할 때 기존 즉시 추출 등록을 해제한다. 두 경로가 동시에 기억을 쓰지 않게 한다.
- [ ] 검증: 저장 원자성, A→B→A, 중복 변경, 삭제 뒤 늦은 갱신, 29:59 허용/30:00 거부, reroll·새 CHAT·Review의 보호 범위 경쟁, 직전이 아닌 응답 거부, 사용자 입력 보존, 여러 출력 조각, 연속 reroll·실패 시 이전 응답 부활 방지.

### 2단계: 원문 컨텍스트와 Review

- [ ] Fact·Episode·MemoryProcessingState와 공통 봇 User 매핑을 추가한다.
- [ ] HistoryService의 고정 개수 Message 조회를 마지막 정리 위치 뒤의 원문과 보호 범위 규칙으로 교체한다. CHAT 신규 사용자 입력 목록을 별도로 기록한다.
- [ ] 원문 토큰 계산, N 임계치, 전체 스냅샷과 protectedFrom, 한 번의 Review 호출을 구현한다.
- [ ] reviewedThrough·후보 출처를 검증하고 기억 갱신과 처리 위치를 원자적으로 저장한다. Pending은 남은 원문에서 계산한다.
- [ ] 검증: N 미만/이상 경계, N 미만에서 30분이 지나도 Review하지 않음, 30분 전이라도 보호 범위 앞은 정리 가능, 중간 구멍·보호 범위 침범 거부, Pending 출처의 Fact·Episode 거부.
- [ ] 검증: 새 Event 도착 시 스냅샷 끝이 아닌 선택 경계까지만 전진, 긴 전송의 전체 조각 보호, reroll·실패 후 미응답 유지, Review 실패 시 원문 유지, 재시작·커밋 재시도 시 중복 없음, CHAT 원문·기억 누락 없음.
- [ ] 검증: 빈 후보와 무진전 결과 구분, 같은 입력 무한 Review 방지, 보호된 Pending만으로 한도 초과 시 명시적 실패, 늦은 과거 Review가 현재 Fact를 덮어쓰지 않음.

### 3단계: 기억 검색과 실제 답변

- [ ] 핵심 Fact·단어 검색을 CHAT에 연결하고 기존 Memory 주입 경로를 교체한다.
- [ ] 정정·자기 설정·대화 선호를 모델 입력과 최종 답변까지 검증한다.
- [ ] 기본 테스트는 모델 함수를 주입해 실행한다. 실제 모델 평가는 별도 실행으로 두고 결과와 실패 사례를 기록한다.
- [ ] 검증: 네 달 전 알레르기 반영, 오래된 여행 조회, 동일 채널의 원문 자기 설정 유지, Review 뒤 같은 캐릭터의 다른 채널에서 회상, 다른 캐릭터·사용자 정보 혼동 방지, “잊어줘” 이후 자발적 언급 회피, 명시적 정정 반영, 삭제 원문 우회 조회 차단.
- [ ] Review 품질 사례: §7의 1~10 정리/11~12 Pending, 해산물 Fact 조기 추출 방지, “잘 못 먹음”을 “싫어함”으로 바꾸지 않음, 질문으로 끝나는 긴 대화의 앞부분 정리, 미완료 계획의 미정 상태 보존, 보호된 뒤쪽 정보가 앞부분 기억에 섞이지 않음.

### 현재 코드의 변경 지점

아래 경로와 동작은 문서 작성 시 확인했다. 신규 클래스는 책임이 실제로 분리될 때만 추가한다.

| 현재 위치 | 필요한 변경 |
| --- | --- |
| `prisma/schema.prisma` | 새 저장 모델과 조회에 필요한 필드·제약. 현재는 기존 Memory 모델만 존재한다. |
| `src/application/RerollConversation.js` | 현재 Generation 연결 메시지를 모아 삭제하는 흐름에 작성자·최신 응답·시간 판정과 선행 교체 표시 추가 |
| `src/platforms/discord/commands/reroll.js` | 현재 prepare 이후 먼저 플랫폼 삭제하는 순서를 애플리케이션의 실행 시점 재검사 뒤로 이동 |
| `src/messages/MessageService.js`, `src/repositories/MessageRepository.js` | 현재 상태 변경과 관찰 이력의 원자적 저장 |
| `src/messages/MessageSender.js`, `src/chat/ChatGenerationLifecycle.js` | 실제 전송 출력과 고정된 전송 종료 시각 기록 |
| `src/messages/HistoryService.js`, `src/chat/context/ChatContextPreparer.js` | 현재 개수 제한·최근 봇 메시지 기준 분리에서 Review 처리 위치·Pending·보호 범위 기준으로 전환 |

## 11. 완료 기준

완료는 §10의 저장·경계 테스트와 실제 모델 사례를 통과하고, 실패·지연·검색 한계를 기록한 상태다. 필수 확인 항목은 다음 여섯 가지다.

1. 토큰 임계치에서 Review를 실행하며 재생성 가능한 내용과 Pending의 사실을 먼저 기억으로 저장하지 않는다.
2. 정리할 앞 구간과 Pending 끝부분 하나를 구분하고, 검증·저장에 성공한 앞 구간만 원문 컨텍스트에서 제외한다.
3. 확정된 기억에 대한 자동 철회·연쇄 무효화·복원 경로가 없다.
4. 오래된 사실·경험을 실제 답변에 사용할 수 있고, 명시적인 정정과 언급 회피 요청을 반영한다.
5. Review 실패·재시작으로 원문을 잃거나 결과를 중복 적용하지 않고, 같은 입력을 진전 없이 반복 호출하지 않는다.
6. 손실 압축·단어 검색의 한계와 짧은 대화의 채널 간 공유 지연을 숨기지 않는다.

MVP를 마치기 위해 별도 관리자 UI, 벡터 검색, 자동 설정 재검사, 전체 원문 재처리, 다중 프로세스 지원을 추가하지 않는다.
