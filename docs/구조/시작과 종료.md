# 시작과 종료

## 시작 순서

Discord와 CLI 진입점은 Windows 인코딩 보정, `.env` 로드, ConfigManager 생성, 로거 설정을 먼저 수행한다. 이후 동적 import로 나머지 런타임을 불러온다.

Discord는 client를 만들고 `createDiscordApplication`을 호출한다. container에서 chat·image 설정을 검증하고 도구를 로드한 뒤 이벤트·명령을 연결한다. 종료 핸들러 등록 후 캐릭터별 토큰으로 로그인한다. ready 이벤트에서 봇 플랫폼 계정을 준비한다.

CLI는 모의 플랫폼 client와 같은 container를 사용한다. 종료 핸들러와 봇 계정을 준비하고 `startRepl`로 TUI를 연다. 여기서 모의인 것은 플랫폼 client이며 AI 생성은 실제 호출이다.

## 종료 순서

`SIGINT`와 `SIGTERM`에서 중복 종료를 막고 다음 작업을 수행한다.

1. 버퍼 타이머와 세션 상태 정리.
2. 진행 중인 모델 요청에 abort 전달.
3. `PROCESSING`·`GENERATED` Generation을 `CANCELLED`로 변경.
4. Discord client 종료, 설정 watcher 종료, Prisma 연결 종료.
5. 종료 코드 0으로 종료.

GenerationRepository와 DB disconnect 함수는 종료 핸들러에 주입된다. 강제 종료로 이 절차가 실행되지 않으면 진행 상태가 남을 수 있다. 별도 자동 복구 worker는 현재 조립되어 있지 않다.

## 설정 변경의 적용 범위

ConfigManager는 JSON 변경을 감시하지만 모든 객체를 다시 만들지는 않는다. 버퍼 시간·캐릭터 경로·Repository의 캐릭터 ID처럼 생성자에서 고정한 값은 재시작해야 확실히 적용된다. `sequence.js`는 동적 import 캐시의 영향도 받는다.

파일 reload는 JSON을 다시 읽으며 최초에 적용한 환경 변수 override를 다시 적용하지 않는다. 인증·캐릭터·팩 변경 후에는 재시작하는 운영 방식을 사용한다.

## 기동 책임을 가진 구성 요소

| 구성 요소 | 책임 | 실패가 드러나는 위치 |
| --- | --- | --- |
| loadEnv | dotenv 로드. 기본적으로 기존 shell 환경 변수를 덮어쓰지 않음 | 환경 설정 단계 |
| createConfigManager | JSON 로드와 인증 override | 설정 검증 또는 이후 값 사용 |
| createContainer | 설정 검증과 공통 의존성 생성 | 플랫폼 main 초기화 |
| createDiscordApplication | 공통 객체와 Discord 이벤트·명령 연결 | Discord 기동 |
| BotAccountService.initBotAccount | 기존 봇 계정 갱신 또는 User·계정 생성 | Discord ready 또는 CLI 준비 |
| registerShutdown | 종료 신호 연결과 정리 절차 | 종료 로그 |

Discord는 main의 ConfigurationError를 코드 78로 분류한다. CLI 진입점에 동일한 오류 분류용 catch가 모두 구현되어 있다고 가정하지 않는다. 플랫폼별 기동 오류 설명을 추가할 때 실제 진입점에서 잡는 범위를 확인한다.

## 종료할 때 작업을 기다리는가

registerShutdown은 버퍼를 없애고 요청에 abort를 전달하지만 모든 ChatFlow Promise가 끝날 때까지 join하지 않는다. 이후 DB 진행 상태를 취소하고 플랫폼·설정·DB 연결을 닫는다. 따라서 ‘graceful’은 정리 순서를 가진 종료이며 진행 중인 응답을 모두 완성해 주는 정책이 아니다.

generation 취소·client 종료·DB disconnect의 일부 오류는 로그를 남기고 다음 정리로 진행한다. DB 취소 실패가 있으면 종료 코드만 보고 모든 row가 정리되었다고 판단하지 않는다. 강제 종료와 프로세스 손실은 이 신호 핸들러의 보장 밖이다.
