## 1. 제품 목표와 확정된 전제

이번 기능은 긴 대화를 압축하는 것만을 목표로 하지 않는다. 비연속적으로 이어지는 대화에서 과거 정보를 다시 사용하는 것이 중심이다.

- 네 달 전 사용자가 땅콩 알레르기를 말했다면 오늘 땅콩샌드위치를 이야기할 때 반영한다.
- 지난봄 함께 이야기했던 여행을 다시 꺼내면 관련 경험을 떠올린다.
- 봇이 대화 중 자신의 거주지를 부산으로 만들었다면 다음 달에도 같은 설정을 유지한다.
- 사용자 정정이나 답변 재생성으로 폐기된 내용을 현재 사실로 사용하지 않는다.

확정된 전제:

1. 현재는 1:1 대화를 기준으로 한다. 향후 n:1 대화 지원은 예정되어 있다.
2. 하나의 Node.js 프로세스에서 여러 provider의 입출력이 동시에 진행될 수 있다. 같은 DB에 여러 애플리케이션 프로세스를 붙이지 않는다.
3. Message는 Discord의 현재 메시지 상태를 반영한다. 수정 시 본문을 갱신하고 삭제 시 행을 제거한다. Events는 발언과 변화를 보존하고 Fact·Episode는 이를 가공한 기억이다. Generation은 실행 로그다.
4. 사용자 발언과 실제로 전달된 봇 발언 모두 기억 추출 대상이다.
5. 봇은 identity.md에 없는 자기 설정을 대화 중 자연스럽게 만들 수 있다. 이는 의도된 캐릭터 창작이다.
6. 기존 메모리 기능은 사용 실적이 없는 구현 잔재로 본다. 기존 구조와의 호환성을 새 설계의 목표로 삼지 않는다.
7. 비용·지연 최적화보다 기능 완성을 우선한다. 무한 호출·무제한 입력·종료 불능은 처음부터 방지한다.
8. 현재 대화 대상으로 수신한 사용자 메시지는 즉시 인지하는 정책을 유지한다. Buffer는 답변 실행을 예약하며 읽는 시점을 결정하지 않는다. 잠수·지연 인지 정책은 이번에 구현하지 않는다.
9. 일반 CHAT 입력은 현재 범위의 Events와 관련 Fact·Episode로 구성한다. 과거 대화 원문을 자동으로 다시 넣지 않는다. Message는 명시적인 원문 조회·인용에 사용한다.
10. MemorySource는 만들지 않는다. Events가 근거 보존을 맡고 FactEvidence·EpisodeEvidence는 Event를 직접 참조한다.

## 2. 설계 선택과 MVP 범위

대화가 의미상 끝났는지 판정하지 않고, 새로 인지한 발언을 크기가 제한된 묶음으로 처리한다. 한 묶음에서 사실 기억과 경험 기억을 함께 만든다.

| 요소                              | 결정과 이유                                                                             |
| --------------------------------- | --------------------------------------------------------------------------------------- |
| 의미상 Conversation 경계          | 도입하지 않는다. 사실과 경험을 기억하기 위해 대화 종료를 확정할 필요는 없다.            |
| Pending tail, 24시간 mustFinalize | 도입하지 않는다. 미답변 질문과 미완료 계획은 기억 내용으로 표현한다.                    |
| 사용자·봇 별도 기억 시스템        | 만들지 않는다. 같은 참여자 식별자, Fact·Episode, 추출·갱신·검색 서비스를 사용한다.      |
| 실행 기록                         | Generation에 MEMORY_EXTRACT 등 기억 작업 타입을 추가한다. CHAT과 구분한다.              |
| 다중 worker claim                 | 도입하지 않는다. 프로세스 내부 단일 기억 처리 담당 작업과 조건부 저장을 사용한다.       |
| 검색                              | 핵심 기억 직접 제공 + 의미 검색 + 단어 검색을 구현하고 실제 답변까지 연결한다.          |
| 별도 벡터DB                       | MVP에서는 도입하지 않는다. SQLite에 벡터를 저장하고 애플리케이션에서 유사도를 계산한다. |

별도 벡터DB는 큰 데이터에서 검색을 빠르게 할 수 있지만 저장소 동기화와 운영 부담이 생긴다. 초기에는 검색 품질과 규모를 측정한다. 전체 벡터 비교가 병목으로 확인되면 검색 저장소를 교체한다. Fact·Episode와 근거는 검색 인덱스와 독립적으로 유지한다.

요약만 반복 갱신하는 설계는 채택하지 않는다. 경험 요약과 별개로 중요한 사실을 보존해야 네 달 전 정보를 다시 찾을 수 있다.

## 3. 참여자: 봇과 사용자를 같은 위치에 둔다

서비스 입력은 사용자·봇별 전용 인수가 아니라 participants와 statements로 통일한다.

- 내부 참여자 ID는 기존 User.id를 사용한다. 기존 구조에서도 봇 계정은 User → PlatformAccount → Message를 사용한다.
- PlatformAccount는 provider별 계정이다. 같은 참여자의 여러 계정은 하나의 User에 연결한다.
- 같은 characterId의 봇 계정은 동일한 User로 연결한다. 제안: User에 선택적인 고유 characterId를 추가하고 계정 초기화 시 이를 기준으로 조회한다.
- 사람의 다른 provider 계정은 명시적으로 연결된 경우만 같은 참여자로 취급한다. 이름이나 말투로 합치지 않는다.
- 모델에는 이번 입력의 참여자 목록과 짧은 별칭을 제공한다. 반환된 별칭은 애플리케이션이 ID로 변환한다. 모델이 새 DB ID를 만들게 하지 않는다.

MemoryService, MemoryExtractor, MemoryRetriever에 BotMemory 전용 경로를 만들지 않는다. 자기 발언, 타인의 주장, 설정 문서처럼 근거의 성격을 공통 규칙으로 평가한다. 캐릭터 설정을 불러오는 어댑터만 봇에게 존재하는 추가 입력이다.

현재 BotAccountService는 provider별 초기화에서 서로 다른 User를 만들 수 있다. 기존 계정을 연결할 때는 확인된 characterId 매핑을 사용한다. 다른 캐릭터까지 합치거나 사용자의 계정을 추정으로 연결하지 않는다.

## 4. 기억의 종류와 자기 설정 정책

### 4.1 사실 기억과 경험 기억

사실 기억은 Fact, 경험 기억은 Episode의 독립된 두 테이블에 저장한다. 공통 Memory 테이블이나 공통 부모 테이블을 두고 kind로 구분하지 않는다. 사용자와 봇은 이 두 테이블과 공통 추출·갱신·검색 서비스를 함께 사용한다. 별도 Summary나 BotMemory 테이블은 만들지 않는다.

| 테이블  | 예시                                                           | 필요한 정보                           |
| ------- | -------------------------------------------------------------- | ------------------------------------- |
| Fact    | 민수는 땅콩 알레르기가 있다. / 봇은 부산에 산다.               | 대상, 속성, 값, 근거, 확인 시점       |
| Episode | 민수와 봇은 봄 여행지를 골랐고 숙소 예약은 아직 정하지 않았다. | 참여자, 사건, 시점, 미해결 내용, 근거 |

모든 잡담을 저장하지 않는다. 지속적인 사실, 취향, 관계, 약속, 중요한 경험을 우선한다. 기억할 내용이 없으면 빈 결과로 정상 완료한다.

경험을 연속된 메시지 구간 하나에 강제로 대응시키지 않는다. 여러 발언이 하나의 경험을 뒷받침할 수 있고, 하나의 발언이 여러 기억의 근거가 될 수도 있다.

### 4.2 봇의 즉석 설정

우선순위:

1. 현재 identity.md와 명시적인 캐릭터 설정.
2. 기존에 채택되어 유지 중인 자기 설정 기억.
3. 앞의 두 곳에 없는 사항에 대해 이번 답변에서 새로 만든 자기 설정.

예: identity.md와 기존 기억에 거주지가 없다면 봇은 “나는 부산에 살아”라고 답할 수 있다. 실제 전달된 발언을 봇 자신에 관한 Fact로 저장한다. 다음 답변에서는 새 거주지를 다시 만들지 않는다.

- 창작은 CHAT 단계에서 한다. 추출 모델은 대화에 없는 거주지나 사건을 추가하지 않는다.
- “부산에 살면 좋겠다”, 인용, 가정, 농담을 거주 사실로 확정하지 않는다.
- “나는 부산에 살아”와 “너 부산 살지?”를 구분한다. 자기 진술과 타인에 관한 추측은 근거가 다르다.
- 이 대상·근거 규칙은 사용자에게도 동일하게 적용한다. 친구 이야기를 작성자 자신의 정보로 저장하지 않는다.
- 자기 설정 창작 허용은 사용자나 외부 세계에 관한 사실까지 마음대로 만드는 허용이 아니다.
- 기존 자기 설정과 다른 발언은 자동으로 덮어쓰지 않는다. 명시적인 정정·변화인지 검사한다.
- 새 자기 설정을 identity.md에 자동 기록하지 않는다. 사용자 소유 설정 파일과 대화 기억은 별개다.

### 4.3 설정 변경

설정 원문과 편집 가능한 변수의 해시를 버전으로 기록한다. 날짜에 따라 계산되는 나이 같은 값 자체를 설정 편집으로 오인하지 않는다.

설정 변경을 감지하면 관련 자기 기억을 다시 검사한다. identity.md가 거주지를 서울로 명시하면 이전 부산 기억은 현재 거주지로 사용하지 않는다. 그렇다고 “부산에서 서울로 이사했다”는 사건을 만들어내지는 않는다.

검사 중인 자기 기억은 현재 설정과 충돌하는 내용으로 공급하지 않는다. 검사는 모델 호출을 사용할 수 있으므로 실행과 버전을 기록한다. 이전 설정 버전에서 생성 중이던 결과는 새 설정 검사를 거치기 전 적용하지 않는다. 현재 설정을 우선하는 규칙은 CHAT 입력에도 항상 포함한다.

## 5. 기억의 대상과 사용할 수 있는 범위

누구에 관한 기억인지와 어느 대화에서 사용할 수 있는지는 별개다. Fact와 Episode의 사용 범위는 `/활성화`에서 선택한 채널의 스코프를 따른다. 기존 명령의 선택지는 `global`, `server`, `channel`이다.

- 일반 기억을 무조건 CHANNEL로 제한하거나 순수 자기 설정을 별도 CHARACTER 스코프로 자동 공유하는 기존 기본 정책은 채택하지 않는다.
- 작성자·기억 대상·참여자·획득 채널을 보존한다. n:1에서도 마지막 발언자에게 모든 기억을 귀속하지 않는다.
- 검색 후보를 모델이나 벡터 비교에 넘기기 전에 애플리케이션에서 확정된 범위 정책을 적용한다. 모델이 공개 가능 여부를 최종 결정하지 않는다.

`/활성화`의 설정을 따른다는 원칙은 확정됐지만, 각 스코프의 정확한 공유 경계와 읽기·쓰기 의미는 아직 미정이다. §17에서 별도로 관리하며 관련 스키마·추출·검색 구현 전에 확정한다.

## 6. 메시지 상태와 인지한 경험: Events

### 6.1 저장 책임과 생성 시점

| 저장소       | 책임                                                                                            |
| ------------ | ----------------------------------------------------------------------------------------------- |
| Message      | 현재 메시지 본문·첨부·작성자. 수정 시 갱신, 삭제 시 행 제거. 삭제 흔적이나 구버전은 남기지 않음 |
| Events       | 발언 생성·수정·삭제와 실제 전달된 봇 발언을 관찰 순서대로 보존. 현재 문맥과 기억 추출의 근거    |
| Fact·Episode | Events를 가공한 사실·관계·경험. 과거 회상에 사용                                                |

- 현재 대화 대상으로 수신한 사용자 발언은 즉시 인지한 것으로 기록한다. 답변 시작 전 수정·삭제되더라도 이미 수신한 경험은 유지한다.
- 봇 발언은 플랫폼 전송이 확인된 부분만 생성 Event로 남긴다. 미전송 초안과 도구 내부 출력은 제외한다. Generation 취소만으로 이미 전달된 조각을 철회하지 않는다.
- 생성·수정 Event에는 확인한 본문과 작성자를 보존한다. 수정은 이전 버전을 참조하고 삭제는 마지막으로 알고 있던 버전을 참조한다. 이전 Event가 없고 Message에만 기존 본문이 있으면 해당 변경 Event에 확인한 이전 본문을 보존한다. 이전 본문을 매번 중복 저장할 필요는 없다.
- Event는 Message FK 없이도 해석할 수 있는 플랫폼 메시지 ID·채널·작성자·수신 시각·버전·출처를 보존한다. Message 삭제가 Events나 FactEvidence·EpisodeEvidence를 연쇄 삭제하지 않게 한다.
- 과거 자료 가져오기는 실시간 수신과 출처를 구분한다. 자동으로 현재 대화의 새 발언으로 넣지 않는다. 별도의 읽음 상태·잠수 모델은 이번에 추가하지 않는다.
- 첨부파일은 실제로 인지한 텍스트 표현이 있는 범위만 기억 근거로 사용한다. 이미지·음성 원본의 새로운 기억 해석 파이프라인은 MVP에서 만들지 않는다.

Message 변경과 Event 저장은 같은 DB 트랜잭션으로 묶는다. 같은 채널의 변경을 순서대로 적용하고, 명령어 처리와 Gateway 수신이 같은 변경을 중복 기록하지 않게 한다. 늦은 갱신이 이미 삭제된 메시지를 다시 만들지 않도록 저장된 삭제 이력을 확인한다.

외부 전송과 SQLite 저장은 하나의 트랜잭션이 될 수 없다. 봇 전송 후 DB 실패는 플랫폼 메시지 ID로 저장을 재시도하고 확인 가능한 전송 기록으로 복구한다. 확인할 수 없는 전송은 복구 필요 상태를 기록한다. Discord 연결 중단 중 놓친 수정·삭제의 재동기화와 플랫폼 전체 복제 보장은 이번 범위에서 제외한다.

### 6.2 Discord 이벤트와 수정·삭제·재생성

Discord의 MESSAGE_UPDATE, MESSAGE_DELETE, MESSAGE_DELETE_BULK를 연결한다. 수정 이벤트는 변경된 데이터를 제공하며 이전 본문을 함께 보내지 않는다. 삭제 이벤트는 메시지 식별자를 제공하며 본문이나 삭제 행위자를 제공하지 않는다. 이전 내용은 로컬에 확인된 버전에서 가져온다. 본문이 없는 업데이트를 빈 문자열 수정으로 취급하지 않고, 실제 본문·대상 첨부 변화가 있는지 검사한다. [Discord 공식 이벤트 명세](https://docs.discord.com/developers/events/gateway-events#message-update)

| 사건                         | 처리                                                                                     |
| ---------------------------- | ---------------------------------------------------------------------------------------- |
| 사용자 발언 수신             | Message와 생성 Event 저장. 즉시 인지 정책 적용                                           |
| 메시지 수정                  | Message 갱신, 새 버전과 수정 Event 기록. 이전 경험은 덮어쓰지 않음                       |
| 일반 삭제                    | 삭제 Event 기록 후 Message 행 제거. 기존 경험·기억 유지                                  |
| 이전 내용을 모르는 수정·삭제 | 확인한 데이터만 기록. 알 수 없는 이전 본문·작성자·삭제 의도를 추측하지 않음              |
| 답변 재생성                  | 대상 봇 발언 Event의 근거 상태를 RETRACTED로 표시하고 의존 기억 재검토. 일반 삭제와 구분 |
| 명시적인 기억 철회           | 지정 Event 근거의 파생 기억을 즉시 검색에서 제외하고 재검토. 전체 계정 삭제와 구분       |

삭제만으로 약속 취소나 발언의 거짓을 확정하지 않는다. 명시적 정정은 현재 기억에 반영하고, 삭제 행위자·의도는 근거 없이 추측하지 않는다. 인지했다고 반드시 수정·삭제를 언급하게 하지 않는다.

재생성은 RP 밖의 수정이다. 내부 철회 기록과 관련 기억 제외를 먼저 저장한 다음 플랫폼 정리와 새 CHAT을 진행한다. 실패해도 철회 상태를 유지한다. 뒤따르는 Gateway 삭제가 일반 삭제로 처리되어 철회된 발언을 다시 문맥이나 기억에 넣지 않도록 작업 사유를 연결한다.

봇 답변을 재생성했다고 사용자 발언까지 폐기하지 않는다. 기존 RerollConversation의 Generation 연결 기준 삭제는 작성자와 실제 출력 범위를 구분하도록 바꿔야 한다. FactEvidence·EpisodeEvidence로 해당 Event에 의존한 기억을 찾고 다른 유효 근거가 남았다면 재검토 후 복원한다. 재생성 이후 사용자 발언까지 자동 삭제하거나 대화 전체를 되감지 않는다. 폐기된 봇 발언을 인용한 사용자 발언은 독립적인 사실 확인으로 취급하지 않는다.

### 6.3 현재 Events로 구성하는 대화 컨텍스트

Message의 최신 본문 목록에 변경 이벤트를 덧붙이지 않는다. 현재 범위의 Events를 관찰 순서대로 조립한다. 예를 들어 “사용자: 세 시에 만나자 → 봇: 좋아 → 앞선 발언이 네 시로 수정됨”을 유지한다. 수정·삭제 관찰은 사용자가 새로 작성한 발언이나 운영 지시로 위장하지 않는다.

메시지 생성·수정·삭제는 같은 이벤트 처리 경로를 사용한다. `수신 → 중복·실제 변경 확인 → Message와 Event 저장 → 답변 예약 대상 판정 → Buffer 갱신` 순서로 처리한다. 같은 채널에서 답변 예약 대상인 세 이벤트 중 하나가 Buffer 타임아웃 안에 발생하면 종류와 관계없이 카운트다운을 초기화한다. 예약이 없다면 새로 예약한다. 플랫폼이 다른 같은 채널 ID는 별개로 취급한다.

봇 자신의 전송은 Event와 기억 근거로 저장하되 자기 답변을 예약하지 않는다. 중복 수신·실제 내용 변화가 없는 업데이트는 타이머를 초기화하지 않는다. 과거 메시지 변경은 저장·기억 처리 대상이어도 무조건 답변을 예약하지 않으며, 재생성에 따른 삭제는 재생성 작업과 중복 예약하지 않는다.

진행 중인 생성에 영향을 주는 생성·수정·삭제는 기존 취소·재예약 흐름과 연결한다. 생성에 사용한 정확한 Event 목록과 범위 끝을 기록하고 도중에 도착한 Event는 다음 실행에 남긴다. 이미 전달한 봇 발언과 수신한 경험은 생성 실패·취소로 제거하지 않는다. 마지막 사용자 메시지가 삭제되어도 즉시 인지한 경험은 유지한다. 답변 예약 타이머와 §8.1의 기억 추출 타이머는 별개다.

현재 범위에서 제외된 과거 Events는 일반 CHAT에 원문으로 재주입하지 않고 Fact·Episode로 회상한다. FactEvidence·EpisodeEvidence 참조는 재검토용이며 과거 원문을 자동으로 가져오는 경로가 아니다. 오래된 메시지에 새 수정 Event가 오더라도 과거 대화 전체를 다시 불러오지 않는다.

현재 범위의 구체적인 제외 기준과 토큰 예산은 컨텍스트 구현 전 확정할 미결 항목이다. 기존 메시지 개수 제한을 Event 개수 제한으로 그대로 바꾸지 않는다. 확정할 규칙은 다음을 만족해야 한다.

- 현재 범위 시작, CHAT에 반영한 범위, 기억 추출 완료 위치를 구분한다. 추출 완료만으로 진행 중인 원문을 즉시 제외하지 않는다.
- 과거로 넘길 범위는 기억 가공 완료 후 제외한다. 기억할 항목이 없는 빈 결과도 정상 완료다.
- 기억 가공 실패나 입력 초과 시 미처리 경험을 조용히 버리지 않는다. 예산 조정 또는 명시적 재시도·실패로 처리한다.
- 수정·삭제 대상이 현재 범위 밖에 있어도 새 변화의 의미를 해석할 수 있게 하되, 과거 원문 참조만으로 현재 범위를 다시 넓히지 않는다.

## 7. 논리 데이터 모델

아래는 새 저장 계약이다. 기존 Memory 필드에 맞춰 요구사항을 줄이지 않는다. 실제 Prisma 모델·관계·인덱스는 §14의 해당 저장소 구현 단계에서 검증한다.

| 모델                  | 필요한 정보                                                                                                                                                                                                                                                                    | 이유                                                  |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------- |
| User 확장             | 선택적 고유 characterId                                                                                                                                                                                                                                                        | 같은 캐릭터의 provider 계정을 공통 참여자로 연결      |
| Events                | id, characterId, channelId, authorId(User, 미확인 시 없음), platformAccountId, kind(CREATE/UPDATE/DELETE), eventKey, 본문, 플랫폼 원본 식별자, messageRevision, previousEventId, receivedAt, 플랫폼 발생 시각(알 수 있는 경우), origin, reason, generationId, ACTIVE/RETRACTED | Message와 독립된 관찰 순서·본문 버전·기억 근거        |

| FactEvidence          | factId, eventId, 근거 역할                                                                                                                                                                                                                                                     | Fact와 Event의 FK 연결, 복수 출처와 철회 영향 조회    |
| EpisodeEvidence       | episodeId, eventId, 근거 역할                                                                                                                                                                                                                                                  | Episode와 Event의 FK 연결, 복수 출처와 철회 영향 조회 |

현재 컨텍스트 시작 위치와 CHAT 반영 위치는 기억 추출의 lastEventId와 별개로 저장한다. 구체적인 필드 위치는 §6.3의 범위 정책 확정 시 정하며, 별도 인지 시점 모델을 추가하지 않는다.

Fact와 Episode 각각에 embeddingJson, embeddingModel, embeddingDimension, embeddingContentRevision을 선택 필드로 둔다. 임베딩이 없어도 본문 기억은 유효하다. 벡터는 다시 만들 수 있는 검색용 데이터다.

저장 규칙:

1. Fact의 subjectId는 필수다. Episode는 참여자 목록을 가지며 subjectId는 선택한다. 모두 같은 서비스로 처리한다.
2. Fact의 factKey는 같은 속성의 재확인·명시적 정정 대상을 조회하기 위한 것이다. 기억 간 충돌 탐지에는 사용하지 않는다. 초기 공통 키는 residence, allergy:<대상>, preference:<대상>처럼 좁게 시작한다. 키 일치나 문자열 일치만으로 의미 중복 해결을 보장하지 않는다.
3. 알레르기·취향처럼 여러 값이 가능한 속성을 거주지처럼 한 칸에 덮어쓰지 않는다.
4. Fact와 Episode의 상태는 ACTIVE, SUPERSEDED(명시적 정정·변화에 따른 대체), INVALIDATED(근거 철회·설정 충돌)로 제한한다. 기억 간 충돌 집합과 DISPUTED 상태는 도입하지 않는다. ACTIVE만 기본 검색에 사용한다.
5. Fact의 coreReason은 NONE, HEALTH_CONSTRAINT, SELF_SETTING이다. 중요도 점수만 높다고 핵심 기억으로 승격하지 않는다.
6. FactEvidence의 (factId, eventId), EpisodeEvidence의 (episodeId, eventId)는 각각 고유하다. 각 기억 테이블의 (extractionGenerationId, candidateIndex)도 고유하며, 저장된 추출 결과의 후보 종류는 재시도 중 바꾸지 않는다. 재시도의 중복 적용을 막는다.
7. Events의 eventKey는 중복 수신·저장 재시도를 식별한다. 메시지 ID·본문 해시만으로 모든 이력을 중복 판정하지 않는다. A → B → A 수정은 별개 변화로 남겨야 한다. 채널 내 적용 순서와 메시지 버전을 함께 관리한다.
8. 처리 순서는 시간 대신 저장 ID를 쓴다. 스냅샷의 정확한 ID 목록을 기록하고 읽은 범위 끝까지만 처리 위치를 전진시킨다. 철회돼 제외한 항목도 처리한 범위에 포함한다.
9. 과거 Event 철회는 처리 위치를 되돌리지 않고 repairRequired로 재검토한다. 신규 ID 처리만으로 철회를 발견하려 하지 않는다.
10. 단일 대상·출처는 FK로 연결한다. 작은 복합 출력·벡터·참여자 목록은 검증한 JSON 문자열로 저장하고, 참여자별 조회가 필요해지면 관계 테이블로 전환한다.

Events는 현재 대화의 순서와 삭제 후 근거를 유지하고, FactEvidence·EpisodeEvidence는 Event와 기억을 연결해 철회 영향을 추적한다. MemorySource나 그 본문 복제 저장소는 추가하지 않는다. 별도 Conversation, ReviewWindow, BotMemory, Summary 모델은 추가하지 않는다.

## 8. 추출과 기억 갱신

### 8.1 실행 시점과 입력

새 Event가 생기면 기억 처리를 예약한다. 초기값은 30초 유휴, 최초 미처리 인지 후 5분 경과, 새 입력 4,000토큰 도달 중 하나를 만족하면 실행한다. 의미상 경계를 판정하는 값이 아니다. 다음 CHAT에서 필요하면 유휴 시간을 기다리지 않고 미처리 자료를 먼저 반영한다.

- 호출당 새 입력 최대 4,000토큰, 이전 발언 참고 최대 2,000토큰으로 시작한다. 설정·기존 기억·출력 공간을 포함해 모델 한도 내에서 조정한다.
- 긴 단일 발언은 eventId와 본문 위치를 유지하며 나눈다. 모든 조각 처리 전 해당 eventId를 완료로 넘기지 않는다. 재시작 가능한 조각 진행 정보를 실행 입력에 기록한다.
- 이전 참고 발언은 신규 추출 대상이 아니다. 일반 신규·갱신에는 새 근거가 하나 이상 필요하다. 철회 복구는 별도 작업으로 구분한다. 이 원문 참조는 기억 추출·재검토 전용이며 과거 원문을 일반 CHAT에 제공하는 허용이 아니다.
- 정확한 원본 목록, 내용, 상태, 설정 버전, 비교할 기억 revision을 고정한다.
- 같은 대상의 같은 Fact 키, 관련 경험, 현재 자기 설정을 함께 제공한다. 기존 기억 자체는 새 사실의 근거로 삼지 않는다.

### 8.2 출력과 검증

모델 출력은 Fact 후보와 Episode 후보를 구분하며 subject/participants, content, Fact의 factKey/value, evidenceIndexes, assertionType, 기존 기억에 대한 제안 동작을 포함한다. 후보 구분은 저장할 테이블을 선택하기 위한 것이며 공통 Memory 테이블의 kind 필드가 아니다. assertionType은 자기 진술·타인 보고·추측 등 근거의 성격을 구분한다.

모델이 반환한 내부 ID·scope·갱신 명령을 그대로 실행하지 않는다. 최소 검증:

- 대상과 근거가 입력 목록 안에 있고, 상태가 유효하다.
- 후보 수·본문 길이·날짜·키·enum이 제한을 만족한다. 초기 상한은 후보 30개, 본문 각각 1,000자다.
- Fact는 근거에 없는 세부 내용을 추가하지 않고 자기 진술·인용·가정을 구분한다.
- 자기 설정은 작성자와 대상이 같은지 확인한다. 범위는 모델이 임의로 승격하지 않고 §17에서 확정할 정책을 따른다.
- 기존 기억 변경은 같은 대상의 제공된 기억만 참조한다. 범위가 다른 근거·기억을 연결할 수 있는 조건은 §17에서 확정한다.

형식 검증은 의미 정확성을 보장하지 않는다. 근거와 후보를 대조하는 모델 검사 및 품질 사례로 오귀속·추가 창작을 검증한다. 경계 판정까지 한 호출에 넣지는 않는다.

### 8.3 갱신 규칙

| 상황                            | 처리                                                                               |
| ------------------------------- | ---------------------------------------------------------------------------------- |
| 같은 사실 재확인                | 근거 추가, lastConfirmedAt 갱신. 동의어마다 새 행을 만들지 않는다.                 |
| 명시적 정정                     | 기존 기억 SUPERSEDED, 새 기억 저장. 대체 관계와 근거 보존.                         |
| 실제 시간 변화                  | 과거 사실과 현재 사실 구분. 이사 같은 변화 근거가 있어야 한다.                     |
| 봇 초안이 기존 자기 설정과 충돌 | 전송 전 점검에서 초안을 수정한다. 기존 기억을 초안에 맞추지 않는다.                |
| 불확실한 타인 주장              | 확인된 Fact로 승격하지 않는다. 필요하면 “누가 그렇게 말했다”는 Episode로 보존한다. |

서로 다른 기억 사이의 모순 탐지·충돌 집합 생성·우선순위 판정·자동 해결·확인 질문은 이번 구현에서 다루지 않는다. 신규 후보와 기존 기억 사이의 충돌 검사도 포함하지 않는다. 위의 명시적 정정·변화, identity 변경 검사, 근거 철회와 전송 전 초안 점검은 유지한다. 모순된 기억이 함께 저장·검색될 수 있다는 한계는 남으며 이를 해결하는 기능을 완료 기준으로 삼지 않는다.

대체 관계는 Fact와 Episode 각각의 선택적 supersedesId로 같은 테이블 안에서 기록한다. 오래됐다는 이유만으로 알레르기나 자기 설정을 삭제하지 않는다. 일시적인 계획은 시점을 보존하고 현재도 유효하다고 추측하지 않는다.

## 9. CHAT 연결과 새 자기 설정의 일관성

흐름:

1. 수신 시 상대 발언·변화를 Events로 보존하고, 현재 대화에 해당하는 입력으로 Buffer의 답변을 예약한다.
2. 현재 identity, 핵심 기억, 관련 기억을 불러온다.
3. 현재 범위의 Events를 순서대로 조립하고 Fact·Episode와 함께 CHAT을 생성한다. Message의 최신 내역이나 과거 Events 원문을 자동으로 추가하지 않는다.
4. 기존 자기 설정·중요 제약과 초안의 명시적 충돌을 전송 전에 점검한다.
5. 실제 전달된 봇 발언의 근거를 저장한다.
6. 새 자기 설정 등 기억을 추출·반영하고 다음 답변에서 재사용한다.

§17에서 확정할 공유 범위 안에서 두 provider의 자기 설정을 일관되게 유지하도록 MVP에서는 캐릭터별 CHAT 생성·전송을 프로세스 내부 큐로 직렬화한다. 메시지 수신은 계속 가능하고 다른 캐릭터는 따로 진행할 수 있다. 비용·지연보다 일관성을 우선하는 초기 선택이다.

다음 답변에서 사용할 수 있는 이전 출력의 미처리 기억 추출을 생성 전에 완료한다. provider·채널 간 대기 대상은 §17의 스코프 정책 확정 후 구체화한다. 예약 작업과 CHAT에서 요청한 즉시 처리는 같은 실행 소유자를 공유한다. CHAT 완료를 기다리는 작업을 해당 CHAT 안에서 다시 기다리는 순환 대기를 만들지 않는다.

추출이 실패하면 제한 시간 내 복구를 시도한다. 공유해야 할 자기 설정의 추출이 실패한 상태로 해당 범위에서 새 자기 설정을 만들게 하지 않고 해당 CHAT을 기술적 재시도 대상으로 둔다. 캐릭터가 “설정에 없어서 모른다”고 말하게 하는 해결책은 사용하지 않는다. 이로 인한 응답 지연과 실패 횟수는 측정한다.

전송 전 점검에는 현재 identity, 유지 중인 자기 설정, 핵심 제약과 초안을 제공한다. 새로운 자기 설정은 허용하고 기존 설정과의 충돌은 수정한다. 수정 재생성은 최대 한 번으로 제한한다. 계속 실패하면 자동 반복을 중단한다. 모델 점검은 절대적인 보장이 아니므로 반복 평가로 실패율을 측정한다.

## 10. 검색과 프롬프트 반영

### 10.1 두 검색 경로

- 핵심 기억: 허용 범위 안에서 Fact에 저장된 현재 참여자의 명시적 건강 제약과 현재 캐릭터의 유지 중인 기본 자기 설정을 직접 조회한다.
- 관련 기억: 현재 발언과 최근 몇 발언으로 Fact와 Episode를 각각 조회하고 후보를 합친다. 테이블이 다르면 같은 ID여도 별개 기억이다.

핵심 기억을 중요도 상위 N개로 자르지 않는다. 초기 예산은 2,000토큰이며 초과하면 항목 손실 없이 표현을 압축한다. 그래도 넘으면 입력 예산 재배분 또는 명시적 작업 실패로 처리한다. 필수 제약을 조용히 누락하지 않는다. 모든 경험·취향을 핵심으로 분류하지 않는다.

### 10.2 의미 검색과 단어 검색

임베딩은 의미 검색에 사용하는 숫자 배열이다. Fact·Episode의 내용·대상·시간을 일정한 형식으로 변환해 저장한다.

- 허용 범위의 ACTIVE 기억을 페이지 단위로 읽어 애플리케이션에서 벡터를 비교한다. 최근 일부만 잘라 네 달 전 기록을 후보에서 제거하지 않는다.
- 같은 모델·차원의 벡터끼리 비교한다. 모델 변경 시 재생성하고 서로 다른 모델 벡터를 섞지 않는다.
- 이름·장소·표현 일치에 대한 단어 검색 후보도 합친다. 한국어를 공백으로 나누는 것만으로 검색 품질을 보장하지 않는다.
- 각 경로 후보 상한은 초기 30개다. 중복 제거 후 관련성을 재평가하고 최종 관련 기억 예산 3,000토큰 안에서 선택한다.
- “그때”, “지난번 여행”은 현재 범위 Events로 질의를 보완한다. 질의 확장이 새 기억을 만들지는 않는다.
- 임베딩 생성 실패 시 기억 본문은 유지하고 단어 검색을 사용한다. 벡터 생성은 별도로 재시도한다.
- embeddingContentRevision과 본문 revision이 다르면 벡터를 사용하지 않는다. 오래된 임베딩 콜백이 새 본문에 결과를 덮어쓰지 않게 한다.

### 10.3 실제 입력과 답변

identity 및 운영 지시, 유효 기억, 현재 범위 Events의 발언·변화 관찰을 구분한다. 기억을 발언자가 방금 말한 새 메시지나 시스템 명령으로 위장하지 않는다. 기억 안의 지시문을 실행하지 않는 규칙을 시스템 지시에 둔다.

기억에는 대상·내용·시점·출처 성격을 포함한다. 철회·대체 상태는 기본 입력에서 제외한다. 서로 다른 기억 간 충돌을 별도로 판정하거나 검색 결과에서 해소하지 않는다. 지금 사용자의 명시적 정정은 저장 전이라도 이전 기억보다 우선하도록 문맥을 제공한다.

사용한 Event ID 목록·범위와 기억 종류(Fact/Episode)·ID·revision, 검색 질의·경로·선택 이유를 CHAT Generation metadata에 기록한다. 관련 없는 과거 정보를 매번 억지로 언급하는 것도 품질 실패다.

벡터 검색만으로 필수 기억 반영을 보장하지 않는다. 땅콩 알레르기 사례는 핵심 조회·실제 입력·전송 전 점검·최종 답변까지 연결해 검사한다.

### 10.4 회상과 원문 조회·인용

일반 답변의 과거 회상은 Fact·Episode로 처리한다. 명시적인 원문 조회·인용은 현재 Message를 사용하며 삭제된 행은 조회되지 않는다. Events의 구버전 본문이나 Generation 실행 로그를 대신 검색해 삭제된 메시지를 찾아 주지 않는다. Events 원문 보존과 AI에게 과거 원문을 제공하는 것은 별개다. 플랫폼 재동기화·인용 직전 원격 재검증은 이번에 구현하지 않는다.

## 11. 저장·재시도·재시작

기억 처리 담당 작업은 container에서 프로세스당 하나만 만든다. worker는 이 백그라운드 작업을 뜻하며 별도 서버가 아니다. provider마다 중복 생성하지 않는다.

처리 순서:

1. 처리 상태와 입력 목록을 읽고 MEMORY_EXTRACT Generation에 고정 입력을 저장한다.
2. AI 호출과 검증은 DB 트랜잭션 밖에서 수행한다.
3. 검증된 출력을 실행 기록에 저장한다. 아직 Fact·Episode 적용 완료는 아니다.
4. 짧은 트랜잭션에서 처리 revision, 근거 상태, 기존 기억 revision, 설정 버전을 재확인한다.
5. Fact·Episode·FactEvidence·EpisodeEvidence·대체 상태·처리 위치·Generation COMPLETED를 함께 저장한다.
6. 임베딩은 본문 저장과 분리하고 해당 본문 revision에만 연결한다.

새 Event는 다음 처리에 남는다. 철회나 설정 변경이 끼어들면 오래된 결과를 적용하지 않고 재구성한다. 동일 결과 재적용 여부는 실행 ID로 확인한다. DB 충돌 재시도에서 읽었던 전제가 달라지면 무조건 덮어쓰지 않는다.

AI·임베딩 호출과 벡터 비교를 SQLite 트랜잭션 안에 넣지 않는다. 입력 묶음과 저장량을 제한해 채팅 메시지 쓰기를 오래 막지 않는다.

실패 정책:

- 호출 제한 시간 초기값 60초. 실패 후 자동 재시도는 1분·5분·15분의 최대 3회, 이후 paused로 두고 명시적인 재시도를 제공한다.
- 입력 초과·모델 거부·반복 형식 오류·네트워크·DB 오류를 구분한다. 입력 초과는 크기 조정으로 처리한다.
- 검증 출력이 저장돼 있고 전제가 유효하면 DB 적용만 다시 시도한다. AI를 재호출하지 않는다.
- 후보 수 초과를 조용히 잘라 성공 처리하지 않는다. 입력 분할 또는 명시적인 실패로 처리한다.
- 예약 작업은 실패한 채널을 건너뛰어 다른 채널을 계속 처리한다. 다음 답변과 기억을 공유하는 범위에 미처리 출력이 있으면 §9의 CHAT 일관성 제한은 적용한다. 공유 범위는 §17에서 확정한다.

시작·종료:

- 시작 시 미완료 실행을 조회한다. 검증 출력이 있으면 적용 복구, 없으면 중단된 시도를 종료 처리하고 새 시도를 만든다. claim 만료를 기다리지 않는다.
- 종료 시 새 CHAT·기억 작업 접수를 멈추고 진행 중 호출에 abort를 전달한다. 정리 대기는 기본 10초다.
- 성공 적용·취소 모두 현재 실행 상태를 조건으로 갱신한다. COMPLETED를 뒤늦게 CANCELLED로 바꾸지 않는다.
- 늦게 도착한 콜백은 실행 ID·현재 상태를 검증한다. 종료·시간 초과 후 새 시도의 상태를 덮어쓰지 않는다.
- 상태 저장 시도 후 DB를 닫는다. 강제 종료 후 재처리가 가능해야 한다.

## 12. 오류 수정과 재처리

Fact·Episode는 수정 가능한 결과이고 Events는 근거다. 잘못된 기억은 원본에서 다시 만들 수 있어야 한다.

| 변경                    | 복구                                                           |
| ----------------------- | -------------------------------------------------------------- |
| 특정 Event 철회         | 관련 기억 즉시 제외, 유효 근거로 재검토                        |
| 특정 Fact·Episode 오류  | 결과 제외, 해당 근거 재추출, 수정 사유 기록                    |
| 추출 모델·프롬프트 변경 | 새 버전 기록, 지정 범위 재처리. 무조건 전량 자동 실행하지 않음 |
| 임베딩 모델 변경        | 본문 유지, 벡터만 재생성. 전환 중 핵심 조회·단어 검색 유지     |
| identity 변경           | §4.3의 설정 충돌 검사·버전 확인                                |

관리자용 실행 함수 또는 CLI로 범위 재처리, paused 재시도, 근거 철회를 제공한다. 관리자 UI나 결과 버전 비교 화면은 만들지 않는다.

범위 재구축은 해당 범위의 관련 결과를 일시 제외하고 원본 순서대로 다시 만드는 유지보수 작업으로 시작한다. 실패하면 불완전 상태를 완료로 노출하지 않는다. 기존 기억을 참조한 다른 기억의 근거 목록도 실제 Event로 유지해, 폐기된 요약만을 근거로 다시 살아나는 일을 막는다.

신규 책임:

- EventRepository: 발언·변화 저장, 순서·버전·중복 방지, 현재 범위 조회와 근거 철회.
- FactRepository, EpisodeRepository: 각 기억 테이블의 근거 연결·상태·벡터 및 조건부 적용. 두 저장소의 결과는 공통 서비스에서 조정한다.
- MemoryExtractor: 공통 참여자 발언에서 후보 추출·검증.
- MemoryService: 재확인·명시적 정정·갱신·복구 조정. 기억 간 충돌 해결은 제외한다.
- MemoryRetriever: 핵심 조회·단어/의미 검색·입력 구성.
- MemoryWorker: 예약·재시도·중단. 의미상 대화 경계는 판단하지 않음.

기존 메모리 호출은 구현 시 확인해 새 흐름으로 교체한다. 이중 추출·이중 주입을 막되 기존 API 유지 자체를 목표로 삼지 않는다. 이번 기능과 무관한 ConversationBuffer 등의 용어 변경은 하지 않는다.

## 15. 테스트·운영·완료 기준

### 제품 품질 사례

1. 네 달 전 땅콩 알레르기를 최근 문맥에서 제거한 뒤 샌드위치 질문에 반영한다.
2. 지난봄 여행 경험을 표현이 다른 질문으로 찾는다.
3. identity에 없는 거주지는 새로 만들 수 있고 이후 다른 지역으로 바꾸지 않는다.
4. identity에 있는 거주지는 즉석 설정으로 덮어쓰지 않는다.
5. identity 변경 후 기존 거주지를 현재로 사용하거나 가상의 이사를 만들지 않는다.
6. 자기 진술·친구 이야기·가정을 구분한다. 작성자가 봇이어도 동일하다.
7. 명시적 정정은 반영한다. 서로 다른 기억 간 모순의 탐지·해결은 평가 범위에서 제외한다.
8. 재생성으로 폐기한 설정·약속이 새 답변에 다시 등장하지 않는다.
9. `/활성화`의 스코프와 §17에서 확정한 정책에 따라 Fact·Episode의 저장·검색 범위를 검증한다. 구체적인 채널 간 허용·차단 사례는 정책 확정 후 작성한다.
10. n:1 입력에서 대상이 섞이지 않는다. 모호하면 기억을 만들지 않는다.
11. 기억 안의 지시문을 운영 명령으로 실행하지 않는다.
12. 관련 없는 옛 이야기를 매번 억지로 꺼내지 않는다.
13. “세 시 제안 → 봇 동의 → 네 시로 수정”을 현재 Events 순서대로 전달하고 현재 약속만 정정한다.
14. 첫 Buffer 실행 전 수신·수정·삭제된 발언도 즉시 인지 정책에 따라 경험을 유지한다.
15. 일반 삭제 뒤 기억은 유지하되 약속 취소나 삭제 의도를 단정하지 않는다.
16. 과거 구간의 Events 원문을 CHAT에서 제거한 상태로 Fact·Episode만으로 회상한다. 삭제 원문은 Message 검색과 Events 우회 검색으로 다시 제공하지 않는다.
17. 기억 가공 실패 시 현재 범위를 조용히 잘라 경험을 잃지 않는다.

### 저장·동시성 테스트

- 고정 입력 처리 중 새 Event가 도착해도 CHAT 반영·기억 처리 완료로 잘못 표시되지 않는다.
- 생성·수정·삭제의 Message 변경과 Event 저장 중 하나가 실패하면 함께 롤백한다.
- 같은 채널에서 생성·수정·삭제가 타임아웃 내 연속 발생하면 마지막 답변 예약 대상 이벤트부터 타이머가 다시 시작된다.
- 봇 자신의 전송·중복 수신·내용 변화 없는 업데이트·재생성 삭제가 답변을 중복 예약하지 않는다.
- Fact와 Episode의 ID가 같아도 검색 결과·근거 철회·Generation 기록에서 혼동하지 않는다.
- 명령/Gateway 중복 삭제, 일괄 삭제, 부분 업데이트, 이전 본문 미확인을 처리한다.
- A → B → A 수정 순서를 보존하고 늦은 갱신으로 삭제 메시지를 되살리지 않는다.
- 생성 도중 수정·삭제를 반영해 재예약하고 이미 수신·전송한 경험을 보존한다.
- 재생성 삭제 이벤트가 철회된 봇 발언을 현재 문맥·기억에 다시 넣지 않는다.
- 원본 재조회·결과 저장 재시도에서 중복이 없다.
- 철회·설정 변경과 추출이 겹쳐도 오래된 결과가 부활하지 않는다.
- 재생성·일반 삭제·부분 전송 취소를 구분한다.
- 같은 캐릭터의 계정 초기화 경쟁에서 서로 다른 공통 참여자가 생기지 않는다.
- §17에서 자기 설정을 공유하기로 확정한 범위의 동시 provider 질문에서 최초 설정의 일관성을 검증한다. 이미 저장된 서로 다른 기억의 충돌 해결을 뜻하지 않는다.
- DB 실패 후 AI 재호출 없이 검증 출력을 적용한다.
- 성공 저장과 종료 경쟁에서 COMPLETED를 CANCELLED로 바꾸지 않는다.
- 임베딩 생성 중 본문 변경 시 오래된 벡터를 적용하지 않는다.
- 재시작·긴 단일 발언 분할·반복 오류에서도 누락과 무한 반복이 없다.

저장·상태 전이는 node:test와 주입 모델로 검증한다. 실제 모델 평가는 별도 명령으로 실행한다. 기본 npm test에 키가 필요한 네트워크 호출을 섞지 않는다.

초기 평가셋은 30개 이상이며 알레르기·자기 설정·재생성·대상 오귀속 사례를 포함한다. 중요 사례는 같은 입력으로 5회 반복하고 한 번이라도 필수 제약 누락·오귀속·철회 내용 부활이 나오면 통과로 보지 않는다. 일반 경험 검색은 기대 기억의 최종 후보 포함률 90% 이상을 초기 목표로 삼고 최종 답변 적절성도 따로 평가한다. 고정 평가셋 통과를 실제 모든 대화의 보장으로 표현하지 않는다.

### 최소 운영 지표

- 가장 오래된 미처리 근거의 나이, 미처리 입력량, paused 수.
- 호출 모델·프롬프트·설정 버전, 토큰·비용·지연·실패·재시도.
- 후보 채택·거부·명시적 대체 수, 자기 설정 생성·전송 전 초안 충돌 수. 기억 간 충돌 지표는 제외한다.
- 검색 후보·사용 기억 종류(Fact/Episode)·ID, 검색 경로, 벡터 미생성·버전 불일치 수.
- 필수 기억 누락, 대상 오귀속, 철회 기억 부활, 불필요한 회상.
- 전송 후 저장 실패, 재시작 복구 실패, 수동 재처리 필요 건수.

일반 로그에 원문을 반복하지 않고 식별자로 실행·근거 기록을 연결한다. 근거 삭제·보관 기간 변경은 재생성 능력에 영향을 주므로 별도 데이터 관리 정책으로 다룬다.

완료 조건은 테이블 생성이나 검색 성공이 아니다. 봇과 사용자 공통 처리, 실제 전달된 자기 설정 유지, 오래된 사실·경험의 답변 반영, 설정·정정·재생성 우선순위, 캐시 삭제와 근거 보존, 단일 프로세스 동시 provider와 재시작 복구를 모두 검증한다. 관련 단위 테스트·전체 npm test·별도 모델 평가 결과와 남은 한계를 기록한다.

## 16. 이후로 미루는 범위

- 의미상 Conversation 재분할·병합, Pending, mustFinalize.
- 여러 애플리케이션 프로세스와 분산 worker.
- 별도 벡터DB 운영과 대규모 검색 최적화.
- n:1의 복잡한 제삼자 관계 추론. 채널 간 기억 공유 범위는 §17 확정 후 `/활성화` 설정에 따라 구현한다.
- 서로 다른 기억 간 충돌 탐지·해결, 충돌 집합·DISPUTED 상태·자동 확인 질문.
- 사용자 계정 자동 매칭, 과거 기록 전체의 자동 역산.
- 관리자 UI, 결과 버전 비교 화면, 자동 identity.md 편집.
- 플랫폼 전체 아카이브, 연결 중단 중 놓친 변경의 재동기화·완전 복제 보장. 현재 수신하는 수정·삭제 이벤트 처리는 MVP에 포함한다.
- 읽는 시점 변경, 잠수·지연 인지·읽음 상태 모델.

초기 과거 자료는 자동으로 인지한 것으로 만들지 않는다. 실제 인지 범위를 증명할 수 있는 자료 또는 별도로 선택한 가져오기 범위만 가져오기 출처를 표시한 Events로 변환한다. 과거 자료는 현재 CHAT 원문으로 주입하지 않는다. 네 달 전 장기 회상 평가는 명시적인 테스트 자료로 주입한다.

## 17. 구현 전에 확정해야 하지만 아직 미정인 부분

### 스코프의 구체적인 의미와 적용 규칙

`/활성화`에서 선택한 `global`, `server`, `channel`을 따른다는 원칙만 확정됐다. 아래 항목은 제안이나 기본값을 확정 정책으로 간주하지 않으며, 관련 스키마·추출·검색 구현 전에 결정한다.

| 미정 항목               | 확정할 내용                                                                                                                                      |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| GLOBAL의 경계           | 같은 캐릭터의 모든 채널·provider 범위인지, 캐릭터 간에도 공유하는 의미인지. characterId와 scope의 관계                                           |
| 읽기와 쓰기             | 획득한 기억이 사용될 범위만 정하는지, 해당 채널이 외부 기억을 읽는 범위도 제한하는지. CHANNEL 채널에서 GLOBAL 기억을 읽을 수 있는지              |
| SERVER와 서버 없는 채널 | 서버 경계의 식별 방법, DM·CLI 등 서버가 없는 채널의 설정·조회 규칙                                                                               |
| 사용자 기억 공유        | 같은 User의 다른 채널·provider에서 무엇을 사용할 수 있는지, 다인 대화에서 대상·참여자 조건을 어떻게 적용할지                                     |
| 자기 설정               | 대화에서 만든 자기 설정도 획득 채널의 범위를 그대로 따르는지, 명시적인 공유 정책이 필요한지. 별도 CHARACTER 스코프는 현재 확정안에 포함하지 않음 |
| 설정 변경과 과거 자료   | 스코프 변경이 기존 Event·Fact·Episode에도 적용되는지, 새 자료부터 적용되는지. 과거 자료 가져오기 범위                                            |
| 범위 저장 시점          | 획득 당시 설정을 Event에 보존할지, 추출·조회 시 설정을 적용할지. 재시도·재처리 중 설정이 바뀐 경우의 처리                                        |
| 서로 다른 범위의 근거   | 재확인·명시적 정정에 서로 다른 범위의 근거를 사용할 수 있는지, 그 결과의 범위는 무엇인지. 기억 내용 간 충돌 해결은 이번 범위에서 제외            |
| 저장·검색·동시성 계약   | scopeKey와 필요한 필드·조회 조건, 허용·차단 평가 사례, §9의 공유 자기 설정에 대한 추출 대기 범위                                                 |

이 항목을 확정하기 전에는 기존의 CHANNEL 고정·CHARACTER 자동 공유 정책이나 특정 GLOBAL 해석을 구현의 기본값으로 사용하지 않는다.
