# 운영

일반 로그는 프로세스 stdout/stderr로, 입력·출력과 API 메타데이터는 DB의 `Generation`으로 확인한다. 먼저 캐릭터와 채널을 특정한 뒤 생성 단계를 따라가면 된다.

## 실행과 종료

로컬 실행은 [시작하기](시작하기.md)를 따른다. 운영 환경에서 PM2를 사용한다면 별도로 설치한 뒤 저장소 루트에서 실행한다.

```powershell
pm2 startOrRestart ecosystem.config.cjs --only aimate
pm2 save
pm2 logs aimate
```

[ecosystem.config.cjs](../ecosystem.config.cjs)는 저장소 루트를 cwd로 사용해 Discord 진입점을 실행한다. 설정 목록의 모든 Discord 캐릭터가 대상이다.

| 종료·실패 | 동작 |
| --- | --- |
| 기동 설정 오류 | 종료 코드 `78`. PM2가 자동 재시작하지 않는다. 수정 후 `pm2 restart aimate`. |
| 일반 기동 실패 | 종료 코드 `1`. 사용 가능한 연결이 하나도 없으면 전체 기동에 실패한다. |
| 일부 캐릭터·연결 실패 | 다른 연결은 계속 실행한다. `character.start.failed`, `connection.start.failed` 확인. |
| SIGINT·SIGTERM | 입력과 타이머를 닫고 생성 취소·진행 작업 정리·연결 종료 후 공통 DB를 닫는다. |

PM2 재시도 간격은 5초다. `min_uptime: 30000`, `max_restarts: 5`는 짧게 실패하는 실행을 제한하며, 전체 누적 재시작 횟수 제한은 아니다. 강제 종료 후 남은 진행 상태를 자동 복구하는 worker는 없다.

## 대화 정책

Discord는 채널 → 카테고리 → 서버 → 기본 거부 순으로 판정한다. 스레드는 부모 채널의 정책을 따른다. 정책은 캐릭터별이므로 명령을 실행할 봇도 확인한다. 현재 정책 유형은 `대화`다.

```text
/정책 설정 유형:대화 상태:허용
/정책 설정 유형:대화 상태:허용 범위:서버
/정책 설정 유형:대화 상태:거부 기간:1
/정책 설정 유형:대화 상태:상속
/정책 상태 유형:대화
```

기간은 1·3·6·12·24시간 중에서 고른다. 임시 설정은 만료 뒤 원래 기본 설정이나 상속으로 돌아간다. `상속`은 그 범위의 기본·임시 설정을 지운다. 서버 설정을 바꿔도 개별 채널·카테고리 설정은 유지된다.

`/정책`은 서버 관리 권한이 필요하다. Discord 서버 대화 정책은 서버 위치를 기준으로 한다. 1:1 DM 대화는 `features.enableDM: true`일 때 허용한다. 그룹 DM은 차단한다. DM 설정은 캐릭터별로 덮어쓸 수 있으며 재시작 후 적용된다. CLI는 새 채널을 만들 때 해당 캐릭터의 허용 정책을 함께 저장한다.

정책 거부·만료는 대기 중인 응답과 진행 생성을 중단한다. 로그 전용 채널은 대화 허용보다 우선해 제외한다. 구현은 [DiscordPolicyService.js](../src/platforms/discord/policy/DiscordPolicyService.js), 판정 함수는 [Policy.js](../src/policies/Policy.js)에 있다.

## Discord에서 생성 로그 보기

서버 관리자가 로그를 받을 채널에서 실행한다.

```text
/로그 채널 상태:활성화
/로그 채널 상태:비활성화
```

`대상`으로 다른 텍스트·공지 채널을 선택할 수 있다. 봇에는 해당 채널의 보기·전송·링크 임베드 권한이 필요하다.

로그 카드는 대기 입력부터 생성 완료·실패까지 갱신한다. `API 요청 전문`, `API 응답 전문` 버튼은 저장된 데이터를 txt 첨부로 제공하며 클릭한 사용자에게만 보인다. 요청 전문에는 system prompt와 대화 문맥이 포함될 수 있으므로 로그 채널의 열람 권한을 정해둔다.

구독은 `LogSubscription(characterId, channelId)`에 저장되어 재시작 후에도 유지된다. 어느 캐릭터든 구독한 로그 채널은 모든 캐릭터의 대화·관찰에서 제외한다. 카드 ID와 대기 묶음은 메모리에 있어 재시작 후 기존 카드를 이어 수정하지 않는다.

카드 동기화는 1초 주기 조회와 생성·메시지 변경 알림을 사용한다. 일반 채팅 처리에서 로그 카드 전송 완료를 기다리지 않는다. 구현은 [DiscordLogService.js](../src/platforms/discord/logging/DiscordLogService.js), 조회는 [DiscordLogRepository.js](../src/platforms/discord/logging/DiscordLogRepository.js), 표시는 [logEmbeds.js](../src/platforms/discord/logging/logEmbeds.js)다.

Decision 모드에서는 `Generation.type: DECISION` 카드도 표시한다. API가 성공했어도 새 입력 등으로 결과를 폐기할 수 있으므로 카드의 `판단 적용`과 DB의 `metadata.application`을 함께 확인한다. 입력·응답과 상태 계약은 [응답 판단](응답%20판단.md#관찰과-처리-위치)에 있다. `decision.persistence.failed`는 판단 결과의 DB 저장에 실패했다는 뜻이다.

## 일반 로그로 단계 좁히기

`logging.level: info`는 생애주기와 결과를, `debug`는 건너뜀 사유·버퍼·단계별 시간·전송 상세를 보여준다. CLI의 TTY 모드에서는 화면 보호를 위해 일반 로그를 출력하지 않는다.

같은 `characterId`, `platformChannelId` / `channelId`, `turnId`, `generationId`를 따라간다.

| 로그 | 확인할 것 |
| --- | --- |
| `message.skipped`, `message.processed` | 입력을 왜 건너뛰었거나 응답 대상으로 삼았는가. |
| `buffer.scheduled`, `buffer.fired` | 연속 입력 대기가 끝났는가. |
| `generation.started`, `generation.input.prepared` | 생성과 입력 준비가 시작됐는가. |
| `model.started`, `model.completed`, `tool.*` | 모델·도구의 결과와 실패 지점. |
| `message.send.completed`, `message.storage.failed` | 전송은 성공했지만 저장이 실패했는가. |
| `generation.completed`, `generation.cancelled`, `generation.failed` | 정상 완료·새 turn에 의한 취소·실패 중 무엇인가. |

생성 취소는 연속 입력을 반영하는 정상 동작일 수 있다. 상태별 의미와 원문·파싱 결과·실제 전송의 차이는 [데이터와 대화](데이터와%20대화.md#생성-기록을-읽는-방법)를 참고한다. Discord 메시지 메뉴의 `생성 정보 확인`으로 출력과 생성 ID를 연결할 수 있다.

## 증상별 확인

| 증상 | 먼저 확인할 것 |
| --- | --- |
| 코드 78로 시작 실패 | chat·image 인증/모델/팩, 캐릭터 목록과 `config.json`의 시간대, 토큰 이름. |
| 로그인했는데 무응답 | 해당 봇의 대화 정책, 로그 전용 채널 여부, Gateway intent와 채널 권한, 입력·버퍼 로그. |
| CLI에서 Discord 인증 오류 | 선택한 캐릭터의 `connections.discord`도 준비하는지 확인. CLI만 사용할 때는 `cli` 연결만 설정. |
| 첫 입력에서 파일 오류 | `chat/sequence.js`와 참조 파일, 캐릭터 identity 등 Git에서 제외된 콘텐츠. |
| 긴 대화에서 모델 오류 | 실제 Event 문맥 크기와 모델 한도. `maxContextMessages`가 자동 제한한다고 가정하지 않는다. |
| 응답 중간에 끊김 | 새 turn의 CANCELLED인지, 전송·저장 오류의 FAILED인지 확인. |
| 이미지가 안 보임 | IMAGE 생성 완료, `content/image/` 파일, 응답 태그와 첨부 권한. CLI는 첨부 미지원. |
| 모델이 말풍선을 나누지 않음 | API 응답에 `[BREAK]`가 있는지 → `Generation.output` 배열 → 실제 Message 순서. |
| 설정 변경 미반영 | [변경 적용 시점](설정과%20콘텐츠.md#변경-후-언제-반영되는가) 확인 후 재시작. |
| DB 테이블·필드 오류 | 앱을 종료하고 현재 스키마를 `npm run db:init`으로 적용. 개발 중 데이터 마이그레이션은 제공하지 않는다. |
| Prisma Client 생성에서 Windows `EPERM` | 실행 중 프로세스가 엔진 DLL을 사용 중인지 확인. 종료 후 `npm run db:generate`. |

플랫폼 전송 성공 후 DB 저장만 실패하면 저장을 한 번 재시도한다. 실패 원인을 조사할 때 전송 자체를 다시 호출하면 중복 메시지가 생길 수 있다. 자동 메시지·이미지 청소 기능은 없다.

일반 로그는 본문·프롬프트·도구 입출력을 통째로 출력하지 않으며 알려진 인증 필드를 마스킹한다. DB의 API 메타데이터 전체에 같은 제거 처리가 적용되는 것은 아니므로 전문을 공유할 때 필요한 부분만 추린다.
