# Discord 프로필·기능 권한 설계 검토

| 항목 | 내용 |
| ---- | ---- |
| 작성일·공식 문서 확인일 | 2026-09-14 |
| 상태 | 후속 설계 검토. 공식 API 지원 사실과 제품 정책 제안을 구분하며, 아래 추천안은 아직 확정하지 않았다. |
| 범위 | 서버·계정 프로필, 접속 상태, 기능 실행 권한, 거절 표현·시스템 안내 |
| 관련 문서 | [메모리 개발 계획 §17](conversation-episode-development-report.md#17-메모리-스코프의-확정-전제와-구현-전-미정-사항) |

현재 메모리 구현에 필요한 저장·추출·검색·컨텍스트 경계는 관련 문서 §17에서 관리한다. 이 문서의 프로필 편집·권한 검사·안내 UI 구현은 메모리 기능의 완료 조건이 아니다.

## 1. 공식 지원 재확인

**봇도 서버마다 다른 아바타·배너·소개를 유지할 수 있다.** Discord 공식 변경 이력은 2025년 9월 10일부터 봇이 Modify Current Member 경로로 `avatar`, `banner`, `bio`를 설정할 수 있다고 명시한다. 일반 사용자 전용 기능을 봇 기능으로 추정한 결론이 아니다. [Discord 공식 변경 이력](https://docs.discord.com/developers/change-log)

현재 Modify Current Member 명세에도 `nick`, `banner`, `avatar`, `bio`가 기재되어 있다. 서버 멤버를 수정하는 API이므로 서버 A의 프로필과 서버 B의 프로필을 각각 설정할 수 있다. [Discord Guild Resource](https://docs.discord.com/developers/resources/guild#modify-current-member)

| 대상 | 확인된 범위와 한계 |
| ---- | ------------------ |
| 서버별 아바타·배너·소개 | 해당 서버의 봇 멤버 프로필로 설정 가능. DM이나 다른 서버의 프로필 편집과 구분한다. |
| 서버별 닉네임 | Modify Current Member의 `nick`으로 설정하며 `CHANGE_NICKNAME` 권한이 명시되어 있다. |
| 계정 기본 아바타·배너 | Modify Current User의 계정 설정이다. 서버 프로필 변경과 다른 작업이다. |
| 온라인·방해금지·자리비움·오프라인 표시, 활동 | 서버 프로필 필드가 아니라 Gateway Update Presence로 변경한다. 이 전송 구조에는 대상 guild_id·channel_id가 없다. 서버별 프로필 지원을 서버별 접속 상태 지원으로 확대 해석하지 않는다. |
| 채널별 프로필 | 확인한 프로필 API는 계정 또는 서버 멤버를 대상으로 한다. 같은 서버 안의 채널마다 독립된 실제 봇 프로필을 설정하는 기능으로 사용할 수 없다. |
| 계정 전체 소개 | 서버별 bio와 구분해야 한다. Modify Current User에는 bio가 없으므로, 계정·애플리케이션 소개 중 실제 제품이 바꾸려는 필드와 지원 API를 구현 전에 별도로 확정한다. |

계정 기본 프로필은 [Modify Current User](https://docs.discord.com/developers/resources/user#modify-current-user), 접속 상태·활동은 [Update Presence](https://docs.discord.com/developers/events/gateway-events#update-presence)를 근거로 구분했다. Gateway 연결·샤딩별 동작을 임의의 서버별 프로필 설정과 동일하게 취급하지 않는다.

이번 확인은 공식 API 명세와 변경 이력의 대조다. 실제 봇 계정으로 프로필을 변경하는 실험은 하지 않았다. 이 프로젝트에 설치된 discord.js의 서버 프로필 편집 지원과 실제 표시 결과는 해당 기능 구현 단계에서 검증한다.

## 2. 공유 계정에서 남는 제품 제약

대화 기억을 스코프별로 격리하더라도 실제 Discord 계정이나 서버 프로필은 여러 대화에서 보일 수 있다. GLOBAL 대화에서만 계정 프로필 변경을 허용해도, 독립된 CHANNEL 대화에서는 변경 이유를 모르는 상황이 남는다. 서버 프로필 변경도 같은 서버의 독립된 CHANNEL 대화에 보일 수 있다.

추천안은 현재 확인 가능한 플랫폼 상태와 변경 경험을 분리하는 것이다. 다른 대화에서는 조회로 확인한 현재 프로필을 사용할 수 있지만, 그 이유·요청자·원래 대화까지 자동 공유하지 않는다. 현재 상태를 모든 대화에 자동 통지하는 기능을 뜻하지 않으며, 실제 입력 제공 방식은 후속 설계에서 정한다. 메모리 입력의 경계는 개발 계획 §17에서 관리한다.

이 방식은 외부 변화가 보인다는 한계를 수용한다. 외형과 접속 상태까지 완전히 독립시켜야 한다면 계정 분리 또는 공유 프로필 고정이 필요하다. 서버별 프로필은 서버 사이의 외형 차이를 지원하지만 채널별 격리를 완성하지는 않는다.

## 3. 기능 실행 권한: 제안

기능 이름이 아니라 실제 변경 대상과 영향 범위로 판단한다. 예를 들어 같은 “프사 변경”이라도 서버 프로필 변경과 계정 기본 프로필 변경을 구분한다.

| 실제 변경 대상 | 대화에서 허용할 범위 제안 |
| -------------- | ------------------------ |
| 현재 채널에 한정되는 작업 | 현재 대화가 속한 해당 채널 |
| 현재 서버의 프로필 | 해당 서버의 SERVER 대화 또는 GLOBAL 대화 |
| 계정 전체 프로필·현재 프로젝트의 접속 상태·활동 변경 | GLOBAL 대화 |

이 표는 스코프 조건만 표현한다. 요청자 권한, 운영자가 허용한 기능, 플랫폼의 실제 실행 권한도 충족해야 한다. GLOBAL 선택 자체로 계정 제어 권한을 부여하지 않으며, `/활성화` 설정 변경이 권한 우회 경로가 되지 않도록 한다.

플랫폼 어댑터가 실제 대상·영향 범위를 제공하고 공통 실행 계층이 허용 여부를 판단하는 구성을 추천한다. 모델에 사용할 수 있는 기능을 안내하는 것과 별개로, 실행 직전에도 현재 캐릭터·대상 계정·범위·권한을 검사한다. 채널에서 거절된 작업을 예약 작업으로 넘겨 실행하는 우회도 허용하지 않는다.

스코프를 잠시 GLOBAL로 바꿔 제한을 우회하는 흐름이나, 채널 요청을 자동으로 전역 요청으로 바꾸는 흐름은 추천하지 않는다. 운영자에 의한 별도 관리 기능을 제공할지는 후속 결정 사항이다.

현재 [setDiscordPresence.js](../src/tools/definitions/setDiscordPresence.js)는 `client.user.setStatus`, [setDiscordStatus.js](../src/tools/definitions/setDiscordStatus.js)는 `client.user.setActivity`를 사용한다. [ToolRegistry.js](../src/tools/ToolRegistry.js)는 활성화 여부·플랫폼·필수 자격증명으로 도구를 필터링하며 스코프 권한 검사는 아직 없다. 프로필 편집뿐 아니라 기존 상태 도구도 후속 권한 설계의 적용 대상이다.

메모리의 GLOBAL은 같은 캐릭터의 여러 provider를 아우르는 개념이고, Discord 계정 변경은 특정 플랫폼 계정에 대한 작업이다. 두 식별 범위를 같은 키나 권한으로 취급하지 않는다. 캐릭터 전환 또는 동시 요청 중 다른 캐릭터·계정의 작업을 실행하지 않는 검증도 필요하다.

## 4. 거절 표현과 시스템 안내: 제안

몰입형·명시형은 말투의 선택으로 제공하되 실행 결과와 차단 사유는 동일하게 유지한다. 몰입형에서도 정확한 사유를 확인할 수 있는 시스템 안내를 제공하는 방식을 추천한다.

| 표현 | 예시 |
| ---- | ---- |
| 몰입형 | “사진은 받았어. 다만 여기서는 내 프사로 바꿀 수 없어.” |
| 명시형 | “이 채널은 채널 스코프라 계정 전체에 적용되는 프로필 변경은 사용할 수 없어요.” |
| 시스템 상세 안내 | “실행되지 않음 · 이 작업은 Discord 계정 전체에 적용됩니다. 전역 대화에서 별도 변경 권한이 필요합니다.” |

정책에 의한 차단을 “서버 오류가 났나 봐” 같은 일시적 장애로 꾸미는 방식은 추천하지 않는다. 재시도를 유도하고 실제 원인을 이해하기 어렵게 한다. 기술 용어를 생략하되 시도·성공·장애 사실을 만들지 않는 편이 낫다. 실제 API 장애와 정책 차단은 구분한다.

일반 채팅 답변에 작은 `안내 보기` 버튼을 붙이고, 클릭한 사람에게만 비공개 응답으로 사유를 보여주는 구성을 추천한다. 슬래시 명령에서는 비공개 응답을 바로 사용할 수 있다. 모달은 interaction에 응답해 여는 UI이므로 일반 메시지 수신만으로 자동 표시하는 흐름으로 설계하지 않는다. 단순한 실행 제한 설명에는 입력 모달보다 안내 메시지가 적합하다. [Discord 컴포넌트·모달](https://docs.discord.com/developers/platform/components), [Interaction 응답](https://docs.discord.com/developers/interactions/receiving-and-responding)

시스템 안내는 캐릭터 대사와 구분해 렌더링한다. 모델이 상세 사유를 창작하게 하지 않고 실행 결과에 연결한다. 안내·도구 결과를 일반 대화 경험으로 추출하지 않는 계약은 메모리 개발 계획 §17에서 다룬다.

## 5. 후속 구현 전에 정할 사항

- 서버 프로필과 계정 기본 프로필 중 요청 대상을 어떻게 명확히 선택할지. 서버 프로필 변경 실패를 계정 프로필 변경으로 자동 대체하지 않을지.
- 계정 전체 소개의 실제 필드·지원 API와 discord.js 호출 경로.
- 계정·서버 작업별 요청자 권한, `/활성화` 변경 권한, 봇의 자율 변경 허용 범위.
- 몰입형·명시형 설정의 적용 단위와 안내 버튼 표시 정책.
- 확인된 현재 플랫폼 상태의 CHAT 제공 방식과 갱신 시점.
- 동시에 들어온 프로필·상태 변경의 실행 순서와 성공 확인 방식.

공식 지원 사실을 제외한 제품 정책은 이 문서 작성만으로 확정하지 않는다.
